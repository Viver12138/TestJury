## 1. 数据职责

| 数据对象 | 职责 | 可重建 | 可修改 |
|---|---|---|---|
| `model_runs` | 模型调用过程与原始响应 | 否 | 只追加 |
| `review_stages` | 阶段 Checkpoint | 否 | 状态推进 |
| `review_candidates` | 融合产生的候选问题、主张与证据 | 可由阶段输出重建 | 仲裁前可更新状态 |
| `candidate_embeddings` | 候选向量 | 是（按 profile 重建） | 可重建 |
| `issue_votes` | 投票事实 | 否 | 只追加（首次为准） |
| `report_json` | 最终报告唯一事实源 | 否 | 生成后不可变 |
| `issues` | 最终问题查询投影 | 是（从 `report_json`） | 仅重建 |
| `human_feedback` | issue 级人工反馈 | 否 | 只追加 |
| `review_decisions` | 报告级人工决定 | 否 | 只追加 |
| `kb_*` / `kb_versions` | 知识库运行时副本 | 是（从 Git） | 发布流程 |

## 2. 核心关系

```
review_jobs 1 ── n review_stages
review_jobs 1 ── n review_candidates 1 ── n issue_votes
review_candidates 1 ── 1 candidate_embeddings（按 profile 可多条）
review_jobs 1 ── 1 report_json 1 ── n issues
issues.candidate_id → review_candidates.id（可空，主审补充问题可无候选）
```

## 3. 外键与唯一约束

| 表 | 约束 | 目的 |
|---|---|---|
| `review_candidates` | `UNIQUE (review_id, candidate_no)`；`UNIQUE (id, review_id)` | 编号唯一；供复合外键引用 |
| `issue_votes` | `UNIQUE (candidate_id, reviewer_id)`；`FK (candidate_id, review_id) → review_candidates(id, review_id)` | 一人一票，且投票与候选同属一个评审 |
| `issue_votes` | `FK model_run_id → model_runs(id)` | 可回溯到调用 |
| `issues` | `UNIQUE (review_id, issue_no)`；`UNIQUE (review_id, candidate_id)`；`FK (candidate_id, review_id) → review_candidates(id, review_id)` | 最终问题与候选一一对应且同评审 |
| `candidate_embeddings` | `PK (candidate_id, embedding_profile_id)`；`FK (candidate_id, review_id) → review_candidates(id, review_id)` | 每候选每 profile 一条且同评审 |
| `review_stage_attempts` | `UNIQUE (review_id, stage, attempt_no)` | 每次尝试可追溯，不覆盖历史 |
| `human_feedback` | `FK (issue_id, review_id) → issues(id, review_id)` | 反馈不能挂到别的评审的 issue |
| `review_stages` | `UNIQUE (review_id, stage)` | 仅当前态；历史在 attempts |
| `review_decisions` | `decision_no` 递增；`INDEX (review_id, decision_no)` | 当前决定 = max(decision_no)；并发用行锁 |
| `review_jobs` | 部分唯一索引 `(idempotency_key) WHERE superseded_by IS NULL` | 同时只有一个 active 代次 |
| `review_jobs` | `fencing_token` 单调递增；阶段/终稿写入按令牌校验 | 防止旧 Worker 覆盖新结果 |
| `batches` | `UNIQUE (idempotency_key) WHERE idempotency_key IS NOT NULL` | 批次级幂等 |

> PostgreSQL 普通唯一约束对 NULL 的处理：`candidate_id` 可空时 `UNIQUE(review_id, candidate_id)` 不阻止多条 NULL；主审补充问题需要单独规则（按 `issue_no` 唯一即可）。

## 4. 复合外键示例

```sql
ALTER TABLE review_candidates
    ADD CONSTRAINT uq_candidate_review UNIQUE (id, review_id);

ALTER TABLE issue_votes
    ADD CONSTRAINT fk_vote_candidate
    FOREIGN KEY (candidate_id, review_id)
    REFERENCES review_candidates (id, review_id);

ALTER TABLE issues
    ADD CONSTRAINT fk_issue_candidate
    FOREIGN KEY (candidate_id, review_id)
    REFERENCES review_candidates (id, review_id);
```

这样即使应用层传错 `review_id`，数据库也会拒绝。

## 5. 投票一致性

- 投票只能写 `candidate_id`，`issue_id` 由投影回填，可为空。
- 同一候选同一模型只允许一条；重复投票默认拒绝（v1 以首次为准）。
- 投票所属 `review_id` 必须与候选一致（复合外键）。
- 投票不因仲裁被修改；仲裁结果写入 `issues.chief_*` / `report_json`，不改 `issue_votes`。
- 模型失败/超时不得写成 `reject`；只能 `not_assessed` 或没有记录（并计入完整性）。

## 6. 证据与主张

`review_candidates.claims`（JSONB）：

```json
[
  {
    "claim_id": "claim_001",
    "claim_role": "core",
    "relation": "and",
    "claim_text": "未覆盖背包已满场景",
    "evidence": [
      { "ref": "chunk:8842", "type": "requirement", "level": "E2" }
    ],
    "evidence_status": "supported"
  }
]
```

- `claim_role` 由模型提出、服务端按 Rubric 校验；投票后冻结；仲裁只能补证据/解释，不能改 core 或候选描述。
- 每个候选至少 1 个 `core`；`core` 缺 E1/E2 → 不得判 blocker。

`evidence_status` 取值与判定：

| 状态 | 条件 |
|---|---|
| `grounded` | 所有关键 claim 均有 E1/E2 证据 |
| `partially_grounded` | 部分 claim 有证据 |
| `ungrounded` | 无 E1/E2 证据（仅 E3/E4 或空） |
| `conflicted` | 证据之间冲突 |
| `insufficient` | 有证据但不足以支持结论 |

**融合不得自动提高证据强度**：合并后按每个 claim 各自证据重新计算，不能把 A 的证据直接算到 B 的主张上。

## 7. 报告不可变性

- `report_json` 写入后置 `report_locked_at`；应用层禁止 UPDATE。
- 数据库触发器：`report_locked_at IS NOT NULL` 时拒绝 `UPDATE report_json/report_summary/ai_verdict`。
- 需要更正时新建 generation，旧报告保留；记录更正原因与操作者（审计）。
- `issues` 投影只读；重建用 `rebuild_projection.py`，不手工改。
- **Schema 多版本**：历史报告按 `report_schema_version` 读取，不自动迁移；渲染器按版本选择；转换只生成派生数据（见 `schemas/README.md`）。

## 8. 生命周期与删除

| 数据 | 保留 | 删除方式 |
|---|---|---|
| `model_runs.raw_*` | 180 天 | 定时清理，审计保留最小字段 |
| `report_json` / `issues` | 长期 | 仅按合规审批删除，先解绑再删 |
| `review_decisions` / `audit_log` | 长期 / ≥1 年 | 审计不可删 |
| `candidate_embeddings` | 随候选 | 级联删除或重建 |

删除评审任务时按 `ON DELETE CASCADE` 清理候选、投票、阶段、投影、决定、webhook；审计只保留 `review_id`、操作、时间。

## 9. Schema 一致性检查清单

- [ ] 所有 `candidate_id` / `issue_id` / `review_id` 的 FK 与唯一约束在 02 与实际迁移一致。
- [ ] `issue_votes` 不再出现 `UNIQUE(issue_id, reviewer_id)`。
- [ ] `review_candidates` 先于 `issues` 创建（或迁移顺序正确）。
- [ ] `candidate_embeddings` / `human_feedback` 使用复合外键绑定 `review_id`。
- [ ] `review_stage_attempts` 保存每次尝试，`review_stages` 只存当前态。
- [ ] `candidate_embeddings` 与 `issue_embeddings` 的 profile 一致。
- [ ] `report_json` 与 `issues` 的 issue_no / severity / status 可逐条对齐。
- [ ] 删除级联覆盖所有子表。
- [ ] 可空字段上的唯一约束行为经过测试（NULL 不会误判冲突）。
- [ ] 主审补充问题的 `candidate_id` 为 NULL，靠 `issue_no` 唯一，不被误判重复。

## 10. CHECK 与事务边界

- 关键状态字段加 CHECK：`review_jobs.status`、`ai_verdict`、`human_status`、`review_stages.status`、`review_candidates.status`、`issues.status`、`issue_votes.validity`、`severity`。
- JSONB 结构（`claims`、`test_scope`、`automation_context`）由应用层 Schema 校验，数据库只保证 JSON 合法。
- **同一事务**内完成：`report_json` + `issues` 投影 + `report_locked_at` + `review_jobs.ai_verdict/status`。
- 审批事务内完成：`review_decisions` INSERT + `review_jobs.human_status/current_decision_id` 更新；用 `SELECT ... FOR UPDATE` 锁 review 行，避免并发顺序竞争。
- 阶段事务内完成：`review_stage_attempts` INSERT + `review_stages` upsert。
- 任何事务失败必须回滚，不允许"报告写了、投影没写"的半成品。

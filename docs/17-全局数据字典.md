### 4.1 知识来源与历史缺陷升级（D181）

每条知识必须能说明"从哪来、是否当前有效"：

| 字段 | 取值/含义 |
|---|---|
| `origin_type` | `requirement` / `specification` / `test_standard` / `historical_bug` / `expert_rule` |
| `derived_from` | 来源文档或缺陷 ID（升级规则必须填） |
| `bug_version` | 历史缺陷发生版本（`historical_bug` 必填） |
| `fixed_version` | 修复版本（已知时必填） |
| `current_validity_confirmed` | 是否已确认当前仍有效（布尔） |
| `confirmed_by` / `confirmed_at` | 确认人/时间 |
| `rule_status` | `draft` / `reviewed` / `published` / `deprecated` |

历史缺陷升级为正式规则必须同时满足（详见 `docs/29` §3.1）：可定位原始缺陷、确认发生版本与条件、确认是稳定业务约束而非一次性错误、模块负责人确认当前仍有效、明确适用范围/生效版本/失效条件、`kb_reviewer` 审核、生成新 RULE-ID 或明确规则版本且不覆盖历史记录。

三类知识分开：历史缺陷 `historical_bug` 仅供风险线索（不可作当前判定依据）；待确认经验需标待确认；已审核正式规则才能作当前依据，且仍需匹配版本与适用条件。

### 4.2 项目内容、治理与基线（2026-11-12）

`design/kb_contract.yaml` 是项目内容兼容映射的机读版本；内容格式详见根目录 `TestJury_项目知识库数据规范_v1.0.md` §6.5–§6.6。`id → doc_id`、`module_id → module`、`knowledge_type → doc_type`；平台 `doc_type` 仍使用 §4 的现有枚举，原 `knowledge_type` 和 `evidence_level` 不丢弃、不自动升级。

| 字段 | 取值/含义 |
|---|---|
| `content_status` | 内容格式中的 `draft` / `in_review` / `approved` / `deprecated` / `superseded` / `rejected` / `archived` |
| 内容到平台状态 | `draft/in_review → draft`；`approved → reviewed`；其余退出有效集合的状态 → `deprecated` |
| `knowledge_governance.decision_status` | `pending` / `decided`；只表示人工决策 |
| `knowledge_governance.documentation_status` | `pending` / `synced` / `reviewed`；知识回写不等于复审 |
| `knowledge_governance.implementation_status` | `not_required` / `pending` / `implemented`；与设计决策台账的同名字段分属不同对象 |
| `knowledge_governance.verification_status` | `not_verified` / `passed` / `failed`；passed 必须有可访问验证证据 |
| `review_baseline.type` | `current_implementation` / `target_specification` |
| `review_baseline.product_version` | 被测产品版本；不能用 TestJury 设计版本替代 |
| `review_baseline.source_ref/source_version` | 当前实现绑定仓库及完整 commit；目标规则绑定受控决策材料及 SHA-256 |
| `formal_admission` | `blocked` / `conditional` / `allowed`；必须限定项目、模块、评审类型、构建版本和解除条件 |

`approved` 不等于 `published`；解析器和候选构建不得自动发布。项目级 `module=null` 仍受项目隔离。MiniShop 当前处于候选内容阶段，全部正式准入保持 blocked；线上任务的基线冻结和 active 检索接入需后续实现。

## 5. 角色与权限

| 角色 | 系统权限 | 知识库权限 |
|---|---|---|
| `reviewer` | 提交评审、issue 反馈、request_changes | — |
| `approver` | 上述 + approve/reject | — |
| `admin` | 系统配置、模型配置、强制重跑 | 可管理账号 |
| `kb_creator` | — | 创建/修改 `draft` |
| `kb_reviewer` | — | 审核 → `reviewed` |
| `kb_publisher` | — | 发布/废弃/回滚 |

- `admin` 不自动获得 `approver` 或 `kb_publisher`。
- 一个身份可绑定多个角色，但必须服务端授予。
- 生产环境 `kb_creator` 与 `kb_publisher` 不得为同一人（可配置）。

业务角色映射（`docs/00` §3.5）：

| 业务角色 | 系统角色/身份 |
|---|---|
| 测试工程师 | `reviewer` |
| 测试负责人 | `approver` |
| 调用系统 | 系统级 API Key（`caller_id`），不默认拥有审批权 |
| 平台管理员 | `admin`，不自动拥有 `approver` |

`api_keys` 授权表（v1.13 / D222）：`key_hash`（sha256，唯一）、`actor_id`、`actor_type`、`roles[]`、`caller_id`、`revoked_at`、`expires_at`；**明文 Key 不落库**。鉴权头统一 `Authorization: Bearer <api-key>`，角色与 `caller_id` 只从该表解析，`X-Role`/`X-Caller-Id` 不作为授权依据。

## 9. 幂等与代次（引用，不重复定义）

提交幂等与代次的语义**不在本文件重复定义**，唯一口径是 `docs/03` §1.1（提交行为矩阵 S1–S7）；本节只固定字段归属：

| 字段 | 所在表 | 语义 | 谁生成 |
|---|---|---|---|
| `case_version` | `review_jobs` | 用例业务版本，不参与内容判重 | 调用方 |
| `input_hash` | `review_jobs` | 规范化输入的内容指纹 | 服务端 |
| `generation` | `review_jobs` | 同一 `idempotency_key` 下的评审代次 | 服务端 |
| `idempotency_key` | `review_jobs` | 输入 + 全部影响结论的版本组合 | 服务端 |
| `parent_review_id` | `review_jobs` | 指向上一代次（历史链） | 服务端 |
| `superseded_by` | `review_jobs` | 指向取代它的下一代次；**仅任务代次链使用** | 服务端 |

规则：

- `review_decisions`、`human_review_events` **不使用** `superseded_by`；人工决定与事件只追加，当前有效决定按 `decision_no`/最新事件取。
- `superseded_by` 是单向指针，只由 `force` 在旧代次终态时写入；不允许手工回填或双写。
- 审批、报告、证据都引用具体 `review_id`，不引用"当前 active 记录"。
- 内容变化由 `input_hash` 决定，业务版本变化（`case_version`）不触发重评。

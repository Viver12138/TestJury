## 3. 关键实现要点

### 3.1 结论由服务端计算

`verdict.py` 是唯一权威。模型输出 `verdict` 只作为对照，不一致时记日志并用服务端结果覆盖。这是防止仲裁模型"凭感觉给结论"的最后一道闸。

### 3.2 仲裁输出完整性校验

仲裁返回后，服务端逐条比对融合清单：

```
缺失条目 → 补为 need_human，parse_warnings += "arbitration_omitted:FUSED-00X"
出现清单外条目 → 若 chief_decision=supplement 且证据完整则接受；否则丢弃并记警告
```

### 3.3 融合中的 embedding 调用

- 用同一 embedding 模型生成问题文本向量，写入 `issue_embeddings`。
- 若 embedding 服务不可用，**退化为规则键直接合并**（只按 `case_id + dimension + step_bucket` 合并），并在报告标注"本次融合未使用语义合并"。

### 3.4 队列与状态推进

- 单进程 asyncio：`asyncio.Semaphore(4)` + 内存队列。
- 任务状态实时写库（每个 stage 变更更新 `review_jobs.stage`），进程重启时把 `processing` 任务重置为 `queued`（最多重试 1 次，避免死循环）。
- 批量任务只是 `review_jobs.batch_id` 的聚合，不单独调度。

### 3.5 版本号

```python
kb_version     = sha256(所有 kb_content 文件内容 + 规则文件) 取前 12 位
rubric_version = sha256(rubric.yaml) 取前 12 位
prompt_version = 每个 prompt 文件独立 sha256 前 8 位
```

版本号在服务启动时计算并缓存；知识库热重载后重新计算。

## 5. 开发顺序（里程碑）

| 里程碑 | 内容 | 完成标志 |
|---|---|---|
| M0 | 骨架：FastAPI + DB + 模型 Mock + 结论判定 | `seed_demo.py` 用 mock 输出跑通全链路，报告可渲染 |
| M1 | 真实三模型接入 + 存档 + 计量 | 单份用例得到真实报告，`model_runs` 有完整原文 |
| M2 | 知识库加载 + 检索 + 降级 | 模块命中/未命中两条路径都可复现 |
| M3 | 融合 + 仲裁校验 + 人工复核清单 | 同一问题多模型提出时正确合并，驳回项进清单 |
| M4 | 复核回写 + 缺口聚合 + 批量接口 | 复核能落库，缺口清单可导出 |
| M5 | 种子集评测 + 阈值与 prompt 调优 | 指标达标（见 07） |

> 建议 M0–M4 完成后再做一次端到端演示，M5 才动 prompt 细节 —— 没有评测数据前调 prompt 是盲调。

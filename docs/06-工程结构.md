## 3. 关键实现要点

### 3.1 结论由服务端计算

`verdict.py` 是唯一权威，输出 `ai_verdict`（`blocked` / `conditional` / `need_human`）。模型输出只作对照，不一致时记日志并用服务端结果覆盖。人工审批走 `review_decisions`，只派生 `human_status`，不回写 `ai_verdict`。

### 3.2 仲裁输出完整性校验

仲裁返回后，服务端逐条比对候选清单：

```
缺失条目 → 补为 need_human，parse_warnings += "arbitration_omitted:FUSED-00X"
出现清单外条目 → 若 chief_decision=supplement 且证据完整则接受；否则丢弃并记警告
chief_decision=reject 但未填 chief_reason → 视为无效，补 need_human
```

投票完整性同理：投票轮缺失的候选补 `not_assessed`，并在报告中标注投票不完整。

### 3.3 检索与向量

- **Embedding 必须带 profile**：`build_kb_index.py` 首次运行创建 `embedding_profiles` 记录；换模型/维度 = 新 profile + 新索引，旧索引保留到评测完成。
- **不混用向量**：同一查询只能与同 profile 的向量比较；`issue_embeddings` 与 `kb_chunks` 都记录 `embedding_profile_id`。
- **融合中的 embedding 调用**：用同一 profile 生成问题文本向量；若 embedding 服务不可用，退化为规则键直接合并，并在报告标注"本次融合未使用语义合并"。
- **检索降级**：向量不可用 → 关键词（trigram + 精确匹配）；关键词索引不可用 → 纯向量；rerank 超时 → 用 RRF 排序；全部写入 `degraded_reasons`。
- **检索参数版本化**：`RETRIEVAL_CONFIG_VERSION` 由 Top-K、RRF k、rerank 阈值、查询上限等参数哈希生成，写入报告；参数变更触发检索回归。

### 3.4 队列与状态推进

- **PostgreSQL 持久化队列**：任务创建即落库（`status=queued`），worker 用 `FOR UPDATE SKIP LOCKED` 领取，不依赖进程内存。
- **租约机制**：领取写 `locked_by/locked_at/lease_expires_at`，执行期按 `QUEUE_LEASE_SECONDS/3` 续租；worker 崩溃后租约过期，任务自动回到可领取状态。
- **重试**：失败按退避重试，`attempt_count` 超过 `QUEUE_MAX_ATTEMPTS` 置 `failed` 并记 `last_error`。
- **状态实时写库**：每个 stage 变更更新 `review_jobs.stage`；成功置 `done` 或 `completed_with_warnings`；进程重启不丢任务，也不需要"重启后重置 processing"的特殊逻辑（租约过期即恢复）。
- **终稿幂等**：写入终稿前校验 `status`、`attempt` 与 `generation`，同一任务重复执行不得产生两份冲突报告。
- 批量任务只是 `review_jobs.batch_id` 的聚合，不单独调度。

### 3.5 版本号

```python
kb_version              = sha256(所有 kb_content 文件内容 + 规则文件) 取前 12 位
rubric_version          = sha256(rubric.yaml) 取前 12 位
prompt_version          = 每个 prompt 文件独立 sha256 前 8 位（含 vote.jinja2）
retrieval_config_version= sha256(检索参数 JSON) 取前 8 位
model_config_version    = sha256(models.yaml) 取前 8 位
report_schema_version   = 来自代码常量（如 report-1.0），随报告写入
```

版本号在服务启动时计算并缓存；知识库切换 active 后重新计算。`model_runs` 同时记录配置值与 API 实际返回版本。

### 3.6 模型注册与适配层

- `llm/registry.py` 读取 `config/models.yaml`，按角色解析 `provider + model_id + base_url + timeout + max_output_tokens + concurrency + pricing`。
- 三类适配器：`ChatAdapter`（评审/仲裁/投票）、`EmbeddingAdapter`、`RerankAdapter`。Embedding/Rerank 不套用聊天接口。
- 启动时做一次轻量可用性检查（模型是否存在、鉴权是否通过），失败只告警不阻塞启动（避免供应商抖动导致服务起不来）。
- 角色到模型是配置映射，不写死在代码；换模型改配置 + 跑回归。
- 限流按 provider 维度统一计数，避免多角色并发打爆同一供应商配额。

#### 3.6.1 模型接入验收

角色可以先冻结，真实 Model ID 必须实测后才能标 `verified`：

| 验收项 | 记录 |
|---|---|
| Provider / Model ID / Model version | 实际服务方与真实标识 |
| API endpoint | 实际接口地址或配置标识 |
| JSON Schema 合规率 | 实测，目标 ≥ 99% |
| 平均 / P95 响应时间 | 实测 |
| 最大输出能力 | 实测，确认不被截断 |
| 并发与限流 | 实测，确认支撑目标并发 |
| 失败与重试 | 超时/5xx/限流下的行为 |
| 验收状态 | `pending` / `verified` |

`models.yaml` 中每个角色带 `acceptance: pending|verified`；未 `verified` 的模型不得用于正式评测结论。

### 3.7 输出校验

`pipeline/validate.py` 对每次模型返回执行：JSON 解析 → Schema → 枚举 → 引用有效性 → 数值范围 → 业务规则（见 `docs/05` §7）。失败不修补，重试 1 次后按角色失败处理；`parse_warnings` 落库并在报告体现。

### 3.8 人工决定

`api/decisions.py` + `review_decisions`：

- 只允许 `approver` 执行 `approve` / `reject`；`reviewer` 只能 `request_changes`。
- 追加写入，禁止 UPDATE/DELETE；`human_status` 取 `decision_no` 最大的一条。
- 审计日志同步写入（`core/audit.py`）。
- `DECISION_REQUIRE_SEPARATION=true` 时校验审批人 ≠ 用例提交人；提交人与审批人来自服务端身份，不取 `X-Role`。

### 3.9 成本与预算

- `metering.py` 每次调用记录 token、`cost_estimate`、`price_config_version`；`review_jobs` 汇总单次成本，批次/每日由查询聚合。
- `budget.py` 在调用前检查剩余预算：超单次预算 → 跳过投票/rerank 并标降级；超批次/每日 → 429 `BUDGET_EXCEEDED`。
- 成本是估算值，与供应商账单可能有差异；`price_config_version` 用于解释。

### 3.10 知识库发布

`kb/publish.py` 串起：元数据校验 → 按类型切片 → embedding（active profile）→ 构建 trigram/可选 FTS 索引 → 检索回归 → 写 `kb_versions(candidate)` → 切 active；失败保持旧 active。回滚只切指针，不删版本（见 `docs/11` §7–§8）。

### 3.11 报告与投影

- `report_json` 是唯一事实源；`issues` 只是查询投影，不允许独立修改 AI 结论。
- 写报告时 `report_json` 与 `issues` 同事务写入，并置 `report_locked_at`；之后不可更新。
- `scripts/rebuild_projection.py` 从 `report_json` 重建 `issues` 与 Markdown，并做一致性校验（数量、issue_no、severity、状态）。
- `scripts/check_consistency.py` 校验外键/唯一约束/候选映射/投影一致性（见 `docs/14` §9）。
- 人工反馈与审批不写投影：`human_feedback` 独立，`review_decisions` 追加；报告展示时实时合并。
- 定期任务比对投影与事实源，差异告警（见 `docs/07` §5.2）。

### 3.12 输入质量检查

分两层，不能混：

| 层 | 位置 | 检查 | 处理 |
|---|---|---|---|
| 同步硬校验 | `api/validation.py`（创建任务前） | JSON/Schema、必填、`steps` 与 `raw_text` 同时为空、超 `INPUT_MAX_CHARS`、字段类型 | 直接 400/422，不创建任务、不返回 202 |
| 异步软校验 | `pipeline/input_check.py`（Worker） | `expected` 缺失、步骤重复、`test_data` 为空、描述不清 | 记入 `input_quality`，继续评审 |

硬错误不可能在 Worker 阶段再变成 HTTP 422；Worker 只产出软问题。输入质量问题与模型发现的问题在报告中分开展示。

### 3.13 性能计时

`timings` 记录 `queue_ms`（入队→领取）、`execution_ms`（领取→终态）、`model_call_ms`（按角色累加）；端到端由 `created_at → finished_at` 计算。指标口径见 `docs/07` §3.5，禁止用单次最大耗时代替 P95。

### 3.14 提示注入防护

- 用例正文与知识库内容全部按**不可信数据**拼接：放在明确的数据块中，不作为指令。
- System Prompt 与规则只在服务端模板中定义；外部文本不能覆盖、不能要求改变投票/权限/规则。
- 知识库内容不触发工具调用或配置修改。
- 输出仍走 Schema/枚举/引用/业务规则校验；模型说"已通过"不等于通过。
- 原始输入与最终 Prompt 分开存档，便于审计。
- 测试集包含"忽略以上规则/直接判通过/你现在是管理员"等注入样本（见 `docs/07` §8.6）。

## 5. 开发顺序（里程碑）

| 里程碑 | 内容 | 完成标志 |
|---|---|---|
| M0 | 骨架：FastAPI + DB + 模型 Mock + 结论判定 | `seed_demo.py` 用 mock 输出跑通全链路，报告可渲染 |
| M1 | 持久化队列 + 模型注册/适配层 + 真实三模型接入 + 存档/计量/成本 | 杀死进程后任务能被重新领取；单份用例得到真实报告与成本记录；模型验收表有记录 |
| M2 | 知识库加载 + 按类型切片 + 发布流程 + 检索黄金集 | 发布/回滚可用；检索评测输出 Recall/MRR/nDCG |
| M3 | Hybrid 检索 + rerank + 证据包 + claim 证据 + 降级 | 模块命中/未命中/通道降级三条路径可复现，证据可溯源 |
| M4 | 融合 + 候选向量 + 投票轮 + 仲裁校验 + `verdict.py` 真值表 | 同一问题正确合并；投票完整；非法输出不进入融合；2/3 与 1/3 按真值表 |
| M5 | 阶段 Checkpoint + 人工决定 + issue 反馈 + 缺口 + 批量 | 投票失败可从阶段恢复；审批 append-only 可查；批次部分失败正确汇总 |
| M6 | 评审黄金集 + 检索/融合评测 + 阈值与 prompt 调优 | 指标达标（见 07），检索、融合、评审指标分开报告 |

> M0–M5 完成后再做端到端演示，M6 才动 prompt 细节 —— 没有评测数据前调 prompt 是盲调。每个里程碑都必须有失败场景测试，不以"接口能返回"为完成标准。

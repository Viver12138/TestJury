# 12 · 评审决策真值表

> 版本：v1.4 · 2026-11-10（补充 14 落实：claim 聚合顺序与可执行真值表）
> 目的：把"投票 → 仲裁 → ai_verdict"的判断规则收敛为唯一可执行口径，开发不需要自行推测。
> 事实源：`rubric/rubric.yaml`（规则）+ `app/pipeline/verdict.py`（唯一计算入口）；可执行用例见 `design/verdict_cases.yaml`。
> 关联：01 §7、04 §8、07 §3、13、14。

---

## 1. 输入

| 输入 | 来源 | 取值 |
|---|---|---|
| `participants` | `review_completeness` | 3 / 2 / 1 / 0 |
| `validity` 票 | `issue_votes.validity` | `accept` / `reject` / `uncertain` / `not_assessed` |
| `severity` 票 | `issue_votes.severity` | `blocker` / `major` / `suggestion` / null |
| `evidence_status` | 候选/最终问题 | `grounded` / `partially_grounded` / `ungrounded` / `conflicted` / `insufficient` |
| `arbitration` | 主审输出 | `adopt` / `reject` / `dispute` / `need_human` / `supplement` |
| `disputed` | 融合/仲裁 | true / false |

## 2. 成立性（validity）判定

> 计票单位是 `participant_id`（本次席位），不是模型名或角色名。一个角色对应一个席位；席位故障可由 fallback 模型顶上，但角色不变、票仍记在该席位。

| 参与数 | 条件 | 结果 |
|---|---|---|
| 3 | accept ≥ 2 且 reject < 2 | `accepted` |
| 3 | reject ≥ 2 | `rejected` |
| 3 | 其它（如 1 accept / 1 reject / 1 not_assessed） | `disputed` |
| 2 | accept = 2 | `accepted` |
| 2 | reject = 2 | `rejected` |
| 2 | 1 accept + 1 reject | `disputed` |
| 2 | 1 accept + 1 not_assessed/uncertain | `insufficient` → need_human |
| 1 | 任意 | 不形成成立性结论（`ai_verdict=null`） |
| 0 | — | 任务失败 |

> `not_assessed` / `uncertain` 永远不计为 `reject`。
>
> 2 席时，只有 1 票明确（另一票 `not_assessed`/`uncertain`）时，无论明确票是 `accept` 还是 `reject`，都判 `insufficient` → `need_human`；不得把单票当多数（对应 VC-007/VC-008）。

## 3. 严重级（severity）判定

只统计 `validity=accept` 的票：

| 条件 | 结果 |
|---|---|
| 无 accept 票 | 不计算 severity |
| accept 票 severity 全部一致 | 该级别 |
| 最高与最低相差 1 级（如 major vs suggestion） | 取较高者，标 `severity_provisional=true` |
| 最高与最低相差 ≥2 级（blocker vs suggestion） | `severity_disputed` → need_human |
| accept 票中有 severity 缺失 | 缺失票不参与；若全部缺失 → need_human |

## 4. 问题级结论

一条候选/问题按下列顺序判定，命中即停：

| 顺序 | 条件 | 问题状态 |
|---|---|---|
| 1 | 参与数 < 2 | `need_human`（无法形成结论） |
| 2 | `evidence_status=conflicted` | `need_human`（证据冲突） |
| 3 | validity = `rejected` | `rejected` |
| 4 | validity = `disputed` 或 `insufficient` | `disputed` / `need_human` |
| 5 | validity = `accepted` 且 severity = `severity_disputed` | `need_human` |
| 6 | validity = `accepted` 且 severity = `blocker` 且 `evidence_status ∈ {grounded, partially_grounded}` | `blocker` |
| 7 | validity = `accepted` 且 severity ∈ {major, suggestion} | 对应级别 |
| 8 | 其它 | `need_human` |

> `historical_bug` / `inference` 不满足第 6 条的证据要求；`ungrounded` / `insufficient` 不能判 blocker。

### 4.1 Claim 级证据聚合

每条 claim 先独立判定：`supported`（有 E1/E2 且匹配）/ `unsupported`（无证据）/ `conflicted`（证据互斥）/ `insufficient`（有证据但不足以支持）。

**核心 Claim 的确定权**：

- Rubric 定义每个 issue 类别允许的 `core` claim 数量、可支撑的最高严重级、以及 core 必须绑定的证据等级。
- 模型提出 `claim_role=core|supporting` 与 `relation=and|or`，**不能自行把 supporting 改成 core 来抬高严重级**。
- 服务端校验：至少 1 个 core；core 必须绑定证据；core 数量/等级符合 Rubric；不符合则降级或判无效。
- 投票开始后 claim 结构与 role 冻结；仲裁只能补证据/解释，**不能删除原始 claim、不能把 supporting 改成 core、不能改候选描述**。发现候选重大错误 → 驳回该候选或新建候选并保留关联，不能沿用原投票。

问题级 `evidence_status` 按固定算法聚合，不由模型自由判断（实现与 `design/verdict_cases.yaml` 的 VC-021–VC-026 一一对应）：

1. 任一 claim 为 `conflicted` → `conflicted`；
2. 全部 claim 都没有 E1/E2 → `ungrounded`（E3/E4 只能支撑非 blocker 说明，不能算"已 grounding"）；
3. core claim（支撑严重级判断的那条）为 `unsupported` / `insufficient` → `insufficient`；
4. core supported，但存在非 core claim 非 supported → `partially_grounded`；
5. 存在 E1/E2 但 core 本身是 E3/E4 → `ungrounded`（核心主张不能靠旁证升级）；
6. 全部 claim supported 且 core 为 E1/E2 → `grounded`。

> 顺序固定、命中即停；不得先看模型自报的 `kb_grounded` 再挑证据。

**Blocker 额外要求**：核心严重性 claim 必须 `supported`，且证据等级为 E1/E2。  
`partially_grounded` 的问题可以保留，但若判 blocker，必须进人工复核；不允许非核心 claim 借用核心 claim 的证据。

**部分证据 blocker 的报告级处理**：`partially_grounded` 的 blocker 仍可使 `ai_verdict=blocked`，但必须同时：
- 进入 `human_review_items`（原因：证据部分支持）；
- 报告标注"blocker 证据部分支持，待人工确认"；
- `human_status=pending`，不得自动通过；
- 不得把该 blocker 降级为 `major` 来规避人工复核。

Claim 关系默认 **AND**（多个主张共同构成问题）；只有描述明确写"任一"时才按 OR，且必须在 `claims` 中标记 `relation=or`。

## 5. 报告级 Verdict

| 条件 | `ai_verdict` |
|---|---|
| 存在问题状态 `blocker`，且该问题未被 ≥2 明确 reject | `blocked` |
| 主审驳回陪审提出的 blocker，且两陪审均未同意驳回 | `blocked` + 待人工裁决 |
| 无 blocker，但存在 `disputed` / `severity_disputed` / `need_human` / evidence conflict | `need_human` |
| 无 blocker、无争议、参与数 ≥2 | `conditional` |
| 参与数 = 1 | `ai_verdict=null`（不出正式结论） |
| 参与数 = 0 | 任务失败，不出结论 |

**系统永不输出 `approved`。** 人工 `approve` 只改变 `human_status`，不改变 `ai_verdict`。

## 6. 不完整评审（2/3）

- 允许形成 `blocked` / `conditional` / `need_human`，但必须：
  - `review_completeness.complete=false`；
  - 报告顶部标"仅 2/3 模型参与"；
  - 结论强度不得表述为"完整三方评审"。
- 2/3 下 `accepted` 需 2 票一致，不能用 1 票 + 1 未评估推出"多数"。
- 2/3 下的 blocker 仍可成立，但必须进入人工复核清单（建议默认，可配置）。
- **每条候选独立计算 `vote_completeness`**：全局 3/3 不代表每条候选都有 3 票。候选有效票 <2 → 该候选 `need_human`；不得用全局参与数替代。

## 7. 仲裁触发与结果

| 触发 | 是否必须仲裁 |
|---|---|
| 存在 `disputed` / `severity_disputed` | 是 |
| 主审拟补充 blocker | 是（且补充后进人工清单） |
| 主审拟驳回陪审 blocker | 是（且进人工清单） |
| 证据冲突 | 是 |
| 全部一致且无争议 | 否，直接规则计算 |

仲裁结果只影响"是否采纳/是否转人工"，**不能修改原始投票**；最终 `ai_verdict` 仍由 `verdict.py` 按本表计算。

**条件执行**：服务端先算分歧；无触发项时跳过主审仲裁，记 `arbitration_required=false`，直接进入规则计算。跳过不代表"主审同意"，报告中必须说明本次未发生仲裁。

## 8. 禁止组合

- `ai_verdict=blocked` 但无 `blocker` 问题；
- `ai_verdict=conditional` 但存在 `disputed`；
- `ai_verdict=approved`（任何情况）；
- 1/3 参与却给出正式 `blocked/conditional`；
- `severity=blocker` 且 `evidence_status=ungrounded`；
- 人工 `approved` 被渲染成"用例通过"。

出现以上任一情况，视为实现缺陷，必须阻断发布。

## 9. 可执行真值表与测试

本表不只是说明文档，配套机器可读用例：

| 文件 | 作用 |
|---|---|
| `design/verdict_cases.yaml` | 36 条固定/参数化/边界/属性/非法输入用例，逐条标注规则 ID（R-*）与 docs/12 章节 |
| `scripts/verdict_reference.py` | 规范参考判定器（纯函数），按本表规则计算 `ai_verdict` / issue 状态 / 完整性 |
| `scripts/check_verdict_cases.py` | 结构与覆盖检查 + 参考判定器一致性 + I1–I8 属性抽样（每轮 3200 组） |

要求：

1. M0 起 `app/pipeline/verdict.py` 必须对同一批用例给出与参考判定器相同的结果；不一致时以本表为准，修实现或修用例并记录理由。
2. 每条规则至少有正例、反例或边界例；修改本表必须同步用例与 `docs/28` §5。
3. 禁止组合（§8）由用例层与实现层各校验一次；只记日志不算通过。
4. 参考判定器不读数据库、不调模型，仅用于对照，不得被生产代码引用。

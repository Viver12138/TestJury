补充 14 的结论是：**不再新增 P0 架构模块，转而清理契约残留、建立自动检查、把 M0 退出条件变成可执行用例**。本轮按此执行，交付四类东西：

| 类别 | 交付 | 落点 |
|---|---|---|

## 2. P0-1：幂等与代次契约收口

### 2.1 唯一口径

`docs/03` §1.1 是提交幂等与代次的**唯一来源**，核心是 S1–S7 行为矩阵：

| # | 输入 | 结果 |
|---|---|---|
| S1 | 无历史记录 | 202，`generation=1` |
| S2 | 已有 active、未 `force` | 200 + 原任务真实状态 + `idempotent_replay=true` |
| S3 | active 已终态、`force=true` | 202，新 `review_id`，`generation+1`，旧记录 `superseded_by` 指向新记录 |
| S4 | 无 active、`force=true` | 202，按历史最大 `generation+1` |
| S5 | 同 key 并发 | 按 key 串行化；未 force 的后到者 200；并发 force 由第一个建新代次，后到者 409（S7）；不产生两份 active |
| S6 | 同 key、请求体不同 | 422 `IDEMPOTENCY_KEY_CONFLICT` |
| S7 | active 仍在运行、`force=true` | 409 `REVIEW_IN_PROGRESS`（状态冲突） |

配套规则：active 唯一性由部分唯一索引兜底、`force` 只取代终态记录、`superseded_by` 仅用于 `review_jobs` 代次链、`review_decisions`/`human_review_events` 只追加不依赖该指针、`409 DUPLICATE` 永久废弃。

### 2.2 清理记录

| # | 位置 | 原描述 | 处置 | 新口径 |
|---|---|---|---|---|

| 2 | `docs/02` §3 第 2 条 | "冲突返回已有报告或 409" | **废弃** | 改为串行化 + 200/202；运行中 `force` 返回 409 `REVIEW_IN_PROGRESS` |

另有文档索引、版本头、文档引用路径、错误码子集、CI 工作流与脚本索引等防漂移检查。

### 3.2 运行方式与 CI

```bash
python scripts/check_contracts.py          # 唯一 CI 入口；退出码 0/1
python scripts/check_contracts.py --list   # 5 个模块
python scripts/check_contracts.py --json   # 机器可读
```

- CI Job `contract` 必须执行该命令；任何错误阻断合并。
- 单测（`unit`）、迁移（`migration`）、Mock 全链路（`mock-e2e`）是独立 Job，见 `design/m0_acceptance.yaml`。
- 不依赖数据库、网络、真实模型；缺 `jsonschema` 时 Rubric Schema 检查明确失败，不静默跳过。

### 3.3 失败输出

每条错误必须包含检查项、文件（可带行号）、规则/字段、期望与实际：

```
[ERROR] docs | docs/19-API错误码与契约.md | REVIEW_IN_PROGRESS | 错误码表缺少 409 REVIEW_IN_PROGRESS
[ERROR] verdict-cases | design/verdict_cases.yaml | VC-014[R-SEV-GAP2].ai_verdict | 期望 'need_human'，实际 'blocked'
```

不允许只输出"检查失败"或堆栈；不允许用警告代替错误。

### 3.4 自检（变异测试）

"检查脚本能通过"不等于"检查脚本有效"。`tests/contract/test_contract_drift.py`（M0-09 ACC-M0-017）在临时副本中修改 `docs/17` 的枚举，断言 `check_contracts.py` 失败并指出文件与字段；`TJ_REPO_ROOT` 环境变量用于指向副本。检查器自身崩溃同样计为失败（见 `check_contracts.py` 的异常兜底）。

## 5. P0-4：Verdict 可执行真值表

### 5.1 文件与职责

| 文件 | 职责 |
|---|---|
| `docs/12` | 规则说明与 §8 禁止组合（人类可读事实源） |
| `design/verdict_cases.yaml` | 36 条用例：30 条规则、positive/negative/boundary/property/invalid 五类；每条标注规则 ID 与 docs/12 章节 |
| `scripts/verdict_reference.py` | 规范参考判定器（纯函数，无 I/O），按 docs/12 §2–§6 计算 |
| `scripts/check_verdict_cases.py` | 结构/覆盖检查 + 参考判定器一致性 + I1–I8 属性抽样（8×400=3200 组） |
| `app/pipeline/verdict.py`（M0 实现） | 生产唯一入口；必须与同一批用例结果一致 |

### 5.2 不变量

| ID | 不变量 | 测试方式 |
|---|---|---|
| I1 | `not_assessed`/`uncertain` 不计为 reject；有效票 <2 不得形成 accepted/rejected/blocker | 随机生成票型 + 有效票计数 |
| I2 | 无 E1/E2、ungrounded、core claim 非 supported/E1-E2 时不得产出 blocker | 随机 claims + 证据等级 |
| I3 | 模型自报结论（`model_claimed_verdict`）不改变 `ai_verdict` | 注入对照 |
| I4 | `human_status` 等人工字段不参与 `ai_verdict` | 注入对照 |
| I5 | issue 证据只由自身 claims 决定，不借用其他 issue | 单 issue vs 多 issue 对照 |
| I6 | 判定只依赖票/证据/席位；版本字段不改变结论 | 注入版本字段 |
| I7 | 同一输入重复计算、票序重排结果一致 | 重复执行 + 洗牌 |
| I8 | 阈值边界、严重级相邻/跨级、证据缺失均有确定结果，且不触发禁止组合 | 随机抽样 + 输出枚举校验 |

> I3/I4 验证的是判定**函数**不读取模型/人工字段；API 层的字段丢弃与权限分离另由 ACC-M0-013/014/015 覆盖。I6 验证判定不因版本字段改变结果；"同一轮评审使用创建时冻结版本"由 `docs/22` 与阶段 Checkpoint 保证，不在纯函数范围内。

### 5.3 测试方法

- **固定用例**：业务场景与已知边界（VC-001–VC-031）。
- **参数化**：票数、证据状态、严重级组合由用例矩阵覆盖。
- **属性测试**：固定种子随机生成，验证 I1–I8；发现反例输出输入快照。
- **变异测试**：`tests/contract/test_verdict_mutation.py` 现在就能证明"改错期望值必失败"；M0 起再对 `verdict.py` 注入"把 `<2` 改成 `<=2`""把 not_assessed 当 reject"等变异，确认测试失败。

### 5.4 与生产实现的关系

参考判定器**不是生产代码**，不得被 `app/` 引用。它的价值是给 `verdict.py` 一个可对照的规范实现和一套可执行断言：M0 验收时两者对同一批用例必须一致；不一致时按 `docs/12` 裁定，修实现或修用例并记录理由。参考判定器不模拟主审仲裁决策，只计算 `arbitration_required` 触发位；仲裁语义（补充/驳回）由 M4 的固定用例覆盖。

## 7. 残余风险与不做什么

| 风险 | 说明 | 缓解 |
|---|---|---|
| 检查脚本自身漂移 | 脚本与文档同时改时可能一起改错 | 变异测试（ACC-M0-017）+ 脚本变更需跑全量 |
| 用例与 `verdict.py` 脱节 | 实现后可能只跑少量用例 | ACC-M0-011 全量对照 + 变更流程要求同步 |
| 参考判定器被误用 | 被当成生产实现 | 文件头声明 + 代码评审；`app/` 不得 import |
| 决策索引覆盖不全 | 只索引跨模块契约与门禁相关决策 | 文件头声明覆盖策略，不宣称全量镜像 |
| `docs/08` D115–D119 重复登记 | 同一决策两个编号 | 保留为历史别名，不新增引用；后续版本清理 |
| Python Enum/DDL 未实现 | 文档层检查不能替代实现层 | ACC-M0-004/005 明确列为 M0 门禁 |
| Rubric 仍为 draft | 生产不可加载 | 上线前 `kb_reviewer` 审核并发布 |

**本轮不做**：不实现应用代码、不建数据库、不接真实模型、不导入知识库、不做性能压测、不部署。这些按 `docs/08` §5.1 的阶段推进。

## 8. 本轮验收标准

1. `python scripts/check_contracts.py` 在干净仓库退出码 0；改动任一枚举、Schema、Rubric 版本、决策 ID 或用例后必须失败并定位。

4. 规则、示例与 API 描述中不再保留旧语义（§2.2 清理记录中的原文引用除外）；幂等公式在 01/02/03 一致。

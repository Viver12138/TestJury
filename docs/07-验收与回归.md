# 07 · 验收与回归

> 版本：v1.1 · 2026-11-10（冻结修订）

## 1. 问题背景

黄金集不存在，短期也无法一次性凑齐可信真值。因此验收分两阶段：**冷启动种子集**（人工标注，量小但可信）+ **线上反向积累**（复核回写，量大但滞后）。

## 2. 冷启动种子集

### 2.1 规模与构成

- **30 份用例**只用于冷启动流程验证与最小示例集，**不足以证明系统达到生产质量门槛**；正式验收前需扩充（见 §2.4）。
- 从现有各模块历史用例中挑选。
- 覆盖分布建议：
  - 含真实 `blocker` 的 ≥ 10 份（否则召回率没法算）
  - 含 `major` 的 ≥ 10 份
  - 质量良好、应判"有条件通过"的 ≥ 5 份（测误报）
  - 纯文本用例 ≥ 3 份（测预处理链路）
  - 至少 1 份所属模块不在知识库中（测降级路径）
  - 至少 2 份不提供 `test_scope`、1 份不提供 `automation_context`（测结论强度限制）

### 2.2 标注规范

每份用例标注两部分：

1. **结论真值**：`blocked` / `conditional`（人工最终判定）
2. **问题真值清单**：每条含 `step_index`、`dimension`、`severity`、`category`、简短描述

标注方式：
- 由 **2 名测试专家独立标注**，分歧项由第三人裁决；
- 标注时**不看模型输出**（盲标），否则等于抄答案；
- 预计总耗时 2–3 小时/人。

### 2.3 检索黄金集（Retrieval Golden Dataset）

评审黄金集只能回答"最终结论对不对"，无法区分"检索没找到"和"模型判断错"。因此单独建检索集，首轮规模 **≥ 100 条查询**：

| 字段 | 说明 |
|---|---|
| `query` | 查询文本（来自标题 / 前置 / 步骤 / 预期 / 测试数据） |
| `query_source` | `title` / `precondition` / `action` / `expected` / `test_data` |
| `module` / `function_point` | 检索过滤范围 |
| `relevant_ids` | 正确知识 ID（带相关等级：2=直接依据，1=辅助） |
| `hard_negative_ids` | 不相关但容易混淆的知识 ID |
| `annotated_by` / `version` | 标注人与版本 |

标注要求：

- 查询从**真实用例的预期结果与前置条件**里出，不用知识库原文反查（否则等于抄答案）；
- 每条查询至少 1 个相关项、至少 1 个 hard negative（相似功能点、相似规则、已修复缺陷）；
- 与评审黄金集分开维护，避免"检索对了所以结论对了"的循环论证。

### 2.4 数据集划分与标注一致性

**四套集合，用途不能混：**

| 集合 | 用途 | 是否可反复使用 |
|---|---|---|
| 开发集（dev） | 调 prompt、检索、规则 | 可 |
| 验证集（validation） | 比较方案、调阈值 | 可 |
| 冻结测试集（frozen） | 正式验收 | **不可**在调参中反复使用 |
| 回归集（regression） | 检测版本退化 | 每次回归跑 |

**标注一致性**：不能只保留融合后的一个标签。

每次标注保留：

- 每位标注人的原始标签、标注时间、标注标准版本；
- 争议维度与分歧内容；
- 标注一致率（逐条一致率 + 总体一致率，建议用 Cohen's κ 或 Krippendorff's α）；
- 分歧处理结果与最终仲裁标签。

初始目标：总体一致率 ≥ 0.75（κ ≥ 0.6）。低于目标时先修标注口径，不要拿去当模型指标。

### 2.5 评测场景覆盖

标注集至少覆盖以下类型，否则指标会掩盖边界问题：

- 明确存在 blocker 的用例；
- 只有 major / suggestion 的用例；
- 实际没有问题的正常用例；
- 文字表达不清但业务逻辑正确的用例；
- 业务规则证据充分（E1/E2）的用例；
- 知识库缺失证据的用例；
- 知识库存在同级规则冲突的用例；
- 历史缺陷与当前版本不一致的用例；
- 单条用例无法判断整体覆盖的用例；
- 多模型意见分歧较大的用例；
- 应判 `need_human`（证据不足/无法判断）的用例。

## 3. 质量指标

### 3.1 评审指标

| 指标 | 定义 | 目标 |
|---|---|---|
| **Blocker Recall（严格）** | 真实 blocker 被报告标为 `blocker` 的比例 | ≥ 70% |
| **Blocker Detection Recall（辅助）** | 真实 blocker 被报告标为 blocker 或 major 的比例；不得与 Strict 混用 | 观察值 |
| **High-risk Recall** | 人工确认的 blocker + major 中，被报告标为 blocker 或 major 的比例 | ≥ 80% |
| **Blocker Precision** | 报告标为 `blocker` 的问题中，人工确认成立的比例 | ≥ 75% |
| **False Discovery Rate（FDR）** | 报告采用的问题中，人工判 `rejected` 的比例（FP/(TP+FP)） | ≤ 25% |
| **False Negative Rate** | 人工确认的问题中，报告完全漏检的比例 | ≤ 20% |
| **Severity Accuracy** | accepted 问题中，严重级与人工标注一致的比例 | ≥ 75% |
| **仲裁准确率** | 仲裁对候选问题的 adopted/rejected 与人工复核一致的比例（排除 need_human） | ≥ 75% |
| **结论一致率** | 终审 `ai_verdict` 与人工最终结论一致的比例，**排除 `need_human` 样本**（单独统计） | ≥ 75% |
| **主审-人工一致率** | 逐条 issue，终审 `status=adopted/rejected` 与人工复核一致的比例（排除 need_human） | ≥ 75% |
| **三方一致率** | 三份盲评的 `ai_verdict` 完全相同的比例 | 观察指标，不作门槛 |
| **`need_human` 转人工率** | 系统判 `need_human`（或含 disputed/severity_disputed）的样本占比 | 观察值，按批次统计 |
| **`need_human` 识别准确性** | 人工判定"证据不足/应转人工"的样本中，系统确实转人工的比例 | ≥ 80% |
| **知识库依据率** | 终审问题中 `kb_grounded=true` 的比例 | 观测值，不设目标 |
| **预处理成功率** | `raw_text` 用例成功结构化比例 | ≥ 90% |

关于**三方一致率**（诊断指标，不是质量门槛）：
- **> 85%**：说明三个视角没有产生有效分工，评审团退化成三个冗余副本 —— 应检查 prompt 是否过于相似、陪审是否只是复述主审口径。
- **< 40%**：说明评审标准不统一或模型能力差异过大，结论不可靠 —— 应先修 rubric，不要直接调模型。
- 该指标受用例难度与模型组合影响大，**不设硬性区间**；变化超过 10 个百分点时人工看差异，而不是直接阻断上线。

### 3.2 检索与重排指标

| 指标 | 评估目标 | 首轮目标 |
|---|---|---|
| **Recall@5** | 正确证据是否出现在前 5 条 | ≥ 85% |
| **Recall@10** | 正确证据是否出现在前 10 条 | ≥ 90% |
| **MRR@10** | 第一个正确证据的排名 | 记录基线，逐轮观察 |
| **nDCG@10** | 多个相关证据的排序质量 | ≥ 0.75 |
| **Evidence Precision** | 最终注入上下文中真正相关证据的比例 | ≥ 70% |
| **Citation Accuracy** | 评审结论引用的证据是否真实存在且匹配 | ≥ 90% |

> 目标值为初始设定，需在第一轮评测后按真实数据校准；不要为了达标去改数据集。

**必须分段评测**，否则无法定位问题：

1. 初检（结构化过滤 + 关键词 / 向量，未融合）；
2. RRF 融合后；
3. Reranker 精排后；
4. 最终证据包（注入模型的那一份 Top K）。

### 3.3 分层质量定位

| 层级 | 主要问题 | 主要指标 |
|---|---|---|
| 检索层 | 正确知识有没有被找到 | Recall@K、MRR、nDCG |
| 重排层 | 正确知识有没有排到前面 | nDCG、Evidence Precision |
| 评审层 | 模型是否正确识别问题 | 召回率、误报率、漏报率 |
| 融合层 | 相同问题是否正确合并 | 重复率、错误合并率（人工抽检） |
| 仲裁层 | 最终结论是否合理 | 仲裁准确率、人工一致率 |
| 报告层 | 结论是否有可靠依据 | Citation Accuracy |

调优顺序固定为**自下而上**：检索层不达标时先修检索，不要用 prompt 掩盖召回缺失。

### 3.4 融合指标

融合不能只看"合并了多少"，要看合并得对不对。用 `data/golden/fusion/` 的三类样本：

| 样本 | 定义 | 期望 |
|---|---|---|
| `positive` | 确实同一根因的问题对 | 应合并 |
| `negative` | 文本相似但根因不同的问题对 | 不应合并 |
| `boundary` | 信息不足、需人工判断 | 保留或交人工 |

| 指标 | 定义 | 首轮目标 |
|---|---|---|
| **错误合并率（False Merge Rate）** | `negative` 被判为同一问题的比例 | ≤ 10% |
| **漏合并率（Miss Merge Rate）** | `positive` 未被合并的比例 | ≤ 20% |
| **边界保留率** | `boundary` 未被强行合并的比例 | ≥ 90% |
| **线上错误合并抽检率** | 人工抽检线上合并对，判为错误的比例 | ≤ 5% |

> v1 优先控制错误合并：错误合并会污染统计与根因分析，比"少合并几条"更难补救。

### 3.5 性能指标口径

性能指标不能混在一起；每条都要说明起止点与统计对象：

| 指标 | 起点 | 终点 | 说明 |
|---|---|---|---|
| 排队时间 | 任务入队 | Worker 领取 | 受并发与批量影响 |
| 模型调用耗时 | 请求发出 | 收到响应 | 按角色分别统计（含重试则单列） |
| 评审执行时间 | Worker 领取 | 任务终态 | 含检索、盲评、投票、仲裁 |
| 端到端耗时 | 用户提交 | 终态可用 | 含排队；是否含重试需注明 |
| 批量完成时间 | 批次提交 | 全部子任务终态 | 不是单条耗时的简单相加 |

- 每组分别统计 **P50 / P95 / P99**，并记录样本量与并发条件。
- **压测前不写死门槛**；当前"模型单次超时 120s"与"端到端 120s"不能同时作为目标，需先测量再定。
- 端到端目标必须注明是否包含排队与重试；不注明口径的数字不能作为发布门槛。

### 3.6 严重级与仲裁指标

| 指标 | 目的 | 口径 |
|---|---|---|
| **Severity Accuracy** | 严重级判断是否准确 | 与人工标注严重级完全一致的比例（仅 accepted 问题） |
| **Blocker Classification Accuracy** | blocker 判断是否准确 | blocker 的 precision / recall 分开报 |
| **Severity Overestimation Rate** | 高估比例 | 模型级别高于人工 ≥1 级的比例 |
| **Severity Underestimation Rate** | 低估比例 | 模型级别低于人工 ≥1 级的比例 |
| **Vote Agreement Rate** | 投票一致程度 | 同一候选上 validity 一致的模型对比例 |
| **Arbitration Change Rate** | 仲裁改变投票结果的比例 | 仲裁终值与多数 validity 不一致的比例 |
| **Arbitration Correction Rate** | 仲裁是否纠正错误 | 仲裁改变且与人工一致的比例 |
| **Human Override Rate** | 人工推翻仲裁的比例 | 人工最终结论与 `ai_verdict` 不一致的比例 |
| **Anchoring Flip Rate** | 投票受锚定影响 | 同一模型初审与投票 validity 翻转的比例 |

### 3.7 模型组合对照

单模型 vs 两模型 vs 三模型、同模型重复调用的对照实验见 `docs/15-模型组合对照实验.md`。验收报告至少回答：

- 三模型相对单模型的 blocker 召回提升是否显著；
- 误报是否下降；
- 严重级准确性是否改善；
- 人工复核率是否下降；
- 单条成本与延迟增加多少；
- 收益来自模型差异还是重复采样。

未完成对照实验前，不得宣称"评审团优于单模型"。

### 3.8 端到端发布门禁

完整指标、数据集要求、样本量与豁免规则见 `docs/21-端到端验收标准.md`。本文的回归指标是发布门禁的一部分，不是全部；发布前必须同时通过真值表、失败恢复、权限/注入、成本与报告可读性检查。

## 4. 指标计算口径

```
blocker_recall    = |{真实 blocker} ∩ {报告中标为 blocker 且语义对齐}| / |{真实 blocker}|
blocker_detection = |{真实 blocker} ∩ {报告中标为 blocker 或 major 且语义对齐}| / |{真实 blocker}|  # 辅助，不替代 strict
high_risk_recall  = |{人工确认 blocker 或 major} ∩ {报告中标为 blocker 或 major 且语义对齐}| / |{人工确认 blocker 或 major}|
blocker_precision = |{报告 blocker} ∩ {人工确认成立}| / |{报告中标为 blocker}|
fdr               = |{报告采用的问题} ∩ {人工判 rejected}| / |{报告采用的问题}|
fnr               = |{人工确认问题} ∩ {报告完全漏检}| / |{人工确认问题}|
```

对齐方式：人工在评测脚本中逐条确认报告问题与真值问题的对应关系（`run_eval.py` 生成待对齐表格，人工勾选）。

> FDR = FP/(TP+FP)，衡量报告误报比例；FPR = FP/(FP+TN) 需要完整负样本标注，v1 不计算标准 FPR，避免用 FDR 冒充 FPR。
>
> 指标名称、分母、统计单位必须与 `docs/21` 完全一致；07 与 21 不允许出现同名不同义的门槛。

**不要**用自动字符串匹配算指标 —— 模型措辞千变万化，自动匹配的结果没有说服力。

## 5. 回归流程

### 5.1 触发条件

任一变更都必须触发全量回归：

- prompt 文件修改（含共用约束与投票轮）
- rubric 修改
- 模型版本或 `models.yaml` 配置变更（含厂商默默升级）
- 融合阈值修改（`FUSION_SIM_THRESHOLD` 等）
- 检索参数修改（Top-K、RRF `k`、rerank 阈值、查询上限）
- embedding profile 变更或知识库切片策略调整
- 知识库版本更新（至少跑一遍，确认结论无异常漂移）
- `report_schema_version` 变更
- Prompt 注册表或模型注册表变更（阶段/Schema/模型 ID）

### 5.2 门禁

```
运行 run_retrieval_eval.py（检索黄金集）
  ├─ 检索指标全部达标 → 进入融合回归
  └─ Recall@10 或 nDCG@10 下降 > 3 个百分点 → 阻断，先修检索，不调 prompt

运行 run_fusion_eval.py（融合正/负/边界样本）
  ├─ 错误合并率 ≤ 10% → 进入评审回归
  └─ 错误合并率上升 > 3 个百分点 → 阻断，先修融合/阈值

运行 run_eval.py（评审黄金集）
  ├─ 指标全部达标 → 允许上线，记录本次指标与全部版本号
  ├─ 任一指标较上次下降 > 5 个百分点 → 阻断上线，需人工评审差异
  └─ 新增 blocker 误报集中在某模块/某维度 → 定向修正 prompt 或知识库，再回归

运行 failure/integration 测试（不可跳过）
  ├─ 按 docs/26 的 Mock/故障注入/迁移测试执行
  ├─ Schema/枚举/引用校验失败不进入融合
  ├─ `docs/12` 真值表用例全部通过（含 2/3、1/3、证据冲突）
  ├─ 幂等键对 NULL 字段、force、重复请求的行为
  ├─ worker 被杀后从阶段 Checkpoint 恢复，不重复出终稿
  ├─ 投影重建与一致性校验（report_json ↔ issues）
  ├─ 候选向量与 claim 证据映射正确
  ├─ 成立性/严重级分开落库，严重级分歧转人工
  └─ webhook 签名、重放、SSRF、失败重试
```

检索不达标时禁止用 prompt 修补——那只会让模型在错误证据上更自信；融合错误合并超标时禁止靠调 prompt 掩盖，先修判重逻辑。

### 5.3 回归记录

每次回归产出一份 `data/golden/runs/<日期>-<摘要>.json`，包含：

- 全部版本号（kb / rubric / prompt / retrieval_config / embedding_profile）
- 检索指标（分段：初检 / RRF / rerank / 证据包）
- 评审指标
- 逐份用例的终审结论 vs 真值
- 与上一次回归的差异清单

## 6. 线上反向积累

### 6.1 数据来源

人工复核通过 `POST /v1/reviews/{review_id}/feedback` 回写（issue 级，不等于报告审批；报告级决定见 `POST /decisions`）：

- `adopted` → 正样本（该问题确实存在）
- `rejected` → 负样本（误报）
- `missed` → 漏检样本（用于算召回）

### 6.2 积累节奏

- 每周导出一次复核数据；
- 累计 **≥ 100 份已复核用例**后，用其替换或扩充种子集做正式评测；
- 每季度用新数据集重算核心指标，形成趋势曲线。

### 6.3 防止"自我确认"偏差

反馈数据来自人工，不是模型自己 —— 但如果复核人员只是"扫一眼就点采纳"，数据会失真。要求：

- `rejected` 必须填写 `note` 说明理由（接口层校验）；
- 每周抽 10% 的 `adopted` 由第二人复核，不一致率 > 15% 时重新培训复核口径。

## 7. 上线前检查清单

- [ ] 30 份种子集标注完成，双人标注 + 第三人裁决
- [ ] 数据集已划分 dev / validation / frozen / regression；frozen 未参与调参
- [ ] 检索黄金集 ≥ 100 条查询标注完成，含 hard negative
- [ ] 融合正/负/边界样本集完成，`run_fusion_eval.py` 跑通
- [ ] `run_retrieval_eval.py` 跑通，检索层指标达标
- [ ] `run_eval.py` 跑通，评审指标达标
- [ ] `models.yaml` 中每个模型 ID 实测可用，超时/限流/价格配置确认
- [ ] embedding profile 已落库且为 1024 维，`kb_chunks` 与 `issue_embeddings` profile 一致

## 9. 已知风险与观察项

| 风险 | 观察方式 |
|---|---|
| 三个模型趋同（一致率 > 85%） | 每次回归记录三方一致率，超阈值即检查 prompt |
| 主审过度驳回陪审（专断） | 统计驳回率，> 30% 时人工抽检驳回理由质量 |
| 主审过度采纳（老好人） | 统计驳回率，< 5% 时检查是否只是机械汇总 |
| 知识库长期不生长 | 每月看 `kb_gaps` open 数量与 accepted 转化率 |
| 模型厂商静默升级 | 记录返回的模型版本字段，与配置版本不符时告警 |
| 复核数据质量下滑 | 每周 10% 抽检，不一致率 > 15% 告警 |
| 检索召回不足被误判为模型能力问题 | 每次回归先看检索层指标，再看评审指标；检索未达标不调 prompt |
| 中文关键词检索效果差 | 对比 pg_trgm / zhparser / 精确匹配，用检索集决定 |
| 检索配置漂移 | `retrieval_config_version` 变化即触发检索回归 |
| `test_scope` 维护成本高 | 先只覆盖 3–5 个高频功能点，其余标 `scope_missing` |

# 07 · 验收与回归

## 1. 问题背景

黄金集不存在，短期也无法一次性凑齐可信真值。因此验收分两阶段：**冷启动种子集**（人工标注，量小但可信）+ **线上反向积累**（复核回写，量大但滞后）。

## 2. 冷启动种子集

### 2.1 规模与构成

- **30 份用例**，从现有各模块历史用例中挑选。
- 覆盖分布建议：
  - 含真实 `blocker` 的 ≥ 10 份（否则召回率没法算）
  - 含 `major` 的 ≥ 10 份
  - 质量良好、应判"有条件通过"的 ≥ 5 份（测误报）
  - 纯文本用例 ≥ 3 份（测预处理链路）
  - 至少 1 份所属模块不在知识库中（测降级路径）

### 2.2 标注规范

每份用例标注两部分：

1. **结论真值**：`blocked` / `conditional`（人工最终判定）
2. **问题真值清单**：每条含 `step_index`、`dimension`、`severity`、`category`、简短描述

标注方式：
- 由 **2 名测试专家独立标注**，分歧项由第三人裁决；
- 标注时**不看模型输出**（盲标），否则等于抄答案；
- 预计总耗时 2–3 小时/人。

## 3. 质量指标

| 指标 | 定义 | 目标 |
|---|---|---|
| **阻断召回率** | 人工标注的真实 blocker 中，被终审报告以 blocker/major 抓到的比例 | ≥ 80% |
| **阻断误报率** | 终审报告中标为 blocker 的问题里，人工复核判 `rejected` 的比例 | ≤ 20% |
| **结论一致率** | 终审 verdict 与人工最终结论一致的比例（`need_human` 计为一致但不计分） | ≥ 75% |
| **主审-人工一致率** | 逐条 issue，终审 `status=adopted/rejected` 与人工复核一致的比例（排除 need_human） | ≥ 75% |
| **三方一致率** | 三份盲评的 verdict 完全相同的比例 | 40%–85% 区间 |
| **知识库依据率** | 终审问题中 `kb_grounded=true` 的比例 | 观测值，不设目标 |
| **预处理成功率** | `raw_text` 用例成功结构化比例 | ≥ 90% |
| **P95 端到端耗时** | 单份用例从入队到 `done` | ≤ 90s（50 份批次约 20 分钟） |

关于**三方一致率**：
- **> 85%**：说明三个视角没有产生有效分工，评审团退化成三个冗余副本 —— 应检查 prompt 是否过于相似、陪审是否只是复述主审口径。
- **< 40%**：说明评审标准不统一或模型能力差异过大，结论不可靠 —— 应先修 rubric，不要直接调模型。

## 4. 指标计算口径

```
recall_blocker   = |{真实 blocker} ∩ {报告中 severity∈{blocker,major} 且与真实问题语义对齐}|
                   / |{真实 blocker}|
```

对齐方式：人工在评测脚本中逐条确认报告问题与真值问题的对应关系（`run_eval.py` 生成待对齐表格，人工勾选）。

```
fp_blocker       = 报告 adopted blocker 中人工判 rejected 的数量 / 报告 adopted blocker 总数
```

**不要**用自动字符串匹配算指标 —— 模型措辞千变万化，自动匹配的结果没有说服力。

## 5. 回归流程

### 5.1 触发条件

任一变更都必须触发全量回归：

- prompt 文件修改
- rubric 修改
- 模型版本变更（含厂商默默升级）
- 融合阈值修改（`FUSION_SIM_THRESHOLD` 等）
- 知识库版本更新（至少跑一遍，确认结论无异常漂移）

### 5.2 门禁

```
运行 run_eval.py
  ├─ 指标全部达标 → 允许上线，记录本次指标与五个版本号
  ├─ 任一指标较上次下降 > 5 个百分点 → 阻断上线，需人工评审差异
  └─ 新增 blocker 误报集中在某模块/某维度 → 定向修正 prompt 或知识库，再回归
```

### 5.3 回归记录

每次回归产出一份 `data/golden/runs/<日期>-<摘要>.json`，包含：

- 五个版本号
- 全部指标
- 逐份用例的终审结论 vs 真值
- 与上一次回归的差异清单

## 6. 线上反向积累

### 6.1 数据来源

人工复核通过 `POST /v1/reviews/{review_id}/feedback` 回写：

- `adopted` → 正样本（该问题确实存在）
- `rejected` → 负样本（误报）
- `missed` → 漏检样本（用于算召回）

### 6.2 积累节奏

- 每周导出一次复核数据；
- 累计 **≥ 100 份已复核用例**后，用其替换或扩充种子集做正式评测；
- 每季度用新数据集重算四个核心指标，形成趋势曲线。

### 6.3 防止"自我确认"偏差

反馈数据来自人工，不是模型自己 —— 但如果复核人员只是"扫一眼就点采纳"，数据会失真。要求：

- `rejected` 必须填写 `note` 说明理由（接口层校验）；
- 每周抽 10% 的 `adopted` 由第二人复核，不一致率 > 15% 时重新培训复核口径。

## 7. 上线前检查清单

- [ ] 30 份种子集标注完成，双人标注 + 第三人裁决
- [ ] `run_eval.py` 跑通，四个核心指标达标
- [ ] 五模型（预处理 + 三评审 + embedding）的 base_url / key / 版本号全部确认
- [ ] 知识库 3–5 个模块内容完成，规则带 RULE-ID 与出处
- [ ] 降级路径实测：陪审超时、主审失败、模块未命中、纯文本不可解析
- [ ] 报告 Markdown 在真实评审会上能被读懂（找 1 名未参与设计的同事试读）
- [ ] `model_runs` 原文存档可查、可导出
- [ ] API Key 分发与调用日志合规确认

## 8. 已知风险与观察项

| 风险 | 观察方式 |
|---|---|
| 三个模型趋同（一致率 > 85%） | 每次回归记录三方一致率，超阈值即检查 prompt |
| 主审过度驳回陪审（专断） | 统计驳回率，> 30% 时人工抽检驳回理由质量 |
| 主审过度采纳（老好人） | 统计驳回率，< 5% 时检查是否只是机械汇总 |
| 知识库长期不生长 | 每月看 `kb_gaps` open 数量与 accepted 转化率 |
| 模型厂商静默升级 | 记录返回的模型版本字段，与配置版本不符时告警 |
| 复核数据质量下滑 | 每周 10% 抽检，不一致率 > 15% 告警 |

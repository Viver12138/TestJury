# 27 · 生产部署与运维设计

> 版本：v1.3 · 2026-11-10（M0 前契约收口）
> 目的：给出 v1 可复现的部署拓扑、迁移、备份、健康检查与扩容规则；不引入 Kubernetes。
> 关联：06、10、13、26。

---

## 1. 拓扑

```
调用方 → Nginx/网关 → FastAPI（可多实例）
                         │
                         ├─ PostgreSQL（pgvector）
                         ├─ 模型供应商（Qwen/DeepSeek/Kimi）
                         └─ Workers（独立进程，可多实例）
                              ├─ retrieval
                              ├─ review
                              ├─ fusion
                              ├─ voting
                              └─ verdict/render
```

- API 与 Worker **独立进程**：API 不执行长任务；Worker 可按队列深度水平扩展。
- v1 用 Docker Compose：`api`、`worker`、`postgres`（pgvector）、可选 `nginx`。
- **附件卷**：`ATTACHMENT_DIR` 必须是所有 Worker/API 都能访问的共享卷（单机 Compose 挂载同一目录）；多机部署前必须换成对象存储，否则附件读取不一致。
- 不使用 Kubernetes；多实例通过共享 PostgreSQL 队列协调。

## 2. 配置

| 项 | 说明 |
|---|---|
| `WORKER_CONCURRENCY` | 每 Worker 进程并发任务数，默认 4 |
| `WORKER_REPLICAS` | Worker 容器数，压测后定 |
| 连接池 | API 与 Worker 分开；每进程池上限 ≤ DB max_connections / 进程数 |
| 超时 | 单次 120s、阶段级、任务 20 分钟、租约 5 分钟 |
| 日志 | stdout JSON，采集到集中日志；带 `review_id/trace_id` |

## 3. 数据库迁移

- Alembic 管理；迁移版本与应用版本关联（`schema_version` 表）。
- 上线顺序：备份 → 迁移（单实例持锁）→ 启动新 API/Worker → 健康检查 → 旧实例下线。
- 大表索引使用 `CREATE INDEX CONCURRENTLY`，避免长锁。
- 迁移失败：停止发布，按备份/回滚脚本恢复；不允许应用连到半迁移库。
- 每次发布前在空库与上一版本库各跑一次迁移测试（见 `docs/26`）。

## 4. 备份与恢复

- PostgreSQL 每日全量 + WAL 归档；保留 7–30 天（按合规）。
- 恢复演练每季度一次；恢复后校验 `report_json ↔ issues`、KB active 唯一。
- KB 事实源在 Git，可重建索引；数据库备份不替代 Git。

## 5. 健康检查

| 端点 | 检查 |
|---|---|
| `/livez` | 仅进程存活；不检查依赖 |
| `/readyz` | DB 连通、迁移版本匹配、队列可读；不具备则 503 |
| `/healthz` | 兼容别名，语义等同 `/readyz` |
| `/metrics` | 队列深度、租约过期、阶段失败率、429 率、成本 |

就绪失败语义：

| 情况 | `/livez` | `/readyz` | 行为 |
|---|---|---|---|
| DB 不可用 | 200 | 503 | 不接收新任务；只读接口可降级 |
| 迁移版本不匹配 | 200 | 503 | 阻止接收新任务 |
| 队列不可读 | 200 | 503 | 不接收新任务 |
| 供应商不可用 | 200 | 200 | 可接收，评审降级/失败并告警 |

`/readyz` 失败体使用统一错误结构，`code=NOT_READY`，`details.reason` 说明具体依赖。

## 6. 扩容与故障

- 队列积压 → 增加 Worker 副本；先确认供应商并发配额。
- 供应商 429 升高 → 降低该 provider 并发，不影响其他 provider。
- DB 连接耗尽 → 降 Worker 并发/副本，检查连接池泄漏。
- Worker 崩溃 → 租约过期自动接管；fencing token 防止旧 Worker 写入。
- API 多实例无需粘性会话；状态全在 DB。

### 6.1 容量与恢复目标

| 项 | 需明确 |
|---|---|
| 全局任务并发 | `worker 副本 × 每进程并发`，与供应商额度、DB 连接池共同计算；不能只看 `WORKER_CONCURRENCY=4` |
| 数据库容量 | 初始容量、增长预估、归档策略；`model_runs` 增长最快，按时间分区/归档 |
| 连接池 | API/Worker 分池，总连接 ≤ DB max_connections |
| 单任务内存/磁盘 | 上限与超限行为 |
| RPO | 可接受数据丢失时间（由备份/WAL 决定） |
| RTO | 可接受恢复时间（演练验证） |

建议初始目标：RPO ≤ 15 分钟、RTO ≤ 2 小时（单机 Compose + WAL 归档）；压测/演练后校准。

RPO/RTO 不能只写在文档里：每季度做一次恢复演练，记录实际 RPO/RTO、失败点与改进项。

## 7. 发布与回滚

- 应用镜像按 digest 固定；配置版本化。
- 回滚应用：切回上一镜像；数据库迁移只在兼容前提下回滚。
- KB 回滚：切 active 指针（`docs/11` §8），不删版本。
- 每次发布记录：镜像、迁移版本、配置版本、KB/Rubric 版本、验收结果。

## 1. 定位与边界

补充 16 的结论是：**设计结构已足够，下一阶段不补文档，而补决策、数据、实验和验收证据**。本文件不是新的架构设计文档，而是执行台账：

- 记录每个 open 事项的负责人（待指定）、阻塞阶段、下一步动作与所需证据；
- 记录每个验证项（V-01–V-12）的当前状态，防止"设计完成"被说成"已验证"；
- 给出可复用的证据模板，保证证据可审计、可复核。

新增架构模块不在本文件范围；任何扩大产品职责的变更仍必须先改 `docs/00`。

## 2. 四状态模型

每个决策/验证项必须明确处于哪一个状态，不得混用：

| 状态 | 含义 | 判定证据 |
|---|---|---|
| `designed` | 设计已明确，可作为实现依据 | 文档 + 决策编号 |
| `implemented` | 代码/配置已落地 | 代码、迁移、配置提交 |
| `verified` | 自动化或技术验证通过 | 测试报告、检查器输出、演练记录 |
| `accepted` | 真实业务负责人或用户验收通过 | 签署的验收记录、用户测试报告、演练批准 |

映射到既有字段：

| 本台账状态 | 既有字段 |
|---|---|
| designed | `status=decided` |
| implemented | `implementation_status=implemented` |
| verified | `validation_status=passed` |
| accepted | `release_status=approved/released`，且必须有 `acceptance_evidence` |

规则：

- **脚本检查通过只等于 verified，不等于 accepted。**
- `accepted` 必须写证据 ID、验收人、时间；没有证据不得标 accepted。
- M0 通过只代表工程正确；评审质量、业务有效性、生产可用分别验收（`docs/08` §5.3）。

### 2.1 状态转换与证据失效（D194）

| 当前 | 目标 | 是否允许 | 条件 |
|---|---|---|---|
| designed | implemented | 允许 | 有实现证据（代码/迁移/配置） |
| implemented | verified | 允许 | 有验证证据，且证据对应当前版本 |
| verified | accepted | 允许 | 有权责任人验收，写验收依据/时间 |
| verified | implemented | 允许 | 验证失败或发现实现缺陷 |
| accepted | implemented | 有条件 | 重大变更或验收失效，必须重新实现/验证 |
| accepted | verified | 有条件 | 只需重新验证，实现无需重做 |
| 任意 | 更早状态 | 不直接覆盖 | 必须写变更原因与历史记录 |

**状态历史**：每次变化追加一条记录，不覆盖原记录：`item_id`、`from`、`to`、`at`、`actor`、`reason`、`evidence`、`versions`、`invalidates_downstream`。旧的验证证据保留，新的验证产生新记录，便于回溯"当时为什么判通过"。

**持久化事实源（R5）**：M0 以 Git 台账为准——`evidence/<item_id>/history.jsonl` 追加状态历史，`evidence/<item_id>/manifest.yaml` 记录证据版本/哈希/有效性；状态历史只追加，禁止改写。后续系统运行时管理时，必须映射到独立的事件表（不复用评审任务的 `review_stage_attempts`），并保持本格式可作为导入源。

**证据失效规则**：

- 模型版本、Prompt、Rubric、知识库、Adapter 或评测集版本变化 → 相关 `verified` 证据自动失效，回到 `implemented` 并重验。
- 验收人权限失效、证据文件缺失/被撤销、下游验证失败 → `accepted` 撤销，登记原因。
- 失效不是删除：状态历史与旧证据保留，只标记 `valid=false`/`invalidated_by`。
- 任何状态变化必须由 `scripts/check_execution_gate.py` 在阶段门禁校验，不靠人工口头确认。

## 4. 本轮补齐的可判定规则

### 4.1 历史缺陷升级为正式规则（Q-08 / D181）

历史缺陷不能直接当规则；只有同时满足以下条件才允许升级：

1. 可定位原始缺陷记录或可信复盘资料；
2. 确认缺陷发生时的产品版本与业务条件；
3. 确认其反映稳定业务约束，而非一次性实现错误；
4. 模块负责人确认该约束当前仍有效；
5. 明确适用范围、生效版本与失效条件；
6. `kb_reviewer` 审核通过；
7. 生成新的 RULE-ID 或明确规则版本，不覆盖历史缺陷记录。

三类知识必须分开：

| 类型 | 用途 | 可作当前判定依据 |
|---|---|---|
| 历史缺陷记录 `historical_bug` | 风险线索与背景 | 否 |
| 待确认经验 | 测试启发 | 否，需标待确认 |
| 已审核正式规则 | 当前有效业务约束 | 是，且需匹配版本/条件 |

字段见 `docs/17` §4.1；升级记录必须写 `derived_from`、`bug_version`、`fixed_version`、`current_validity_confirmed`、`confirmed_by/at`。

### 4.2 A–E 批准口径（D182）

`docs/15` §6.1 是唯一批准规则；`§2.1` 只列冻结项、`§6` 只给判定原则，不得各写一套阈值。

### 4.3 知识库帮助度（D183）

`docs/29` §10 区分**主观帮助度**与**客观质量增量**；帮助度分母是"注入了知识且进入人工复核的任务"，由复核人一人一评，不作为知识库有效性的唯一证据。

### 4.4 报告用户验收（D184）

`docs/07` §8.7 使用三层经验用户 + 人工评审基线对照，任务 T1–T6 与指标固定，不再只做视觉检查。

### 4.5 成本双层预算（D185）

`docs/20` §6.4 区分"技术保护上限"与"业务批准预算"；前者由工程配置，后者由业务审批，不得互相替代。

### 4.6 Rubric 发布流程（D186）

`docs/04` §9 与 `rubric/README` 明确审核人、批准人、发布前回归、回滚与旧报告保留。

## 5. 证据模板

### 5.1 数据集冻结记录（V-02）

| 字段 | 说明 |
|---|---|
| `dataset_version` | 唯一版本号 |
| `case_count` / `blocker_count` | 样本量与真实 blocker 数 |
| `strata` | 模块/复杂度/风险级分布 |
| `annotation` | 标注人、双人一致性、裁决记录 |
| `split` | dev/validation/frozen/regression 边界 |
| `checksum` | 内容哈希 |
| `approved_by` / `approved_at` | 批准人/时间 |

### 5.2 模型准入记录（V-01/V-12）

`design/model_admission.yaml`：每个角色必须有真实 Model ID、技术验证、Adapter 测试、数据准入、允许数据等级、脱敏要求、DPA、结论；`verified` 与 `approved` 缺一不可进入生产。

### 5.3 实验协议（Q-14）

`design/experiment_protocol.yaml`：`status=signed` 前必须填全阈值、数据集版本、签署人；未签署不得启动正式实验。

### 5.4 演练记录（Q-18/V-11）

| 字段 | 说明 |
|---|---|
| `drill_id` / `drill_type` | disaster_recovery / compliance_deletion |
| `backup_timestamp` / `target_recovery_point` | 备份与目标恢复点 |
| `actual_rpo` / `actual_rto` | 实测值 |
| `deletion_scope` / `restored_deleted_data` | 删除范围与恢复后是否重现 |
| `consistency_check` | 报告/投影/知识库一致性 |
| `issues` / `approved_by` | 问题清单与验收人 |

### 5.5 用户验收记录（Q-16/V-08）

三层用户（资深/一般/模块不熟）、任务 T1–T6、人工评审基线对照、指标与问题清单；未通过项回到 Schema/Decision Trace/Prompt/Rubric。

### 5.6 错误来源分类与责任边界（D201）

AI 结论错误不能一概归因于模型，最小记录需区分来源：

| 错误来源 | 典型情况 | 处理方向 |
|---|---|---|
| 输入数据错误 | 缺字段、附件缺失、格式异常 | 修正输入或明确拒绝 |
| 业务知识错误 | 过期、冲突、版本不适用 | 修正知识并重新评审 |
| 检索错误 | 未召回、错误召回 | 调整检索与知识组织 |
| 模型判断错误 | 证据正确但结论错误 | 模型/Prompt/Rubric 复验 |
| 融合/仲裁错误 | 单模型正确、融合错误 | 检查融合与仲裁规则 |
| 服务端规则错误 | Verdict/业务规则实现错误 | 修复并回归 |
| 人工审批错误 | 裁定不符合正式规则 | 复核责任与权限流程 |

每类错误记录：初步定位人、最终确认人、是否重新评审、是否改知识库/评测集、是否重跑实验、是否通知用户。最小记录不要扩展成通用缺陷平台。

## 6. 执行顺序

| 阶段 | 对应里程碑 | 目标 | 出口（必须完成） |
|---|---|---|---|
| S1 业务决策与责任 | M0 前 | Q-07/Q-08/Q-09/Q-12/Q-13 形成结论和责任人；阶段映射收口 | 台账 owner 非空；无生产级前置依赖 |
| S2 真实评测条件 | M1–M2 | 模型验证、数据集冻结、A–E 协议签署、KB 单模块 | V-01、V-02、V-04；Q-14 协议 signed |
| S3 业务有效性 | M4–M6 | A–E、K0/K1、复核演练、用户验收 | V-05、V-06、V-07、V-08；V-03A |
| S4 生产准入 | production | 预算、压测、删除恢复、安全、Rubric 正式发布 | V-03B、V-09、V-10、V-11、V-12 |

> S2 不要求 Rubric 完成 production 发布；M0 只需要"可加载、可校验、draft 不得进生产"，正式发布属于 S4。阶段不可跳过；上一阶段没有证据，不进入下一阶段。任何"先上线再补证据"的决定必须由业务负责人书面批准并登记风险。

### 6.1 阶段映射与 Rubric 生命周期（D193）

| 阶段 | 验证项 | 必须完成 | 可以延后 |
|---|---|---|---|
| S1 | Q-07/08/09/12/13 | 决策与责任人 | 全部 V 项 |
| S2 | V-01、V-02、V-04 | 模型技术验证、数据集冻结、KB 单模块 | Rubric 正式发布（V-03B） |
| S3 | V-05/V-06/V-07/V-08 + V-03A | 业务有效性证据 | 生产发布、预算/压测 |
| S4 | V-03B、V-09–V-12 | 生产准入证据 | — |

**Rubric 生命周期拆分**：

| 阶段 | 要求 | 目的 |
|---|---|---|
| M0 | Schema、规则结构、加载校验可用；生产模式拒绝 draft | 系统能读取并检查 Rubric |
| M2/M6 | 用真实评测数据完成效果验证与回归 | 证明 Rubric 对评审质量有效 |
| Production | 正式审批、发布、冻结版本、回滚 | 生产使用可控、可追溯 |

M0 **不得**被 production 级发布要求阻塞；但 M0 的"能够加载"也**不等于** Rubric 已通过业务有效性验证。`execution_plan.yaml` 的 `stage_mapping`/`rubric_lifecycle` 与本节同源。

## 7. 检查分层与门禁

补充 17 要求区分"结构检查"与"执行门禁"：

| 层 | 命令 | 何时 | 检查内容 |
|---|---|---|---|
| 结构检查 | `scripts/check_execution_plan.py`（包含在 `check_contracts.py`） | 每次提交/CI | YAML 可解析、字段/状态合法、ID 引用、Q/V 覆盖、阶段映射与协议结构 |
| 执行门禁 | `scripts/check_execution_gate.py --stage S1/S2/S3/S4` | 阶段验收/发布前 | 每项**最低状态**（stage_gates）、owner/决策、证据 manifest 与哈希、状态历史、协议签署、S4 数据准入 |

- 结构检查通过**只说明台账自洽**；执行门禁通过才说明该阶段证据齐全。
- 执行门禁不放在默认 CI（会因 owner 未指定而失败），由 `.github/workflows/execution-gate.yml` 手动触发。
- 证据目录约定见 `evidence/README.md`：`evidence/<item_id>/<evidence_id>`。
- 字段非空不等于证据有效；脚本只验证存在性、版本与格式，证据是否支持业务验收仍需人工判断。

## 8. 结构检查范围（CI）

`scripts/check_execution_plan.py` 校验：

- `execution_plan.yaml` 覆盖全部 `open` 待决事项与 V-01–V-12；
- 状态/阶段/证据字段合法；`accepted` 必须有 `acceptance_evidence` 与验收人；
- `model_admission.yaml`、`experiment_protocol.yaml`、`kb_pilot.yaml`、`review_roster.yaml` 的结构与状态自洽（如协议 signed 必须有阈值与签署人）。

检查通过仍只代表台账自洽，不代表实验或业务验收已完成。

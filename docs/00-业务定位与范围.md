## 1. 文档目的

本文档定义 TestJury 的产品定位、目标用户、核心业务流程、评审对象、业务输入与输出边界、系统职责边界以及版本范围。

本文档是 TestJury 的**业务层顶层设计**，主要解决以下问题：

1. TestJury 是什么产品，核心解决什么问题？
2. 产品主要服务哪些用户，各类用户承担什么职责？
3. v1 明确评审什么，不评审什么？
4. AI 评审结果与人工审批之间是什么关系？
5. TestJury 与测试管理平台、测试执行平台及人工测试人员如何协作？
6. 后续新增需求应依据什么原则判断是否属于 TestJury 的职责？

本文档不替代架构设计、数据模型、API、评审标准或验收规范；上述文档应以本文档确定的业务边界为依据。文档关系见 §13，落地映射见 §17。

### 1.1 文档使用原则

- 本文档定义业务目标和业务边界，不规定具体技术实现。
- 业务规则与技术实现发生冲突时，应先确认业务规则是否需要调整。
- 任何扩大评审对象、自动化程度、审批权限或系统职责的变更，都必须经过明确的业务决策。
- 未在本文档或经批准的后续修订中定义的能力，不应默认纳入 v1。
- 本文档的决策编号为 `BIZ-001`–`BIZ-015`（§14）；下游设计文档引用业务边界时应引用这些编号。

### 1.2 版本命名

## 2. 产品定位

### 2.1 产品定义

TestJury 是一个面向软件测试活动的 **AI 测试用例质量评审系统**。

系统以测试用例及其关联的需求、业务规则、测试范围和自动化上下文为评审输入，通过多个专业化评审角色或评审策略，对测试用例的质量进行分析，识别缺陷、遗漏、歧义和潜在风险，并提供可追溯的证据、修改建议及结构化评审结论。

TestJury 的核心职责是：

> 帮助测试人员在测试用例进入执行阶段之前，发现用例设计中的质量问题，提高测试用例的完整性、准确性、可执行性和可维护性。

TestJury 负责提供评审意见和辅助决策依据，**不代替测试负责人进行最终审批，也不负责执行测试用例**。

### 2.2 要解决的核心问题

传统测试用例评审通常存在以下问题：

1. **评审质量依赖个人经验**：不同评审人员的经验和关注点存在差异，评审标准难以保持一致。
2. **评审覆盖不稳定**：评审人员可能遗漏边界条件、异常路径、状态变化或业务规则约束。
3. **评审成本较高**：人工逐条检查用例需要投入较多时间，尤其是在用例数量较大时。
4. **问题依据不够明确**：部分评审意见只有结论，缺少对应的需求依据、业务规则或用例内容证据。
5. **评审过程难以标准化**：不同团队、不同人员的评审尺度可能不一致，历史评审经验也不容易沉淀和复用。
6. **自动化可行性判断缺少统一标准**：部分用例在设计阶段没有充分考虑前置条件、数据准备、环境依赖和结果校验等自动化要求。

TestJury 通过结构化评审标准、知识依据、证据关联和人工复核机制，改善上述问题。

### 2.3 核心价值

| 服务对象 | 核心价值 |
|---|---|
| 测试工程师 | 更快发现用例问题，获得明确的问题依据和修改建议 |
| 测试负责人 | 提高评审一致性，降低重复检查成本，获得可复核的评审依据 |
| 测试管理平台 | 通过标准化接口接入 AI 评审能力，形成可集成的用例质量检查环节 |
| 测试团队 | 沉淀统一的评审标准和知识，逐步提升团队用例设计质量 |

### 2.4 产品定位边界

TestJury 是测试用例质量评审系统，不是：

- 测试管理平台的完整替代品；
- 测试用例编写或管理平台；
- 自动化测试执行平台；
- 缺陷管理系统；
- 需求管理系统；
- 自动决定测试质量是否合格的审批系统；
- 不区分测试类型、适用于所有质量活动的通用 AI 评审平台。

TestJury 可以与上述系统集成，但不应因此承担它们的核心职责。

## 3. 目标用户与角色职责

TestJury 的用户体系分为业务使用者、管理复核者和系统集成方三个层次。

### 3.1 第一层：测试工程师

**定位：主要业务使用者。**

主要职责：

- 提交需要评审的测试用例；
- 提供或关联必要的需求、业务规则和测试上下文；
- 查看 AI 评审发现的问题；
- 根据评审意见修改测试用例；
- 对不认同的评审意见提供说明或反馈；
- 重新提交修改后的用例进行评审。

主要诉求：

- 快速发现用例设计问题；
- 清楚理解问题发生在哪里；
- 知道为什么这是一个问题；
- 获得可操作的修改建议；
- 避免反复进行低价值的人工检查。

### 3.2 第二层：测试负责人

**定位：评审复核者和最终业务决策者。**

主要职责：

- 查看 AI 评审结果；
- 判断问题是否成立；
- 处理存在争议或需要业务判断的问题；
- 根据团队规范决定是否接受用例；
- 对 AI 评审结果进行确认、驳回或补充；
- 在必要时调整团队评审标准或反馈知识问题。

主要诉求：

- 了解用例的主要质量风险；
- 快速定位需要人工关注的问题；
- 复核 AI 结论及其依据；
- 保留最终审批权；
- 让团队的评审尺度更加统一。

**关键原则：AI 可以提出评审意见，但不能代替测试负责人作出最终业务审批决定。**

### 3.3 第三层：测试管理平台或其他调用系统

**定位：系统集成方。**

主要职责：

- 向 TestJury 提供待评审的测试用例及必要上下文；
- 接收评审任务状态和结构化评审结果；
- 根据自身业务流程展示评审结果；
- 根据自身权限和审批规则决定是否允许用例进入后续流程；
- 维护 TestJury 与自身业务对象之间的关联关系。

主要诉求：

- 通过 API 或其他约定方式接入评审能力；
- 获得结构化、稳定、可追溯的评审结果；
- 将 AI 评审纳入现有测试管理流程；
- 自主配置后续审批或流程门禁。

TestJury 不负责替调用方定义完整的测试管理流程，也不默认拥有调用方系统中的审批权限。

### 3.4 角色权限原则

| 行为 | 测试工程师 | 测试负责人 | 调用系统 |
|---|---:|---:|---:|
| 提交测试用例评审 | 是 | 可按业务需要 | 是 |
| 查看 AI 评审结果 | 是 | 是 | 是 |
| 修改测试用例 | 按原系统权限 | 按原系统权限 | 按接口约定 |
| 复核 AI 评审意见 | 可反馈 | 是 | 不默认承担 |
| 最终业务审批 | 否 | 是 | 可按自身流程执行 |
| 修改团队评审标准 | 否 | 按授权管理 | 不默认拥有 |
| 管理系统集成配置 | 否 | 按授权管理 | 按接口约定 |

具体账号、组织、角色、数据权限和接口鉴权方式由权限设计及 API 文档定义。本文档只确定业务职责，不规定具体授权实现。

### 3.5 与系统角色的映射

业务角色与 `docs/17` 的系统角色不是一一对应，必须显式映射，避免把"提交人"当成"审批人"：

| 业务角色 | 系统角色 | 说明 |
|---|---|---|
| 测试工程师 | `reviewer` | 可提交、查看、issue 级反馈、`request_changes` |
| 测试负责人 | `approver` | `reviewer` 权限 + `approve`/`reject`；必须个人可信身份 |
| 调用系统 | 系统级 API Key（`caller_id`） | 可提交与查询；不默认拥有审批权（`docs/09` §6.1） |
| 平台管理员 | `admin` | 系统配置；不自动获得 `approver` 或 `kb_publisher` |
| 知识库角色 | `kb_creator`/`kb_reviewer`/`kb_publisher` | 与业务审批无关，职责分离见 `docs/11` §11 |

> 调用系统可以在自身流程中执行最终审批；如果它把审批结果回传 TestJury，TestJury 只做记录与展示，不代替调用方定义门禁（见 §9.4）。

## 4. 核心业务流程

### 4.1 标准业务流程

1. **提交评审**：测试工程师或调用系统提交测试用例。
2. **上下文准备**：关联需求、业务规则、测试范围及其他必要信息。
3. **输入校验**：检查评审输入是否满足基本要求；必要信息不足时明确提示。
4. **AI 评审**：系统依据适用的评审标准执行用例质量分析。
5. **结果汇总**：整合各评审环节发现的问题、证据、建议和结论。
6. **结果呈现**：向测试工程师和测试负责人展示结构化结果。
7. **人工复核**：测试负责人判断问题是否成立，并处理需要业务判断的事项。
8. **用例修改**：测试工程师根据意见修改用例。
9. **重新评审**：必要时提交修改后的版本再次评审。
10. **业务审批**：测试负责人或调用系统依据自身业务规则作出最终决定。

### 4.2 业务流程原则

- AI 评审与人工审批是两个不同环节，必须在状态和记录上区分。
- 每次评审应关联明确的输入版本，避免用例修改后无法判断历史结果对应的内容。
- 评审问题应尽可能关联具体用例内容及其依据。
- 输入信息不足时，应明确表达评审限制，不应伪装成完整评审。
- 重新评审应能够区分新旧结果，避免历史意见与当前版本混淆。
- 人工复核结果不应覆盖或伪造原始 AI 评审结果。

### 4.3 业务状态的概念区分

业务上至少需要区分以下状态类别，并映射到下游字段（不合并为一个"通过/不通过"）：

| 状态类别 | 含义 | 下游字段 |
|---|---|---|
| 评审任务状态 | 评审任务是否已提交、处理中、完成或失败 | `review_jobs.status`（`docs/17` §1） |
| AI 评审结论 | AI 对当前用例质量形成的机器判断 | `ai_verdict`（`blocked`/`conditional`/`need_human`/`null`） |
| 人工复核状态 | 人工是否已复核、是否接受相关问题 | `human_review_tasks.status` + `result`（issue 级） |
| 最终业务审批状态 | 用例是否被业务负责人或调用系统接受 | `review_decisions.decision` → 派生 `human_status`；或调用方外部流程 |

具体状态枚举、状态迁移和异常处理规则由 `docs/17`、`docs/09`、`docs/13` 定义。

## 5. 评审对象与评审范围

### 5.1 v1 核心评审对象

v1 仅聚焦于 **功能测试用例的质量评审**（`test_type=functional`）。评审对象是已经形成或正在形成的功能测试用例，重点检查其是否能够准确、清晰、完整地验证相关功能需求和业务规则。

### 5.2 v1 评审维度

v1 应围绕功能测试用例质量建立统一的评审标准。建议至少覆盖：

1. **需求一致性**：测试用例是否与需求描述和业务规则保持一致。
2. **测试目标明确性**：用例是否具有明确的验证目标。
3. **前置条件合理性**：执行用例所需的前置状态和条件是否明确、合理。
4. **测试步骤可执行性**：步骤是否清晰、完整，是否存在歧义或无法执行的描述。
5. **预期结果明确性**：预期结果是否具体、可观察、可判断。
6. **边界条件考虑**：是否遗漏与当前功能相关的重要边界场景。
7. **异常场景考虑**：是否遗漏合理且重要的异常路径。
8. **业务规则覆盖**：是否遗漏需求或业务规则明确要求验证的关键行为。
9. **数据合理性**：测试数据是否满足场景要求，是否存在明显矛盾或缺失。
10. **重复与冗余**：是否存在无意义的重复用例或重复步骤。
11. **自动化可行性提示**：用例是否具备必要的执行条件、数据准备和结果校验描述。

以上是**业务评审维度**。各维度的具体规则、权重、严重程度、判定标准和证据要求由 `docs/04` 与 `rubric/rubric.yaml` 定义，不在多个文档中重复维护。映射关系见 `docs/04` §2.1。

### 5.3 测试范围信息的使用边界

如果输入中提供了 `test_scope` 或类似测试范围信息，v1 可以利用它检查当前用例是否遗漏了范围中已经明确列出的场景。

但必须明确：

- v1 不输出完整的功能点覆盖率；
- 不将单条用例的局部评审包装成整个需求或功能的覆盖率评估；
- 不因未提供完整测试范围就推断整个功能存在覆盖缺口；
- 评审意见应明确区分"当前用例存在的问题"和"当前输入范围内可能未覆盖的场景"。

完整的需求—功能点—测试场景—测试用例覆盖关系分析，应作为后续独立能力规划（v1.5，见 §10.2）。

### 5.4 自动化可行性评审的定位

自动化可行性属于功能测试用例评审中的辅助维度，而不是 v1 的核心产品定位。

v1 可以识别用例是否具备自动化所需的基本描述，例如：

- 前置条件是否明确；
- 测试数据是否可准备；
- 操作步骤是否具有可重复性；
- 预期结果是否可验证；
- 是否依赖人工判断或外部环境；
- 是否存在明显的环境、权限或数据依赖。

v1 不负责：

- 自动生成完整自动化测试脚本；
- 自动执行测试；
- 自动配置测试环境；
- 自动修复自动化脚本；
- 保证所有被判断为可自动化的用例都能成功自动化执行。

自动化可行性评审应提供判断依据和限制说明，不应将"理论上可自动化"表述为"已经具备可执行自动化能力"。

### 5.5 附件定位（v1）

v1 附件能力**仅用于存档、人工复核与审计取证**，不参与 AI 分析：

- 报告必须提供 `attachments[]`，并对每项标注 `analyzed_by_ai=false`；不得把附件内容写成 AI 结论依据。
- 附件访问权限、保留期限、删除规则按 `docs/10` §4.4；删除后历史报告保留最小元数据并显示"已删除"。
- 多模态分析需单独设计与验收，不属于 v1。
- 如果试点后确认没有存档/审计需求，可按 `Q-04` 评估延期；延期不改变已发布接口的删除语义。

## 6. 测试类型范围与扩展原则

### 6.1 v1 严格限定为功能测试

v1 不将性能测试、安全测试、兼容性测试、可靠性测试、可用性测试等纳入正式评审范围。

原因：

1. 不同测试类型的质量目标不同；
2. 不同测试类型需要不同的评审规则和专业知识；
3. 不同测试类型的输入材料和证据要求存在明显差异；
4. 将多种测试类型混入同一套评审标准，容易造成评审标准失焦；
5. 在核心功能测试评审质量尚未验证稳定之前，过早扩展会增加验证和维护成本。

**输入契约**：调用方必须通过 `case.test_type` 显式声明测试类型，**v1 只接受 `functional`**。缺失 → **422 `TEST_TYPE_REQUIRED`**；非功能类型 → **422 `UNSUPPORTED_TEST_TYPE`**；两种情况都不创建任务、不进入模型评审、不输出质量结论（见 `docs/03` §1、`docs/19` §2）。

**兼容模式**：仅当服务端显式配置 `TEST_TYPE_DEFAULT_POLICY=compat` 且调用方在 `TEST_TYPE_COMPAT_CALLERS` 白名单时，缺失才按 `functional` 处理；必须记录 `test_type_source=compat_default` 并告警，且设置退出时间/版本边界。默认 `strict`，**不得静默推断**。

**禁止行为**：不得使用功能测试 Rubric 对非功能用例强行给出 `blocked`/`conditional`/`need_human` 结论；不得把"不支持"包装成"评审发现质量问题"；报告必须展示实际 `test_type` 及其来源。

### 6.2 长期定位：可扩展的测试用例质量评审系统

TestJury 的长期产品定位仍然是测试用例质量评审系统，而不是永远只支持功能测试的单一工具。

未来可以通过独立的测试类型配置扩展能力，例如：

- 功能测试评审标准；
- 性能测试评审标准；
- 安全测试评审标准；
- 兼容性测试评审标准；
- 其他经过业务论证的测试类型。

每种测试类型应具备与其专业目标相匹配的：

- 评审标准（Rubric）；
- 知识库或专业知识来源；
- 输入上下文要求；
- 证据和问题分类；
- 结论规则；
- 验收数据集和质量门槛。

**扩展测试类型不等于简单增加几个提示词。** 新测试类型必须经过独立的业务设计、评审标准设计、质量验证和版本决策（决策规则见 §12.3）。

## 7. 业务输入边界

### 7.1 输入内容

TestJury 的核心输入为待评审的功能测试用例。为提高评审准确性，可以根据评审任务提供以下上下文（对应 `docs/03` §1 的请求字段）：

| 输入类别 | 说明 | 业务作用 | 请求字段 |
|---|---|---|---|
| 测试用例 | 用例标题、前置条件、步骤、预期结果等 | 核心评审对象 | `case` |
| 测试类型 | v1 仅 `functional`；必填 | 判断是否在支持范围 | `case.test_type` |
| 需求信息 | 需求描述、验收标准、需求条目等 | 判断用例是否符合需求 | 知识库/需求上下文 |
| 业务规则 | 业务约束、状态规则、计算规则等 | 判断用例是否符合业务逻辑 | 知识库 `RULE-*` |
| 测试范围 | 当前任务明确要求验证的功能或场景 | 辅助识别范围内的场景遗漏 | `test_scope` |
| 自动化上下文 | 执行环境、工具、数据准备方式等 | 辅助判断自动化可行性 | `automation_context` |
| 历史信息 | 历史评审记录、已确认规则等 | 在适用情况下提供参考 | `related_case_ids`、知识库历史缺陷 |

### 7.2 输入质量要求

- 输入字段应有清晰定义，避免不同调用方对同一字段产生不同理解（唯一字段定义见 `docs/17`）。
- 必要输入缺失时，应明确提示缺失项及其影响。
- 可选输入缺失时，应说明评审能力受到的限制。
- 不得将模型推测的业务信息当作用户提供的事实。
- 不得在缺乏需求依据时，直接把某种测试设计偏好判定为确定缺陷。
- 对上下文冲突，应指出冲突来源，必要时转交人工判断。

### 7.3 信息不足时的处理原则

信息不足不等于用例必然不合格。

系统应区分：

1. **用例本身存在问题**：例如步骤与预期结果矛盾。
2. **评审依据不足**：例如缺少需求说明，无法确认某个场景是否必须覆盖。
3. **输入信息冲突**：例如需求描述与业务规则相互矛盾。
4. **当前能力不支持**：例如提交了 v1 不支持的测试类型。

对以上情况应分别给出问题或限制说明，不能统一归为用例质量缺陷。下游表达方式：

| 情况 | 下游字段/状态 |
|---|---|
| 用例自身问题 | `issues`（正常问题，带证据） |
| 评审依据不足 | `evidence_status=insufficient`、`degraded_reasons`、`review_completeness` |
| 输入信息冲突 | `evidence_status=conflicted` → `need_human` |
| 类型/能力不支持 | 422 `UNSUPPORTED_TEST_TYPE`（不建任务）；能力内的降级记 `degraded_reasons` |

## 8. 业务输出边界

### 8.1 核心输出

TestJury 的评审结果应尽可能包含（对应报告字段见 `schemas/report.schema.json`）：

1. **问题描述**：发现了什么问题 → `issues[].rationale`。
2. **问题位置**：问题对应的用例、步骤、字段或内容位置 → `issues[].step_index`。
3. **问题类型**：问题属于哪个评审维度 → `issues[].dimension` + `category`。
4. **严重程度**：问题对用例质量的影响等级 → `issues[].severity`。
5. **证据依据**：对应的需求、业务规则、测试范围或用例内容 → `issues[].evidence_refs`、`kb_refs`、`evidence_status`。
6. **修改建议**：建议如何修改或补充 → `issues[].suggestion`。
7. **评审限制**：当前判断依赖哪些信息、存在哪些不确定性 → `degraded_reasons`、`review_completeness`、`input_quality`。
8. **AI 评审结论**：当前评审任务形成的机器评审判断 → `ai_verdict`。
9. **人工复核信息**：如已复核，记录人工处理结果及必要说明 → `human_review_items`、`human_review_tasks`、`decision_summary`。
10. **测试类型与来源**：本次实际采用的 `test_type` 与 `test_type_source`（`request`/`compat_default`），不得只显示默认值。

### 8.2 AI 评审结论边界

AI 评审结论用于表达当前评审发现和风险，**不等于最终业务审批**。

现有设计中的 `blocked`、`need_human`、`conditional` 等结论继续保持机器评审语义：

| AI 结论 | 业务含义 |
|---|---|
| `blocked` | 存在阻断性问题，当前不应直接进入后续业务环节 |
| `need_human` | 存在需要人工判断或补充确认的事项 |
| `conditional` | 在明确的条件或限制下，评审结果才具有参考意义 |

v1 不应输出 `approved` 作为 AI 自动审批结论。如果未来需要表达"未发现明显问题"，也应使用不会被误解为最终审批通过的机器评审语义，并在接口和界面中明确标注其含义。

### 8.3 人工审批结论边界

最终业务审批由测试负责人或调用方依据自身流程完成。人工审批至少应与 AI 评审结论在概念上分离：

- AI 评审结论：系统分析后形成的机器判断；
- 人工复核结果：人工对 AI 发现的问题进行确认或驳回；
- 最终业务审批：有权限的业务角色或调用系统作出的流程决定。

人工可以接受、驳回或补充 AI 评审意见，但不应篡改历史 AI 评审记录（`ai_verdict` 不可变，人工决定走 append-only 的 `review_decisions`）。

**外部审批**：如果调用方在自身系统中完成最终审批，TestJury 不要求回传；回传时只作为业务记录保存，不改变 `ai_verdict`，也不自动控制调用方流程。

### 8.4 结果可追溯要求

评审结果应能够关联：

- 被评审的用例及其版本（`case_id`、`case_version`、`input_hash`）；
- 本次评审的输入上下文（`test_scope`、`automation_context`、附件指纹）；
- 使用的评审标准版本（`rubric_version`）；
- 评审任务及执行时间（`review_id`、`created_at`/`finished_at`）；
- 发现的问题及其证据（`issues`、`evidence_refs`）；
- AI 原始评审结果（`report_json`、模型原始输出存档）；
- 人工复核记录（`human_review_tasks`、`human_review_events`）；
- 最终业务审批记录（如由 TestJury 负责记录或由调用方回传）。

具体字段、存储策略和审计实现由 `docs/02`、`docs/09`、`docs/14` 定义。

## 9. 系统职责边界

### 9.1 TestJury 负责

- 接收功能测试用例评审请求；
- 校验评审输入（含 `test_type` 支持范围）；
- 根据适用的评审标准组织 AI 评审；
- 在允许的范围内检索和使用知识依据；
- 识别用例质量问题；
- 输出问题、证据、建议和机器评审结论；
- 保留必要的评审记录和版本关联；
- 支持人工复核信息的记录或集成；
- 向外部系统提供约定的评审能力和结果。

### 9.2 TestJury 不负责

- 编写和维护完整的产品需求；
- 代替测试人员完成全部测试设计工作；
- 执行手工测试或自动化测试；
- 管理测试环境和测试数据；
- 创建、调度或维护自动化测试任务；
- 管理缺陷生命周期；
- 代替测试负责人进行最终审批；
- 决定外部测试管理平台的完整流程；
- 保证测试用例能够发现所有软件缺陷；
- 对缺少依据的业务规则作出权威解释；
- 在 v1 中对性能、安全、兼容性等非功能测试用例作正式质量评审。

### 9.3 与外部系统的关系

| 外部系统 / 角色 | 主要职责 | TestJury 的关系 |
|---|---|---|
| 需求管理系统 | 管理需求、验收标准和需求变更 | 获取评审所需的需求上下文 |
| 测试管理平台 | 管理测试计划、测试用例及测试流程 | 接收用例评审请求并返回结果 |
| 自动化测试平台 | 管理自动化脚本、执行环境和执行结果 | 获取必要的自动化上下文；不承担执行职责 |
| 缺陷管理系统 | 管理缺陷记录和处理流程 | 不负责缺陷生命周期管理 |
| 知识库 | 存储需求规范、业务规则、测试规范等 | 为评审提供可追溯的参考依据 |
| 测试工程师 | 设计、修改和执行测试用例 | 提交用例并处理评审意见 |
| 测试负责人 | 复核评审结果并作出业务决策 | 查看、复核并完成最终审批 |

### 9.4 外部流程门禁

TestJury 可以向调用系统提供评审结果，供其制定流程门禁。例如，调用方可以根据 AI 评审结论、人工复核状态和自身业务规则，决定用例是否允许进入下一阶段。

但必须遵守：

- TestJury 不默认控制外部系统的流程状态；
- TestJury 不默认拥有最终放行权限；
- AI 评审结果不能直接等同于业务审批结果；
- 门禁策略由调用方负责定义和执行；
- 如果未来需要提供门禁能力，必须单独明确权限、责任和异常处理规则。

## 10. 产品版本范围

版本规划用于控制产品复杂度，避免在核心评审能力尚未稳定时过早扩展。

### 10.1 v1：功能测试用例质量评审

**目标：建立可靠、可追溯的功能测试用例 AI 评审闭环。**

范围包括：

- 单条功能测试用例质量评审；
- 需求和业务规则一致性检查；
- 用例步骤、预期结果、前置条件等质量检查；
- 边界、异常和业务规则相关问题识别；
- 基于已提供 `test_scope` 的范围内场景遗漏提示；
- 自动化可行性辅助评估；
- 评审问题、证据和修改建议输出；
- AI 评审结论与人工审批分离；
- 评审记录和必要的版本追溯；
- 面向测试管理平台的集成能力。

v1 明确不包括：

- 完整需求覆盖率分析；
- 多条用例之间的全局覆盖关系分析；
- 性能、安全、兼容性等非功能测试正式评审；
- 自动化脚本生成与执行；
- 自动审批或自动放行；
- 完整测试管理平台能力。

### 10.2 v1.5：评审覆盖关系增强

建议在 v1 的评审质量和稳定性达到验收要求后，再考虑：

- 多条测试用例之间的关联分析；
- 测试用例与需求、功能点、场景之间的覆盖关系；
- 重复用例和覆盖缺口分析；
- 更完整的需求级或功能级覆盖评估；
- 覆盖分析结果的可追溯证据。

v1.5 的具体范围需要根据 v1 使用反馈和评估数据另行确定。

### 10.3 v2：多测试类型与平台化扩展

在核心功能测试评审能力成熟后，可评估：

- 性能测试用例评审；
- 安全测试用例评审；
- 兼容性测试用例评审；
- 其他测试类型的独立评审能力；
- 更完善的组织级评审标准管理；
- 更深入的测试管理平台集成；
- 基于团队历史评审数据的质量分析。

以上属于方向性规划，不构成对具体版本交付时间或功能的承诺。每项能力都必须经过独立的业务论证和质量验收。

### 10.4 版本范围总表

| 能力 | v1 | v1.5 | v2 或后续 |
|---|---:|---:|---:|
| 单条功能测试用例质量评审 | 核心 | 保留 | 保留 |
| 需求一致性检查 | 支持 | 增强 | 保留 |
| 步骤和预期结果质量检查 | 支持 | 增强 | 保留 |
| 边界与异常场景提示 | 支持 | 增强 | 保留 |
| 基于输入范围的场景遗漏提示 | 有限支持 | 增强 | 保留 |
| 完整需求覆盖率分析 | 不支持 | 重点评估 | 可扩展 |
| 多用例关联分析 | 不作为核心 | 重点评估 | 可扩展 |
| 自动化可行性辅助评估 | 有限支持 | 增强 | 可扩展 |
| 自动化脚本生成 | 不支持 | 不作为默认目标 | 可评估 |
| 自动化测试执行 | 不支持 | 不支持 | 不属于默认定位 |
| 性能测试用例正式评审 | 不支持 | 不支持 | 可扩展 |
| 安全测试用例正式评审 | 不支持 | 不支持 | 可扩展 |
| 兼容性测试用例正式评审 | 不支持 | 不支持 | 可扩展 |
| AI 自动审批 | 不支持 | 不支持 | 不作为产品默认职责 |
| 人工审批记录与集成 | 支持必要闭环 | 增强 | 保留 |

## 11. 核心业务原则

### 11.1 证据优先

评审意见应尽可能有明确依据。依据可以来自需求、业务规则、测试范围、测试规范或用例自身内容。如果无法找到足够依据，应表达不确定性，而不是生成确定性缺陷结论（对应 `evidence_status` 与 E1–E4 证据分级）。

### 11.2 AI 辅助，不替代人工责任

AI 负责分析和提供评审意见；测试负责人或调用方负责最终业务决定。不得通过界面文案、状态命名或接口语义，让用户误以为 AI 已经完成最终审批。

### 11.3 评审范围必须明确

每次评审都应明确当前评审对象、输入上下文和适用标准。不能把局部用例评审结果夸大为整个需求、功能或产品的质量结论。

### 11.4 不确定性必须可见

对缺少上下文、存在冲突、知识依据不足或超出能力范围的情况，应明确展示限制（`degraded_reasons`、`review_completeness`、`input_quality`）。不能为了给出完整结果而掩盖输入不足。

### 11.5 评审结果必须可追溯

评审意见应尽可能关联输入版本、评审标准版本、证据来源和人工处理记录。历史评审记录应保留其原始语义，不因后续修改而被静默覆盖。

### 11.6 质量优先于功能数量

优先保证 v1 功能测试评审的准确性、稳定性、可解释性和可复核性。不以增加评审维度或测试类型数量作为产品成熟度的唯一衡量标准。

### 11.7 扩展必须有独立依据

新增测试类型、自动化能力、审批能力或覆盖分析能力时，必须明确：

- 新能力解决什么业务问题；
- 服务哪些用户；
- 需要哪些输入；
- 输出承担什么业务含义；
- 与现有能力如何区分；
- 如何验证质量；
- 是否改变现有职责边界。

## 12. 新需求准入原则

后续出现新需求时，应先判断其是否符合 TestJury 的产品定位，再决定是否进入版本计划。

### 12.1 准入判断问题

1. 该需求是否直接改善测试用例质量评审？
2. 是否服务于已定义的目标用户？
3. 是否属于当前版本明确支持的测试类型？
4. 是否需要 TestJury 承担其他系统的核心职责？
5. 是否会模糊 AI 评审与人工审批的边界？
6. 是否有足够的输入和证据支撑该能力？
7. 是否能够定义明确的验收标准？
8. 是否会显著增加系统复杂度，影响 v1 核心能力的稳定性？

### 12.2 需求分类建议

| 分类 | 判断标准 | 处理方式 |
|---|---|---|
| 核心范围内需求 | 直接改善 v1 功能测试用例评审 | 可进入 v1 需求评估 |
| 核心能力增强 | 改善准确性、证据、追溯或稳定性 | 优先评估 |
| 后续版本需求 | 有价值，但不属于 v1 必要范围 | 纳入后续版本候选 |
| 外部系统职责 | 属于测试管理、执行、缺陷或需求管理等系统 | 原则上不纳入 |
| 定位冲突需求 | 会改变 AI 与人工责任、产品职责或测试类型边界 | 必须先进行业务决策 |
| 暂不明确需求 | 价值、输入、验收标准或责任边界不清晰 | 暂缓，补充业务定义 |

### 12.3 需求扩展的决策规则

任何涉及以下事项的需求，不应仅通过技术实现直接纳入：

- 从功能测试扩展到其他测试类型；
- 从单条用例评审扩展到完整需求覆盖分析；
- 从 AI 评审扩展到自动审批；
- 从质量评审扩展到测试执行；
- 从独立评审服务扩展为完整测试管理平台。

此类变化必须先更新业务定位或版本范围，再调整架构、数据模型和 API。对应决策登记见 §14 与 `docs/08` §2.0.2。

## 16. 总结

TestJury 的核心定位是 **面向功能测试用例的 AI 质量评审系统**。

v1 应专注于单条功能测试用例的质量评审，帮助测试工程师发现问题、理解依据并改进用例，同时帮助测试负责人提高评审效率和一致性。

产品应坚持以下边界：

- 测试工程师是主要业务使用者；
- 测试负责人承担人工复核和最终业务决策责任；
- 测试管理平台是重要的系统集成方；
- v1 严格聚焦功能测试，不混入其他测试类型；
- 长期可以扩展为支持多测试类型的质量评审系统，但每种类型必须有独立的评审标准和质量验证；
- AI 负责评审，不负责最终审批；
- TestJury 负责质量评审，不负责测试执行；
- 评审结果必须尽可能有证据、有限定、可追溯；
- 新需求必须先通过业务定位和职责边界判断，再进入技术设计。

**产品发展的优先级应当是先把功能测试用例评审做准确、做稳定、做可信，再扩展评审范围和平台能力。**

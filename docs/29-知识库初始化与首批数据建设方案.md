# 29 · 知识库初始化与首批数据建设方案

> 版本：v1.7 · 2026-11-10（补充 16 落实：历史缺陷升级条件、帮助度口径、试点台账）
> 目的：回答"第一批知识从哪来、怎么审、怎么验"，避免把"定义了知识库结构"误当成"知识库可用"。
> 关联：`docs/11`（知识库维护与发布）、`docs/16`（质量治理）、`docs/25`（解析与增量）、`docs/07`（检索黄金集）、`docs/00`（业务边界）。

---

## 1. 范围与原则

- 首批只做 **3–5 个高价值功能模块**，不做全量导入。
- 每个模块必须能回答：规则从哪来、谁审核、适用范围、如何检索验证、错了怎么回滚。
- **历史缺陷是风险线索，不是当前业务规则**；只有经审核、标注适用版本的条目才能进入有效知识集。
- 知识库质量以"对评审结论的帮助"验收，不以条目数量验收。

不在本文档范围：知识库编辑界面、自动抽取、跨模块覆盖分析、非功能测试知识（v2 另行设计）。

---

## 2. 首批模块选择

### 2.1 选择标准

| 维度 | 要求 | 权重建议 |
|---|---|---|
| 真实用例量 | 近 3 个月有稳定提交量 | 高 |
| 规则稳定性 | 业务规则近期无大改；有明确 owner | 高 |
| 历史问题代表性 | 有可复盘的历史缺陷/评审争议 | 中 |
| 来源可得性 | 需求、规则、接口文档可获得且可信 | 高 |
| 专家可审核 | 有模块负责人/策划愿意审核 | 高 |
| 可验收性 | 能构造检索与评审验收集 | 中 |

### 2.2 候选与决策

建议从现有测试点覆盖的模块中选 3–5 个（示例：背包/仓库、挖宝、语音聊天室+打赏、帮会/约战、奇穴装配）。最终名单由模块负责人确认，登记为决策记录（待决项 `Q-07`），并同步到机器台账 `design/kb_pilot.yaml`（含 owner、资料清单、规则数、用例数、验收数据集）。

每个模块产出一页 `kb_content/<模块>/README.md`：owner、范围、来源清单、审核人、首个发布版本。

## 3. 知识来源

| 来源 | 典型内容 | 权威性 | 用途 | 限制 |
|---|---|---|---|---|
| 已确认业务规则 | 状态、数值、前置、冷却 | E1 | 判定规则冲突 | 必须有 owner 与版本 |
| 需求/规格说明 | 功能描述、验收标准 | E2 | 判断意图与覆盖 | 需求变更需同步 |
| 接口文档 | 字段、错误码、约束 | E2 | 判断可执行/数据 | 与实现可能不一致 |
| 测试规范 | 用例模板、步骤要求 | E3 | 测试设计建议 | 不能当业务事实 |
| 经审核的历史用例 | 标准写法、场景集合 | E2/E3 | 参考与对照 | 不能直接证明当前正确 |
| 历史缺陷与复盘 | 曾出现的缺陷模式 | E2（weak） | 风险提示 | **不得表述为当前缺陷** |
| 专家经验 | 边界/异常设计经验 | E4 | 建议 | 必须标推断，不能判 blocker |

> 每条知识必须记录来源与适用范围；没有来源的"经验"只能进 `draft`，不得作为 E1/E2 依据。

### 3.1 历史缺陷升级为正式规则的条件（Q-08 / D181）

历史缺陷只有同时满足以下条件，才允许整理为正式规则：

1. 能定位原始缺陷记录或可信复盘资料；
2. 能确认缺陷发生时的产品版本与业务条件；
3. 能确认其反映稳定业务约束，而不是一次性实现错误；
4. 模块负责人确认该约束当前仍有效；
5. 能明确适用范围、生效版本与失效条件；
6. 由 `kb_reviewer` 审核通过；
7. 升级后生成新的 `RULE-ID` 或明确规则版本，不覆盖历史缺陷记录。

字段（`docs/17` §4.1）：`origin_type`、`derived_from`、`bug_version`、`fixed_version`、`current_validity_confirmed`、`confirmed_by/at`、`rule_status`。未满足条件的条目只能保持在 `historical_bug` 或 `draft`，不得进入当前证据集。

## 4. 数据准入规则

每条知识/规则至少包含：

| 字段 | 说明 | 必填 |
|---|---|---|
| `RULE-ID` | 稳定、唯一、不复用 | 是 |
| `module` / `function_point` | 所属模块与功能点 | 是 |
| `doc_type` | `rule`/`requirement`/`known_limit`/`history_bug`/`term`/`flow` 等 | 是 |
| `source_ref` / `source_version` | 出处与版本 | 是 |
| `applicable_conditions` | 适用产品/环境/配置/角色 | 是（可为空但需显式） |
| `valid_from/to_version`、`effective_from/to` | 生效区间 | 条件 |
| `rule_status` | `draft`/`reviewed`/`published`/`deprecated` | 是 |
| `evidence_level` | E1–E4 | 是 |
| `owner` / `reviewer` | 维护与审核责任人 | 是 |
| `created_at` / `updated_at` | 时间 | 是 |
| `supersedes` / `superseded_by` | 替代关系（KB 内容版本，不是评审代次） | 条件 |
| `content_hash` | 切片与增量构建依据 | 是 |

**准入 checklist**：来源可追溯、适用条件明确、审核人签字、冲突已裁决、切片不破坏语义、检索可命中、失效规则不进检索。任一不满足 → 不得 `published`（`docs/11` §7.1、`docs/25` §1）。

---

## 5. 知识粒度

优先存"可独立引用、可追溯、可支撑判断"的知识单元，而不是把整份文档切块：

| 单元 | 示例 | 适用 |
|---|---|---|
| 一条业务规则 | "藏宝点冷却 30 秒" | 规则冲突、覆盖判断 |
| 一个功能点说明 | "藏宝点发现流程" | 意图、场景覆盖 |
| 一条已知限制 | "跨地图挖宝不支持" | 边界/异常 |
| 一个历史缺陷 | "v2.3 背包满时挖宝道具丢失" | 风险提示（weak） |
| 一个术语 | "藏宝点 ≠ 宝箱点" | 术语一致性 |
| 一个完整流程 | "接取→挖宝→结算" | 步骤/状态判断 |

- 一条规则一个 chunk；文档章节可保留 heading_path 供回溯。
- 历史缺陷必须带"发生版本/修复版本"，默认 `evidence_strength=weak`。

---

## 6. 分类、元数据与检索

- 分类沿用 `docs/17` §4 的 `doc_type`；检索按"结构化过滤 → 关键词 → 向量 → RRF → rerank → 证据包"（`docs/11` §5–§6）。
- 每条切片带 `source_ref`、`heading_path`、`content_hash`、`embedding_profile_id`、`valid_*`、`evidence_level`。
- 检索结果必须携带来源、版本、适用范围与有效状态；不适用但相关的证据可展示，不得作为判定依据（`docs/11` §9.1）。

---

## 7. 来源追溯与版本

- Git + Markdown 是唯一事实源；PostgreSQL 只是检索索引（`docs/11` §1）。
- 发布产生新的 `kb_version`；报告引用当时的 `kb_version` + `chunk_id`，历史可回查。
- 删除用 tombstone，不物理删历史；旧报告仍能定位到当时内容。
- 增量构建按 `content_hash`；规则删除必须在新版本显式体现（`docs/25` §2–§3）。

---

## 8. 审核与发布职责（RACI）

| 事项 | 负责 | 批准 |
|---|---|---|
| 模块选择与范围 | 模块负责人 | 测试负责人 |
| 来源收集与规则整理 | `kb_creator` | 模块负责人 |
| 规则审核 | `kb_reviewer` | 模块负责人 |
| 冲突裁决 | `kb_reviewer` + 模块负责人 | 产品负责人 |
| 发布/回滚 | `kb_publisher` | 模块负责人 |
| 废弃/替代 | `kb_publisher` | 模块负责人 |

- 生产环境 `kb_creator` 与 `kb_publisher` 不得为同一人；`admin` 不自动拥有发布权（`docs/17` §5）。
- 每次发布记录发布人、时间、差异报告与检索指标（`docs/11` §8.1）。

## 9. 冲突与失效处理

1. **同级权威冲突**（两条 E1 对同一行为规定不同）：不得自行选择，记录双方证据，评审转 `need_human`，发布前必须裁决。
2. **E1 与 E2 冲突**：以 E1 为准，提示"需求与规则不一致，需确认"。
3. **版本/时效**：过期或未生效规则默认不注入；只有"历史对照"场景可注入并标注失效。
4. **失效替代**：新规则发布时显式标记替代关系；旧规则 `deprecated` 后不再进入检索。
5. **更新后历史评审**：不自动重评；需要时新建 generation 并记录触发原因（`docs/11` §7.2）。

## 10. 首批数据验收

| 指标 | 定义 | 初始门槛 |
|---|---|---|
| 来源可追溯率 | 有 `source_ref` 且可回查的条目比例 | 100% |
| 人工审核通过率 | 提交审核后通过的比例 | ≥ 90% |
| 过期知识识别率 | 已失效/不适用条目被正确排除的比例 | 100%（抽检） |
| 规则检索 Recall@10 | 黄金集正确规则进入前 10 | ≥ 90% |
| nDCG@10 | 多个相关证据排序质量 | ≥ 0.75 |
| 证据可定位率 | 能定位 `chunk_id` + `source_ref` + `kb_version` | 100% |
| 错误知识影响率 | 因错误知识导致的错误评审比例 | ≤ 5%（人工抽检） |
| 对评审的帮助度 | 测试人员认为证据有助于判断的比例 | ≥ 70% |

- 黄金集：每模块 ≥ 20 条查询，含精确规则号、数值、同义改写与 hard negative；分层报告。
- 与 `docs/07` §2.3 检索黄金集合并管理，避免重复标注。

### 10.1 "帮助度"统计口径（D183）

"对评审有帮助"必须可计算，不能只报一个主观比例：

- **分母**：注入了知识证据、且进入人工复核的评审任务；一个任务由一名复核人评一次，同一用户多次评分不独立计数。
- **评价项**：`helpful` / `neutral` / `misleading` / `unjudgeable` 四类；可选 5 分制仅作辅助。
- **判定标准**："有帮助"指证据实际影响或确认了问题判断（引用、成立性、严重级），不是"读过"或"报告更长"。
- **主观与客观分开**：主观帮助度单独报告；知识库是否有效必须同时看 K0/K1 客观质量增量（`Q-15`、`docs/30` §3.1），不得用主观比例替代。
- 报告需给出样本量、评价人角色、任务分布与 `misleading` 比例，而不是只写"≥70% 有帮助"。

## 11. 建设路径（时间盒）

1. **选择与建模板（1 周）**：确认 3–5 个模块，产出 owner、来源清单、规则模板与审核表。
2. **首批录入与审核（2–3 周）**：每模块 ≥ 20 条有效规则；`draft → reviewed` 全流程演练。
3. **切片/索引与检索验收（1 周）**：发布 candidate，跑黄金集；不达标只修知识/检索，不调 Prompt。
4. **试点评审（2 周）**：用真实用例跑评审，人工复核并记录"知识是否帮助判断"；通过后再扩模块。

> 不通过就停在试点，不带病全量导入；知识库建设不是"导入越多越好"。

## 13. 风险与待决

| 风险 | 应对 |
|---|---|
| 来源不可信 | 无来源不进 `published`；E1 必须 owner 签字 |
| 历史缺陷被误用 | `history_bug` 只能 weak，Prompt 与校验双重限制 |
| 规则冲突未裁决 | 发布前强制裁决，冲突证据留档 |
| 规则过期未清理 | `valid_to` + 季度复核；过期不注入 |
| 只追求条目数 | 以检索与评审帮助度验收，不看数量 |

待决事项：首批模块名单（`Q-07`）、历史缺陷转正式规则的条件（`Q-08`）、供应商数据准入（`Q-09`）、附件是否延期（`Q-12`）。登记见 `docs/08` §2.16。

# 01 · 架构设计

## 1. 系统边界

```
调用方（测试流水线 / 人工上传）
        │  HTTP + API Key
        ▼
┌──────────────────────────────────────────────┐
│              评审团服务 (FastAPI)              │
│                                              │
│  接收 → 规范化 → 知识库检索 → 三方盲评         │
│       → 问题融合 → 主审仲裁 → 渲染 → 落库     │
│                                              │
└───────┬───────────────┬──────────────┬───────┘
        │               │              │
        ▼               ▼              ▼
   qwen-max       deepseek-flash   kimi-k3
   （主审）          （陪审甲）       （陪审乙）
        │
        ▼
   PostgreSQL + pgvector
   （任务 / 报告 / 问题 / 原始调用存档 / 知识库 / 缺口）
```

服务自身**不含任何执行测试的能力**，只做静态评审。所有模型调用走 OpenAI 兼容协议，通过配置切换。

## 2. 组件划分

| 组件 | 职责 |
|---|---|
| API 层 | 请求校验、鉴权、创建任务、查询结果、接收复核回写 |
| 任务调度 | 进程内 asyncio 队列 + 信号量（并发 4），负责排队、超时、重试 |
| 用例规范化 | 结构化用例校验；`raw_text` 走预处理模型拆分步骤 |
| 知识库检索 | 模块命中 → 组装"结构化规则 + 原文切片 + 术语 + 已知限制"上下文包 |
| 盲评执行 | 三模型并行调用，互不可见 |
| 问题融合 | 规则键分桶 + embedding 同义合并 + 置信度计算 |
| 主审仲裁 | 主审第二次调用：确认/驳回/补充，产出终稿问题清单与结论 |
| 报告渲染 | JSON 落库 + Markdown 模板渲染 |
| 模型适配层 | OpenAI 兼容调用、超时/重试、token 计量、原始请求响应存档 |
| 知识库子系统 | 文档加载、索引构建、检索、缺口聚合 |
| 复核回写 | 记录人工对每条问题的裁决，供黄金集与调优使用 |

## 3. 主流程

```
1. POST /v1/reviews
   └─ 校验请求 → 计算 input_hash → 幂等检查
      ├─ 已存在相同 hash 且未 force → 直接返回旧报告
      └─ 新建 review_job（status=queued）→ 返回 review_id

2. 进入队列，获得并发槽位（≤4）
   status=processing, stage=preprocess
   ├─ 结构化用例：直接通过
   └─ raw_text：调用预处理模型拆成 steps 数组
      └─ 拆分失败 → 标记 degraded_reason=raw_text_unparsed，steps=null

   stage=kb_retrieve
   ├─ 模块命中 → 组装上下文包（≤15k token）
   │    包含：功能点索引、业务规则（带 RULE-ID）、术语表、已知限制、相关历史缺陷
   └─ 模块未命中 → degraded=true，只注入通用测试设计准则

   stage=blind_review  （三路并行，各自独立上下文，互不可见）
   ├─ 主审盲评  qwen-max       → 全维度评审
   ├─ 陪审甲    deepseek-flash → 业务/需求视角为主
   └─ 陪审乙    kimi-k3        → 测试设计 + 自动化可行性为主
   每路输出：结构化 issues[] + summary

   stage=fusion
   ├─ 规则键分桶：(case_id, step_index±1, dimension)
   ├─ 桶内 embedding 余弦 ≥ 0.86 → 判为同一问题，合并
   ├─ 置信度：1 方提出 0.6 / 2 方 0.85 / 3 方 0.95
   └─ 同一位置"有问题 vs 没问题"的对立 → 标记 disputed

   stage=arbitration  （主审第二次调用）
   输入：规范化用例 + 知识库上下文包 + 三份原始意见 + 融合候选清单
   输出：
   ├─ 终稿 issues[]（adopted / rejected / disputed / need_human）
   ├─ 驳回理由（每条被驳回的陪审意见必填）
   ├─ 主审补充问题（标记 source=chief_supplement）
   └─ verdict + 摘要 + 知识库缺口候选

   stage=render
   ├─ 结论判定（见 §6）
   ├─ JSON 落库、Markdown 渲染
   └─ status=done
```

## 4. 盲评约束（防污染）

1. **三路调用并发发起，互不读取对方结果**；主审在盲评阶段的上下文里不出现"还有两个陪审"的暗示，避免它揣测他人意见。
2. **三路使用同一份用例和同一份知识库上下文包**，差异只来自角色 rubric 与模型本身。
3. **主审的两份输出（盲评 / 仲裁）分别落 `model_runs`**，prompt 与输出完整存档，事后可复盘。
4. 仲裁时主审能看到自己那份盲评结果（它本来就在三份里），但对三方**一视同仁处理**。

## 5. 问题融合算法

```
输入：三份 issues[]（各自为 object 数组）
步骤 1 归一化
  每条 issue 必须有：step_index（可为 null）、dimension、severity、category、
                   evidence_quote、rationale、suggestion、kb_grounded、kb_refs
  字段缺失或格式不符 → 该条丢弃并记入 model_runs.parse_warnings

步骤 2 分桶（规则键）
  桶键 = (case_id, dimension, step_bucket)
  step_bucket：以该 issue 的 step_index 为基准，±1 步的 issue 落入同一候选桶
  （step_index 为 null 的问题单独成"用例级"桶）

步骤 3 同义判定（embedding）
  桶内两两计算 issue 描述（rationale + evidence_quote）的余弦相似度
  ≥ 0.86  → 同一问题，合并
  0.70–0.86 → 标记"疑似重复"，交仲裁模型判定
  < 0.70  → 不同问题，各自保留

步骤 4 合并
  severity   = 三方取最高
  category   = 取出现次数最多者（并列取主审）
  proposed_by = 合并去重
  confidence = 1 方 0.6 / 2 方 0.85 / 3 方 0.95
  evidence   = 保留最完整的一条原文引用
  kb_grounded= 任一方有知识库依据即为 true，kb_refs 合并

步骤 5 对立检测
  同一桶内出现"该步骤有问题"与"该步骤无问题"的明确对立 → disputed
  disputed 不参与投票，直接进人工复核清单
```

> 阈值 0.86 / 0.70 为初始值，写入配置文件，随种子集评测调整。

## 6. 结论判定

系统只输出三档，**永不输出"通过"**：

| 结论 | 条件 |
|---|---|
| **打回** `blocked` | 存在任一 `blocker` 级问题，且**未被多数（≥2/3）否决** |
| **打回（待裁决）** `blocked` | 主审驳回了陪审提出的 `blocker`，但两陪审均未同意驳回 → 仍判打回，标注"待人工裁决" |
| **待人工裁决** `need_human` | 无 `blocker`，但存在 `disputed` 项，或参与模型不足 3 个 |
| **有条件通过** `conditional` | 无 `blocker`、无 `disputed`，可存在 `major` / `suggestion` |

补充规则：
- 主审新增的 `blocker` 若两陪审均未提及 → 结论仍为打回，同时进人工复核清单（防主审幻觉误毙）。
- 三份意见结论一致但理由互相矛盾 → 结论不变，矛盾进"存疑项"。
- 只有人工通过复核接口把结论置为 `approved` 后，报告才显示"通过"。

## 7. 降级与失败矩阵

| 故障 | 行为 |
|---|---|
| 陪审甲或乙超时/报错 | 重试 1 次；仍失败 → 继续评审，`participants` 记 2 个，报告顶部标注"仅 2 模型参与，可信度下降" |
| 主审盲评失败 | 重试 2 次；仍失败 → **任务失败**（无法构成三方评审） |
| 主审仲裁失败 | 重试 2 次；仍失败 → **任务失败**，三份盲评结果保留可查 |
| 三模型全部失败 | 任务失败 + 告警 |
| 知识库未命中模块 | 降级评审，报告顶部醒目提示；业务规则类问题标记为推断 |
| `raw_text` 无法结构化 | 降级为整篇评审，`step_index=null`，问题定位到用例级 |
| 排队超限 | 返回 429 + Retry-After |

## 8. 并发、超时、幂等

- 单机并发 4 个评审任务；每个任务内三路模型调用并行。
- 单次模型调用超时 120s；单任务总超时 10 分钟。
- 幂等键：`(case_id, input_hash, kb_version, rubric_version, prompt_version)`；相同则返回已有报告，`force=true` 才重跑。
- 批量任务内部逐份独立入队，部分失败不影响整体；批次汇总给出成功/失败/未完成计数。

## 9. 版本与可追溯

报告头部固定记录：

```
kb_version      = 知识库内容哈希
rubric_version  = rubric 文件哈希
prompt_version  = 各 prompt 文件哈希（按角色分别记录）
model_versions  = qwen-max / deepseek-flash / kimi-k3 的具体版本号
```

任何一次"为什么这次评审结论变了"都可以通过这五个版本号定位到差异来源。

## 10. 安全与合规

- 三厂商云 API 已确认允许调用；用例内容按公司要求记录调用日志（调用方、时间、模型、token）。
- API Key 鉴权，`X-Caller-Id` 记录调用方。
- 原始 prompt / 输出全量存档于 `model_runs`，仅服务内部可读；对外接口不返回原始 prompt。

# 01 · 架构设计

> 版本：v0.11 · 2026-11-10（最后一轮冻结候选）

## 1. 系统边界

```
调用方（测试流水线 / 人工上传）
        │  HTTP + API Key
        ▼
┌──────────────────────────────────────────────┐
│              评审团服务 (FastAPI)              │
│                                              │
│  接收 → 规范化 → 检索（Hybrid） → 三方盲评     │
│       → 投票融合 → 主审仲裁 → 渲染 → 落库      │
│                                              │
└───────┬───────────────┬──────────────┬───────┘
        │               │              │
        ▼               ▼              ▼
   qwen-max       deepseek-flash   kimi-k3
   （主审）          （陪审甲）       （陪审乙）
        │
        ▼
   PostgreSQL + pgvector
   （任务队列 / 报告 / 问题 / 投票 / 原始调用存档 / 知识库 / 缺口）
```

服务自身**不含任何执行测试的能力**，只做静态评审。评审模型与 embedding 走 OpenAI 兼容协议；rerank 允许独立协议（DashScope / 本地），由模型适配层按配置切换。

## 2. 组件划分

| 组件 | 职责 |
|---|---|
| API 层 | 请求校验、鉴权、创建任务、查询结果、接收复核回写 |
| 任务队列 | PostgreSQL 持久化队列 + Worker 领取（租约、重试），并发由 Worker 数量控制 |
| 用例规范化 | 结构化用例校验；`raw_text` 走预处理模型拆分步骤 |
| 输入质量检查 | 硬错误（空/超长/字段非法）拒绝；软问题记 `input_quality`，与模型发现的问题分开 |
| 检索查询构建 | 把用例拆成标题/目的/前置/步骤/预期/数据多类查询，附结构化过滤条件 |
| 混合检索 | 结构化过滤 → 关键词（trigram/精确）→ 向量检索 → RRF 融合 → Reranker 精排 → 证据包 |
| 盲评执行 | 三模型并行调用，互不可见 |
| 问题融合 | 候选问题对齐、分层去重合并，写入 `review_candidates` |
| 候选问题 | 仲裁前中间实体，承载中性描述、claims 证据与来源留痕；投票挂在其上 |
| 决策计算 | `verdict.py` 按 `docs/12` 真值表统一计算，唯一入口 |
| 阶段恢复 | `review_stages` Checkpoint，失败从最后成功阶段继续 |
| 投票轮 | 三模型对候选问题逐条判断成立性与严重级，写入 `issue_votes` |
| 主审仲裁 | 条件触发：仅在存在分歧/证据冲突/补充意图时调用，逐条确认/驳回/补充 |
| 报告渲染 | `report_json` 落库（唯一事实源）+ 按 `report_schema_version` 渲染 Markdown；`issues` 为只读投影 |
| 模型适配层 | 模型注册表 + 聊天/Embedding/Reranker 三类适配器、超时/重试/限流、token 与成本计量、原始请求响应存档 |
| 输出校验 | 每次模型返回做 JSON/Schema/枚举/引用有效性校验，不静默修补 |
| 知识库子系统 | 文档加载、按类型切片、索引构建、检索、缺口聚合 |
| 知识库发布 | 校验 → 切片 → 向量化 → 检索回归 → 切 active / 回滚（见 `docs/11`） |
| 复核与审批 | issue 级反馈（评测信号）+ 报告级人工决定（`review_decisions`，见 `docs/09`） |

## 3. 主流程

```
1. POST /v1/reviews
   └─ **同步硬校验**（API 层，创建任务前）：JSON/字段类型/Schema、必填、steps 与 raw_text 不能同时为空、长度上限
      ├─ 不通过 → 直接返回 400/422，不创建任务
      └─ 通过 → 计算 input_hash（规范化输入）与 idempotency_key（+ 各版本号）
         ├─ 命中 active 记录且未 force → 返回原任务真实状态（见 03 §1）
         └─ 写入 review_jobs（status=queued, generation=1, case_version）→ 202 返回 review_id

2. Worker 领取任务（租约、attempt_count++）
   status=processing, stage=input_check
   ├─ **异步软校验**：预期缺失、步骤描述不清、前置/数据不充分 → 记入 input_quality
   ├─ 软问题不阻断评审，作为评审输入的一部分
   └─ 通过 → stage=preprocess
      （硬错误已在 API 层拦截；Worker 不再返回 422）

   stage=preprocess
   ├─ 结构化用例：直接通过
   └─ raw_text：调用预处理模型拆成 steps 数组
      └─ 拆分失败 → 标记 degraded_reason=raw_text_unparsed，steps=null

   stage=kb_retrieve
   ├─ 查询构建：标题 / 目的 / 前置 / 每步 action / 每步 expected / 测试数据
   ├─ 结构化过滤（module + function_point + doc_type + kb_version）
   ├─ 关键词（trigram/精确匹配）+ 向量召回 → RRF 融合 → Reranker 精排
   ├─ 组装证据包（≤15k token，Top K 默认 8–12，每条带溯源与证据类型）
   │    内容：业务规则（RULE-ID）、功能说明、术语、已知限制、相关历史缺陷
   └─ 模块未命中 → degraded=true，只注入通用测试设计准则

   stage=blind_review  （三路并行，各自独立上下文，互不可见）
   ├─ 主审盲评  qwen-max       → 全维度评审
   ├─ 陪审甲    deepseek-flash → 业务/需求视角为主
   └─ 陪审乙    kimi-k3        → 测试设计 + 自动化可行性为主
   每路输出：结构化 issues[] + summary
   每路返回后立即校验（JSON → Schema → 枚举 → 引用 → 数值范围）
   └─ 校验失败重试 1 次；仍失败按角色失败处理（见 §8），不修补后使用

   stage=fusion
   ├─ 规则键分桶：(case_id, dimension, step_index±1)
   ├─ 候选向量写入 candidate_embeddings，桶内召回"疑似重复"（0.70–0.86）
   ├─ Reranker 判定是否同一缺陷/同一根因
   ├─ 高确定性才合并；边界保留独立条目
   ├─ 写入 review_candidates（C-001…，含中性描述与 claims/evidence_status）
   ├─ 证据按 claim 绑定，不因合并提高证据强度
   └─ 同一位置"有问题 vs 没问题"的明确对立 → disputed

   stage=vote  （三路并行，互不可见）
   ├─ 投票材料：中性描述 + 用例 + 相同证据 + rubric 版本
   │    **隐藏** proposed_by / 他人论证 / 他人投票 / severity_proposal / 暗示严重级的措辞
   ├─ 逐条回答 validity 与 severity 两个独立字段
   └─ 缺失条目补 not_assessed，写入 issue_votes(candidate_id, model_run_id)

   stage=arbitration（条件触发）
   ├─ 服务端先计算：存在 disputed / severity_disputed / 证据冲突 / 主审拟补充问题？
   ├─ 否 → stage=skipped，直接进入 verdict（记录 arbitration_required=false）
   └─ 是 → 主审第三次调用；失败则 ai_verdict=need_human，不得用陪审替代仲裁
   输出：终稿候选处理（adopted / rejected / disputed / need_human）
   ├─ 驳回理由（每条被驳回的陪审意见必填）
   ├─ 主审补充问题（标记 source=chief_supplement）
   └─ 终稿问题 + 摘要 + 知识库缺口候选（**不输出 ai_verdict**）

   stage=verdict
   └─ verdict.py 按 docs/12 真值表重算 ai_verdict（唯一入口）

   stage=render
   ├─ 服务端按 §7 重算 ai_verdict
   ├─ report_json 落库（唯一事实源），同事务生成 issues 只读投影（candidate_id 回链候选）
   ├─ 按 report_schema_version 渲染 Markdown
   └─ status = done | completed_with_warnings
```

**人工决定不在流水线内**：评审完成后 `human_status=pending`，审批接口追加 `review_decisions`，只改人工状态，不改 `ai_verdict`、不改报告内容（见 `docs/09`）。

## 4. 盲评约束（防污染）

1. **三路调用并发发起，互不读取对方结果**；主审在盲评阶段的上下文里不出现"还有两个陪审"的暗示，避免它揣测他人意见。
2. **三路使用同一份用例、同一份 `test_scope` / `automation_context` 和同一份证据包**，差异只来自角色 rubric 与模型本身。
3. **主审的三份输出（盲评 / 投票 / 仲裁）分别落 `model_runs`**，prompt 与输出完整存档，事后可复盘。
4. 仲裁时主审能看到自己那份盲评结果（它本来就在三份里），但对三方**一视同仁处理**；投票轮三路同样互不可见，避免相互锚定。
5. **投票材料必须去来源化**：隐藏 `proposed_by`、隐藏其他模型的原始论证与解释，只给标准化候选描述、用例原文、必要证据与统一字段；禁止把"谁提的、说得多严重"带入投票。初审结论与投票结论分别落库，用于分析锚定效应。

**评审拓扑不写死**：实现支持 `single` / `dual` / `multi` 三种配置，报告记录 `topology` 与实际参与模型。三模型不是既定生产结论，由 `docs/15` 的 A–E 实验决定（见 README 决策 90）。

## 5. 知识检索与证据链路（Hybrid Retrieval）

检索质量决定评审质量：召回不足或召回错误，模型再强也只能在错误证据上判断。因此不使用"整份用例一次向量检索"的做法，而是**多查询 → 混合召回 → 融合 → 精排 → 证据包**五步。

### 5.1 多查询构建

把一份用例拆成多类检索查询，分别召回证据：

| 查询来源 | 主要用途 |
|---|---|
| 用例标题 / 功能点 | 定位模块与规则范围 |
| 测试目的 / 业务描述 | 召回功能说明与业务流程 |
| 前置条件 | 召回权限、状态、数据约束 |
| 每个步骤的 `action` | 召回流程规则与操作限制 |
| 每个步骤的 `expected` | 召回判定标准与业务规则（信息密度最高） |
| 测试数据 / 字段 / 枚举 / 边界值 | 精确召回数值、上限、错误码 |

原因：标题常缺少具体规则，前置条件对应权限/状态约束，步骤对应流程，预期结果承载最重要的业务规则，测试数据需要精确匹配。

每个查询携带 `module`、`function_point`、`doc_type`、`kb_version` 过滤条件；查询数默认上限 12，超出时按 **预期结果 > 步骤 > 前置条件 > 标题** 的优先级截断。

### 5.2 召回与融合

1. **结构化过滤**：先用元数据把候选限定在本模块、本功能点、当前 `kb_version`，避免跨模块、跨版本召回。
2. **关键词检索**：RULE-ID/字段名/错误码/数值的精确匹配 + `pg_trgm` 三元组相似度（中文可用的 v1 方案）；安装 `zhparser` 后可升级为 `zh` 分词的 FTS。负责精确词项，不依赖未部署的扩展。
3. **向量检索**：pgvector 余弦距离，负责同义表达、自然语言描述、语义相近规则。
4. **RRF 融合**：`score = Σ 1/(k + rank_i)`，`k` 默认 60；不对未校准的检索分数做线性相加。
5. **Reranker 精排**：RRF 后 Top 40 与查询一起交给 reranker，按业务相关性重排。
6. **证据包组装**：取精排 Top 8–12，按 15k token 预算装载；同一知识只保留最高排名的一条。

> 向量相似不等于业务相关：功能名相似但角色不同、规则描述相似但场景不同、字段名相似但含义不同——这些都交给 reranker 判断，而不是靠距离阈值。

多查询时按查询分别做检索与 RRF，再跨查询归并：同一知识取最高 rerank 分数，最后统一排序进入证据包。不能把多个查询的原始分数直接相加。

### 5.3 证据必须可溯源

每条进入上下文的知识至少携带：

- 知识条目 ID（`chunk_id` / `rule_id`）与原始文档 ID；
- `source_ref`（文档名 + 章节/行号）与 `heading_path`；
- `doc_type`（规则 / 功能说明 / 已知限制 / 历史缺陷 / 术语）；
- `module`、`function_point`、`kb_version`；
- 检索通道（fts / vector / rule_direct）、融合排名、reranker 分数；
- 原文内容。

评审结论的 `kb_refs` 指向具体知识条目，报告附录给出"知识 → 原文位置"映射。**不允许只输出"知识库认为不符合"**。

### 5.4 检索降级

| 故障 | 行为 |
|---|---|
| 向量检索不可用 | 退化为"结构化过滤 + 关键词（trigram/精确）"，`degraded_reasons += "vector_unavailable"` |
| 关键词索引不可用 | 退化为纯向量检索，`degraded_reasons += "keyword_unavailable"` |
| Reranker 超时 | 直接用 RRF 排序，`degraded_reasons += "rerank_skipped"` |
| 模块未命中 | 只注入通用测试准则，业务规则类结论一律降级为推断 |
| Embedding profile 不一致 | 禁止混用；按 profile 重建索引后再检索 |

降级必须在报告顶部明示，不能让"检索残缺"看起来像"知识库确认"。

## 6. 问题融合与投票

### 6.1 投票状态：未提及 ≠ 反对

只 merge 各模型的 `issues` 列表，无法计算支持票与反对票。因此 fusion 之后单独加一轮**投票**（`stage=vote`）：每个模型拿到候选问题清单，逐条给出态度并落 `issue_votes`。

| 值 | 含义 |
|---|---|
| `accept` | 明确认为该问题成立 |
| `reject` | 明确认为该问题不成立 |
| `not_assessed` | 未评估 / 无法评估该条（不代表否定） |
| `uncertain` | 评估后表示不确定 |

`not_assessed` 不计入反对票。把"没说话"当作"反对"会造成错误的多数否决。

### 6.2 分层融合

```
步骤 1 归一化
  每条 issue 必须有：step_index（可为 null）、dimension、severity、category、
                   evidence_quote、rationale、suggestion、kb_grounded、kb_refs
  字段缺失或格式不符 → 该条丢弃并记入 model_runs.parse_warnings

步骤 2 分桶（规则键）
  桶键 = (case_id, dimension, step_bucket)
  step_bucket：以该 issue 的 step_index 为基准，±1 步的 issue 落入同一候选桶
  （step_index 为 null 的问题单独成"用例级"桶）

步骤 3 向量召回
  桶内两两计算 (rationale + evidence_quote) 的余弦相似度
  ≥ 0.86      → 高相似，进入 rerank 判定
  0.70–0.86   → 疑似重复，必须交 rerank 判定
  < 0.70      → 不同问题，各自保留

步骤 4 Reranker 判定 + 三重一致性
  对候选对判断"是否表达同一缺陷 / 同一根因"，而不是只看相似度
  必须同时满足：Claim 一致、Evidence 指向同一规则/约束、Root Cause 一致
  三者任一不满足 → 不合并，保留独立候选
  判定为同一且证据一致 → 合并
  判定不一致或分数接近阈值 → 不合并，必要时标 disputed

步骤 5 合并（产出候选清单）
  severity      = 三方取最高
  category      = 取出现次数最多者（并列取主审）
  proposed_by   = 合并去重
  evidence      = 保留最完整的一条原文引用
  kb_grounded   = 任一方有知识库依据即为 true，kb_refs 合并去重
  留痕          = merged_from（被合并的原始问题）+ fusion_basis（分桶/余弦/rerank 分数）
  标准化        = 生成中性候选描述（不携带提出者、不携带原始论证）
  → 输出候选问题清单 C-001…（写入 review_candidates）；投票状态与计数在 stage=vote 完成

步骤 6 对立检测
  同一桶内出现"该步骤有问题"与"该步骤无问题"的明确对立 → disputed
  disputed 候选仍需投票，但直接进人工复核清单，不参与结论判定
```

> 0.86 / 0.70 是初始经验值，必须用"重复 / 非重复"标注数据校准后写入配置。不能把经验阈值直接当生产规则。

### 6.3 计数与置信度

必须分开记录：

- `support_count`、`reject_count`、`not_assessed_count`、`uncertain_count`
- `support_ratio`（支持数 / 参与模型数）
- `confidence`：**仅在黄金集校准后写入**，并记录 `confidence_source=calibrated`

**全局参与数 ≠ 每条候选的有效票数**：`review_completeness` 记录整体 3/3、2/3；每条候选另记 `vote_completeness`（如 "2/3"）与 `vote_valid_count`。某候选只有 1 份有效票时，不得按全局 3/3 处理。

模型数量、能力、维度分工和历史表现都会影响可信度，因此不做"1 方 0.6 / 2 方 0.85 / 3 方 0.95"这类硬映射。未校准阶段报告直接展示计数与 `support_ratio`，`confidence=null` 并标 `confidence_source=uncalibrated`，不伪造数值。

## 7. 结论判定（AI 结论与人工决定分离）

> 完整判定表见 `docs/12-评审决策真值表.md`；本节只列摘要。所有分支由 `verdict.py` 执行，API/Worker/渲染不得各自实现。

### 7.1 AI 结论

系统只输出三档 `ai_verdict`，**永不输出 `approved`**：

| AI 结论 | 条件 |
|---|---|
| **打回** `blocked` | 存在任一 `blocker` 级问题，且未被 ≥2 个参与模型明确 `reject` |
| **打回（待裁决）** `blocked` | 主审驳回了陪审提出的 `blocker`，但两陪审均未同意驳回 → 仍判打回，标注"待人工裁决" |
| **待人工裁决** `need_human` | 无 `blocker`，但存在 `disputed` / `severity_disputed`；或某候选有效票 <2 |
| **有条件通过** `conditional` | 无 `blocker`、无 `disputed`，可存在 `major` / `suggestion` |

> 可用模型仅 1/3 时 `ai_verdict=null`（未形成正式 AI 结论），见 §8.1。

补充规则：

- "否决"只统计明确 `reject`；`not_assessed` 与 `uncertain` 不计入否决票。
- 主审新增的 `blocker` 若两陪审均未提及 → 结论仍为打回，同时进人工复核清单（防主审幻觉误毙）。
- 三份意见结论一致但理由互相矛盾 → 结论不变，矛盾进"存疑项"。
- `ai_verdict` 由服务端 `verdict.py` 计算，模型输出只作对照；写入后不可变。

### 7.1.1 成立性与严重级分开计算

- **成立性**：3 方时 ≥2 明确 `accept` 且 <2 `reject` → accepted；≥2 `reject` → rejected；其余 → disputed。2 方时需 **2 票一致**，1-1 为 disputed，1 accept + 1 not_assessed 为 insufficient（转人工）。完整表见 `docs/12`。
- **严重级**：只在 `validity=accept` 的票中统计，取最高级别为终值；若最高与最低相差 ≥2 级（`blocker` vs `suggestion`）→ `severity_disputed`，转人工。
- **blocker 成立条件**：validity accepted（3 方需 ≥2 accept，2 方需 2 accept）+ severity=blocker + 无 ≥2 明确 reject，三者同时满足；证据状态不得为 `conflicted`/`insufficient`/`ungrounded`。
- 主审把陪审提出的 blocker 降级 → 服务端强制进人工复核，模型不能取消。
- 严重级调整保留原始 `issue_votes.severity` 与调整理由；最终值不覆盖投票记录。

### 7.1.2 仲裁与真值表边界

- 主审输出是**结构化仲裁意见**，服务端做 Schema/权限/真值表校验；自然语言不能绕过规则。
- 主审可解释、可驳回、可补充，但**不能修改原始投票**；最终 `ai_verdict` 仍由 `verdict.py` 计算。
- 主审驳回两名陪审都接受的 `blocker` → 结论仍为 `blocked`，并强制进人工复核。
- 主审新增 `blocker` → 无论陪审是否提及，都进人工复核；不强制二次投票，但报告标注 `source=chief_supplement`。
- 主审把 `blocker` 降为 `major` → 强制人工复核，保留原严重级与理由。
- 主审调整证据引用 → 必须重新计算 claim 级 `evidence_status`；不能直接改 `kb_refs` 后沿用旧状态。
- 仲裁失败 → `ai_verdict=need_human`，不允许仅凭陪审结果生成正式 `blocked/conditional`。

**条件仲裁**：服务端先算分歧；无 `disputed`/`severity_disputed`/证据冲突/补充意图时，可跳过主审仲裁并记 `arbitration_required=false`，直接进入 `verdict.py`。

### 7.2 人工决定

`ai_verdict` 不因人工操作而改变。审批通过 `review_decisions` 追加记录，派生 `human_status`：

| 人工状态 | 产生方式 |
|---|---|
| `pending` | 初始；尚未有任何决定 |
| `approved` | `decision=approve` |
| `rejected` | `decision=reject` |
| `changes_requested` | `decision=request_changes` |

- 决定 append-only，只 INSERT；当前有效决定取 `decision_no` 最大的一条，不修改历史记录。
- 只有 `approver` 可 `approve` / `reject`；`reviewer` 只能 `request_changes`。
- 人工批准不把报告改写为"用例通过"，也不消除降级标记。
- 详细规则见 `docs/09`。

## 8. 降级与失败矩阵

失败必须显式：任何降级都写 `degraded_reasons`，任何未评估都写 `not_assessed`，不允许"看起来完整"的报告。

### 8.1 可用模型数

> 2/3 的完整判定（候选级与报告级）以 `docs/12` 为准；本节只列摘要。

| 可用模型 | 行为 | 结论 |
|---|---|---|
| 3/3 | 正常执行完整流程 | 正式 AI 结论 |
| 2/3 | 允许降级执行；候选成立需 2 票一致；`review_completeness` 标"不完整" | 正式 AI 结论，但标"2/3 参与"；blocker 必须进人工复核 |
| 1/3 | 不生成正式 AI 结论；`ai_verdict=null` | 无正式结论，转人工/失败 |
| 0/3 | 任务失败 | `failed` |

主审失败时**不得**由陪审模型替代主审仲裁；只能按上表降级或失败。

### 8.2 环节故障矩阵

| 故障 | 行为 | 能否出正式完整结论 |
|---|---|---|
| 主审盲评失败 | 重试 2 次；仍失败 → **任务失败**（`failed`），保留已完成的调用 | 否 |
| 主审仲裁失败 | 重试 2 次；仍失败 → **任务失败**，保留三份盲评与投票；若配置允许降级，则 `ai_verdict=need_human` + `completed_with_warnings`，禁止给 `blocked/conditional` | 否 |
| 陪审甲或乙失败 | 重试 1 次；仍失败 → 继续评审，`participants` 记 2 个，报告标注"仅 2 模型参与" | 仅降级结果 |
| 投票轮部分失败 | 缺失的候选补 `not_assessed`，报告标注"投票不完整"，结论按实际票计算 | 仅降级结果 |
| 投票轮全部失败 | 所有候选投票记 `not_assessed`，**不伪造投票**；`ai_verdict=need_human`（除非配置明确允许按盲评意见降级），标注"未获得独立投票" | 仅人工复核 |
| 三模型全部失败 | 任务失败 + 告警（`failed`） | 否 |
| Embedding 服务失败 | 退化为关键词检索（trigram + 精确匹配），`degraded_reasons += "vector_unavailable"` | 可出降级报告，必须标注 |
| Reranker 失败/超时 | 保留 RRF 排序，`degraded_reasons += "rerank_skipped"`，降低结论置信度展示 | 可出降级报告，必须标注 |
| 知识库未命中模块 | 降级评审，顶部提示；业务规则类问题标为推断 | 可出降级报告 |
| 知识库不可用 | 不得声称"知识库证实"；只做通用准则评审 | 仅降级结果 |
| `raw_text` 无法结构化 | 降级为整篇评审，`step_index=null` | 可出降级报告 |
| 缺少 `test_scope` | 只做单条用例局部评审；禁止功能点覆盖结论 | 可出报告，限制结论 |
| 缺少 `automation_context` | 禁止断言"无法自动化"，降级为"待确认" | 可出报告，限制结论 |
| 输出校验失败 | 重试 1 次；仍失败按对应角色失败处理，不修补使用 | 视角色而定 |
| 排队超限 | 返回 429 + `Retry-After`；不静默丢弃 | 否 |
| 预算不足（无法覆盖投票） | 不跳过投票；受影响候选标 `need_human`，状态 `completed_with_warnings`，报告标注预算不足 | 仅降级结果，不出正式完整结论 |

状态语义：

- `queued` / `processing` / `retrying`：未完成；
- `done`：完整完成；
- `completed_with_warnings`：完成但有降级或未评估项，必须展示明细；
- `failed`：无法形成可用结论。

`completed_with_warnings` 的报告可由人工批准，但批准不改变降级标记（见 `docs/09` §7）。

## 9. 并发、任务可靠性与幂等

### 9.1 任务队列：PostgreSQL 持久化

`asyncio.Queue` 只存在进程内存，服务重启即丢任务。v1 规模（日 ≤ 200、单批 ≤ 50）不需要 Redis，直接用 PostgreSQL 当队列：

1. `POST /v1/reviews` 写入 `review_jobs(status=queued)` 后立即返回，不依赖进程内队列。
2. Worker 用 `SELECT ... FOR UPDATE SKIP LOCKED` 领取 `queued` / `retrying` 或租约过期的任务。
3. 领取时写 `locked_by`、`locked_at`、`lease_expires_at`（默认 5 分钟，每 60s 续租），`attempt_count += 1`。
4. 执行评审，按 stage 推进状态，每个阶段写 `review_stages` Checkpoint。
5. 成功置 `done` / `completed_with_warnings`；失败按退避重试，超过 `max_attempts`（默认 3）置 `failed` 并记 `last_error`。
6. Worker 崩溃 → 租约过期后由其他 Worker 重新领取，并从最后成功的 Checkpoint 继续。

### 9.2 超时与并发

单机 Worker 数默认 4（`WORKER_CONCURRENCY`），每个任务内三路模型调用仍并行。超时分四层：

| 层 | 默认 |
|---|---|
| 单次模型调用 | 120s（embedding 30s、rerank 20s） |
| 阶段 | 预处理 60s、KB 检索 60s、盲评 240s、融合 30s、投票 180s、仲裁 180s、verdict 15s、渲染 30s |
| DB 事务 | 10s（单次写入事务上限） |
| 任务总超时 | 20 分钟（795s 阶段 + 10s DB + 重试余量，不含排队） |
| Worker 租约 | 5 分钟，租约 < 任务超时，便于崩溃恢复 |

阶段与恢复细节见 `docs/13-任务状态与恢复机制.md`。

### 9.3 幂等与代次

**幂等键**不是单一 `input_hash`，而是"输入 + 会影响结论的版本"的组合：

```
input_hash       = sha256(规范化 case + test_scope + automation_context + 影响结论的 options)
idempotency_key  = sha256(input_hash + kb_version + rubric_version + prompt_version_hash
                          + embedding_profile_id + retrieval_config_version + model_config_version)
```

- 同一 `idempotency_key` 且 `superseded_by IS NULL` → 返回已有报告（部分唯一索引保证同一时刻只有一个 active）。
- `force=true` → 事务内把旧记录 `superseded_by` 指向新记录，插入 `generation+1` 且 `parent_review_id=旧记录` 的新记录；历史报告不覆盖。
- **版本在创建时冻结**：`kb_version`、`rubric_version`、`prompt_versions`、`model_config_version`、`retrieval_config_version`、`embedding_profile_id`、`reranker_profile_id`、`report_schema_version` 全部写入 `review_jobs`；恢复任务不得切换（见 `docs/22`）。
- 可空字段（`test_scope`、`automation_context`）在计算哈希前必须规范化：显式 `null` 与"未提供"统一为同一值，避免 `NULL` 参与唯一约束导致幂等失效。

**同一任务被重复领取或重试时，不得产生两份互相冲突的终稿**：终稿写入前校验 `status`、`attempt` 与 `generation`，已存在终稿则丢弃本次结果并记日志。

### 9.4 批量

批量任务内部逐份独立入队，部分失败不影响整体；批次汇总给出成功/失败/未完成计数。

## 10. 版本与可追溯

报告头部固定记录：

```
kb_version              = 知识库内容哈希（active 版本）
rubric_version          = rubric 文件哈希
prompt_version          = 各 prompt 文件哈希（按角色分别记录）
retrieval_config_version= 检索参数哈希（Top-K、RRF k、rerank 阈值、查询上限）
embedding_profile       = provider / model / version / dimension / normalize
model_config_version    = models.yaml 配置版本（provider/base_url/model_id/timeout/限流/pricing）
report_schema_version   = 报告 JSON 结构版本（历史报告按原版本读取）
generation              = 同一幂等键下的第几次评审（强制重跑递增）
```

任何一次"为什么这次评审结论变了"都可以通过这些版本号定位到差异来源。

## 11. 安全与合规

- 三厂商云 API 已确认允许调用；用例内容按公司要求记录调用日志（调用方、时间、模型、token）。
- API Key 鉴权，`X-Caller-Id` 记录调用方。
- 原始 prompt / 输出全量存档于 `model_runs`，仅服务内部可读；对外接口不返回原始 prompt。

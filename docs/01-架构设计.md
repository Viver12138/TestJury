# 01 · 架构设计

> 版本：v0.2（并入评审修订，见 [08-评审修订与实施计划](08-评审修订与实施计划.md)）

## 1. 系统边界

```
调用方（测试流水线 / 人工上传）
        │  HTTP + API Key
        ▼
┌──────────────────────────────────────────────┐
│              评审团服务 (FastAPI)              │
│                                              │
│  接收 → 规范化 → 检索（Hybrid） → 三方盲评     │
│       → 投票融合 → 主审仲裁 → 渲染 → 落库      │
│                                              │
└───────┬───────────────┬──────────────┬───────┘
        │               │              │
        ▼               ▼              ▼
   qwen-max       deepseek-flash   kimi-k3
   （主审）          （陪审甲）       （陪审乙）
        │
        ▼
   PostgreSQL + pgvector
   （任务队列 / 报告 / 问题 / 投票 / 原始调用存档 / 知识库 / 缺口）
```

服务自身**不含任何执行测试的能力**，只做静态评审。评审模型与 embedding 走 OpenAI 兼容协议；rerank 允许独立协议（DashScope / 本地），由模型适配层按配置切换。

## 2. 组件划分

| 组件 | 职责 |
|---|---|
| API 层 | 请求校验、鉴权、创建任务、查询结果、接收复核回写 |
| 任务队列 | PostgreSQL 持久化队列 + Worker 领取（租约、重试），并发由 Worker 数量控制 |
| 用例规范化 | 结构化用例校验；`raw_text` 走预处理模型拆分步骤 |
| 检索查询构建 | 把用例拆成标题/目的/前置/步骤/预期/数据多类查询，附结构化过滤条件 |
| 混合检索 | 结构化过滤 → FTS → 向量检索 → RRF 融合 → Reranker 精排 → 证据包 |
| 盲评执行 | 三模型并行调用，互不可见 |
| 问题融合 | 候选问题对齐、分层去重合并 |
| 投票轮 | 三模型对候选问题逐条表态，写入 `issue_votes` |
| 主审仲裁 | 主审第三次调用：逐条确认/驳回/补充，产出终稿问题清单与结论 |
| 报告渲染 | JSON 落库 + Markdown 模板渲染 |
| 模型适配层 | OpenAI 兼容调用、超时/重试、token 计量、原始请求响应存档 |
| 知识库子系统 | 文档加载、按类型切片、索引构建、检索、缺口聚合 |
| 复核回写 | 记录人工对每条问题的裁决，供黄金集与调优使用 |

## 3. 主流程

```
1. POST /v1/reviews
   └─ 校验请求（case + test_scope + automation_context）→ 计算 input_hash → 幂等检查
      ├─ 已存在相同 hash 且未 force → 直接返回旧报告
      └─ 写入 review_jobs（status=queued）→ 返回 review_id

2. Worker 领取任务（租约、attempt_count++）
   status=processing, stage=preprocess
   ├─ 结构化用例：直接通过
   └─ raw_text：调用预处理模型拆成 steps 数组
      └─ 拆分失败 → 标记 degraded_reason=raw_text_unparsed，steps=null

   stage=kb_retrieve
   ├─ 查询构建：标题 / 目的 / 前置 / 每步 action / 每步 expected / 测试数据
   ├─ 结构化过滤（module + function_point + doc_type + kb_version）
   ├─ FTS 召回 + 向量召回 → RRF 融合 → Reranker 精排
   ├─ 组装证据包（≤15k token，Top K 默认 8–12，每条带溯源）
   │    内容：业务规则（RULE-ID）、功能说明、术语、已知限制、相关历史缺陷
   └─ 模块未命中 → degraded=true，只注入通用测试设计准则

   stage=blind_review  （三路并行，各自独立上下文，互不可见）
   ├─ 主审盲评  qwen-max       → 全维度评审
   ├─ 陪审甲    deepseek-flash → 业务/需求视角为主
   └─ 陪审乙    kimi-k3        → 测试设计 + 自动化可行性为主
   每路输出：结构化 issues[] + summary

   stage=fusion
   ├─ 规则键分桶：(case_id, dimension, step_index±1)
   ├─ 桶内 embedding 召回"疑似重复"（0.70–0.86）
   ├─ Reranker 判定是否同一缺陷/同一根因
   ├─ 高确定性才合并；边界保留独立条目
   └─ 同一位置"有问题 vs 没问题"的明确对立 → disputed

   stage=vote  （三路并行，互不可见）
   ├─ 每个模型拿到：用例 + 候选问题清单 + 自己的盲评输出
   ├─ 逐条表态：accept / reject / uncertain / not_assessed
   └─ 缺失条目补 not_assessed，写入 issue_votes

   stage=arbitration  （主审第三次独立调用）
   输入：规范化用例 + test_scope + automation_context + 证据包 + 三份原始意见 + 候选问题与投票
   输出：
   ├─ 终稿 issues[]（adopted / rejected / disputed / need_human）
   ├─ 驳回理由（每条被驳回的陪审意见必填）
   ├─ 主审补充问题（标记 source=chief_supplement）
   └─ verdict + 摘要 + 知识库缺口候选

   stage=render
   ├─ 结论判定（见 §7）
   ├─ JSON 落库、Markdown 渲染
   └─ status=done
```

## 4. 盲评约束（防污染）

1. **三路调用并发发起，互不读取对方结果**；主审在盲评阶段的上下文里不出现"还有两个陪审"的暗示，避免它揣测他人意见。
2. **三路使用同一份用例、同一份 `test_scope` / `automation_context` 和同一份证据包**，差异只来自角色 rubric 与模型本身。
3. **主审的三份输出（盲评 / 投票 / 仲裁）分别落 `model_runs`**，prompt 与输出完整存档，事后可复盘。
4. 仲裁时主审能看到自己那份盲评结果（它本来就在三份里），但对三方**一视同仁处理**；投票轮三路同样互不可见，避免相互锚定。

## 5. 知识检索与证据链路（Hybrid Retrieval）

检索质量决定评审质量：召回不足或召回错误，模型再强也只能在错误证据上判断。因此不使用"整份用例一次向量检索"的做法，而是**多查询 → 混合召回 → 融合 → 精排 → 证据包**五步。

### 5.1 多查询构建

把一份用例拆成多类检索查询，分别召回证据：

| 查询来源 | 主要用途 |
|---|---|
| 用例标题 / 功能点 | 定位模块与规则范围 |
| 测试目的 / 业务描述 | 召回功能说明与业务流程 |
| 前置条件 | 召回权限、状态、数据约束 |
| 每个步骤的 `action` | 召回流程规则与操作限制 |
| 每个步骤的 `expected` | 召回判定标准与业务规则（信息密度最高） |
| 测试数据 / 字段 / 枚举 / 边界值 | 精确召回数值、上限、错误码 |

原因：标题常缺少具体规则，前置条件对应权限/状态约束，步骤对应流程，预期结果承载最重要的业务规则，测试数据需要精确匹配。

每个查询携带 `module`、`function_point`、`doc_type`、`kb_version` 过滤条件；查询数默认上限 12，超出时按 **预期结果 > 步骤 > 前置条件 > 标题** 的优先级截断。

### 5.2 召回与融合

1. **结构化过滤**：先用元数据把候选限定在本模块、本功能点、当前 `kb_version`，避免跨模块、跨版本召回。
2. **关键词检索**：PostgreSQL Full Text Search，中文分词需 zhparser / pg_jieba（或以 n-gram + 规则编号/字段名/错误码/数值的精确匹配兜底）。负责精确词项。
3. **向量检索**：pgvector 余弦距离，负责同义表达、自然语言描述、语义相近规则。
4. **RRF 融合**：`score = Σ 1/(k + rank_i)`，`k` 默认 60；不对未校准的检索分数做线性相加。
5. **Reranker 精排**：RRF 后 Top 40 与查询一起交给 reranker，按业务相关性重排。
6. **证据包组装**：取精排 Top 8–12，按 15k token 预算装载；同一知识只保留最高排名的一条。

> 向量相似不等于业务相关：功能名相似但角色不同、规则描述相似但场景不同、字段名相似但含义不同——这些都交给 reranker 判断，而不是靠距离阈值。

多查询时按查询分别做检索与 RRF，再跨查询归并：同一知识取最高 rerank 分数，最后统一排序进入证据包。不能把多个查询的原始分数直接相加。

### 5.3 证据必须可溯源

每条进入上下文的知识至少携带：

- 知识条目 ID（`chunk_id` / `rule_id`）与原始文档 ID；
- `source_ref`（文档名 + 章节/行号）与 `heading_path`；
- `doc_type`（规则 / 功能说明 / 已知限制 / 历史缺陷 / 术语）；
- `module`、`function_point`、`kb_version`；
- 检索通道（fts / vector / rule_direct）、融合排名、reranker 分数；
- 原文内容。

评审结论的 `kb_refs` 指向具体知识条目，报告附录给出"知识 → 原文位置"映射。**不允许只输出"知识库认为不符合"**。

### 5.4 检索降级

| 故障 | 行为 |
|---|---|
| 向量检索不可用 | 退化为"结构化过滤 + FTS"，`degraded_reasons += "vector_unavailable"` |
| FTS 不可用 | 退化为纯向量检索，`degraded_reasons += "fts_unavailable"` |
| Reranker 超时 | 直接用 RRF 排序，`degraded_reasons += "rerank_skipped"` |
| 模块未命中 | 只注入通用测试准则，业务规则类结论一律降级为推断 |
| Embedding profile 不一致 | 禁止混用；按 profile 重建索引后再检索 |

降级必须在报告顶部明示，不能让"检索残缺"看起来像"知识库确认"。

## 6. 问题融合与投票

### 6.1 投票状态：未提及 ≠ 反对

只 merge 各模型的 `issues` 列表，无法计算支持票与反对票。因此 fusion 之后单独加一轮**投票**（`stage=vote`）：每个模型拿到候选问题清单，逐条给出态度并落 `issue_votes`。

| 值 | 含义 |
|---|---|
| `accept` | 明确认为该问题成立 |
| `reject` | 明确认为该问题不成立 |
| `not_assessed` | 未评估 / 无法评估该条（不代表否定） |
| `uncertain` | 评估后表示不确定 |

`not_assessed` 不计入反对票。把"没说话"当作"反对"会造成错误的多数否决。

### 6.2 分层融合

```
步骤 1 归一化
  每条 issue 必须有：step_index（可为 null）、dimension、severity、category、
                   evidence_quote、rationale、suggestion、kb_grounded、kb_refs
  字段缺失或格式不符 → 该条丢弃并记入 model_runs.parse_warnings

步骤 2 分桶（规则键）
  桶键 = (case_id, dimension, step_bucket)
  step_bucket：以该 issue 的 step_index 为基准，±1 步的 issue 落入同一候选桶
  （step_index 为 null 的问题单独成"用例级"桶）

步骤 3 向量召回
  桶内两两计算 (rationale + evidence_quote) 的余弦相似度
  ≥ 0.86      → 高相似，进入 rerank 判定
  0.70–0.86   → 疑似重复，必须交 rerank 判定
  < 0.70      → 不同问题，各自保留

步骤 4 Reranker 判定
  对候选对判断"是否表达同一缺陷 / 同一根因"，而不是只看相似度
  判定为同一且证据一致 → 合并
  判定不一致或分数接近阈值 → 不合并，必要时标 disputed

步骤 5 合并（产出候选清单）
  severity      = 三方取最高
  category      = 取出现次数最多者（并列取主审）
  proposed_by   = 合并去重
  evidence      = 保留最完整的一条原文引用
  kb_grounded   = 任一方有知识库依据即为 true，kb_refs 合并去重
  留痕          = merged_from（被合并的原始问题）+ fusion_basis（分桶/余弦/rerank 分数）
  → 输出候选问题清单 C-001…（与 issues.issue_no 一一对应）；投票状态与计数在 stage=vote 完成

步骤 6 对立检测
  同一桶内出现"该步骤有问题"与"该步骤无问题"的明确对立 → disputed
  disputed 候选仍需投票，但直接进人工复核清单，不参与结论判定
```

> 0.86 / 0.70 是初始经验值，必须用"重复 / 非重复"标注数据校准后写入配置。不能把经验阈值直接当生产规则。

### 6.3 计数与置信度

必须分开记录：

- `support_count`、`reject_count`、`not_assessed_count`、`uncertain_count`
- `support_ratio`（支持数 / 参与模型数）
- `confidence`：**仅在黄金集校准后写入**，并记录 `confidence_source=calibrated`

模型数量、能力、维度分工和历史表现都会影响可信度，因此不做"1 方 0.6 / 2 方 0.85 / 3 方 0.95"这类硬映射。未校准阶段报告直接展示计数与 `support_ratio`，`confidence=null` 并标 `confidence_source=uncalibrated`，不伪造数值。

## 7. 结论判定

系统只输出三档，**永不输出"通过"**：

| 结论 | 条件 |
|---|---|
| **打回** `blocked` | 存在任一 `blocker` 级问题，且未被 ≥2 个参与模型明确 `reject` |
| **打回（待裁决）** `blocked` | 主审驳回了陪审提出的 `blocker`，但两陪审均未同意驳回 → 仍判打回，标注"待人工裁决" |
| **待人工裁决** `need_human` | 无 `blocker`，但存在 `disputed` 项，或参与模型不足 3 个 |
| **有条件通过** `conditional` | 无 `blocker`、无 `disputed`，可存在 `major` / `suggestion` |

补充规则：

- "否决"只统计明确 `reject`；`not_assessed` 与 `uncertain` 不计入否决票。
- 主审新增的 `blocker` 若两陪审均未提及 → 结论仍为打回，同时进人工复核清单（防主审幻觉误毙）。
- 三份意见结论一致但理由互相矛盾 → 结论不变，矛盾进"存疑项"。
- 只有人工通过复核接口把结论置为 `approved` 后，报告才显示"通过"。

## 8. 降级与失败矩阵

| 故障 | 行为 |
|---|---|
| 陪审甲或乙超时/报错 | 重试 1 次；仍失败 → 继续评审，`participants` 记 2 个，报告顶部标注"仅 2 模型参与，可信度下降" |
| 主审盲评失败 | 重试 2 次；仍失败 → **任务失败**（无法构成三方评审） |
| 主审仲裁失败 | 重试 2 次；仍失败 → **任务失败**，三份盲评结果保留可查 |
| 投票轮部分失败 | 缺失的候选补 `not_assessed`，报告标注"投票不完整"，结论按参与票计算 |
| 投票轮全部失败 | 退化为"提出即支持、未提及即 not_assessed"，报告标注"未获得独立投票" |
| 三模型全部失败 | 任务失败 + 告警 |
| 知识库未命中模块 | 降级评审，报告顶部醒目提示；业务规则类问题标记为推断 |
| 检索链路部分降级 | 按 §5.4 处理，`degraded_reasons` 记录具体通道 |
| `raw_text` 无法结构化 | 降级为整篇评审，`step_index=null`，问题定位到用例级 |
| 缺少 `test_scope` | 只能做单条用例的局部评审；禁止输出"功能点缺少某类场景"的覆盖结论 |
| 缺少 `automation_context` | 禁止断言"某步骤无法自动化"；降级为"待确认，缺少框架能力信息" |
| 排队超限 | 返回 429 + Retry-After |

## 9. 并发、任务可靠性与幂等

### 9.1 任务队列：PostgreSQL 持久化

`asyncio.Queue` 只存在进程内存，服务重启即丢任务。v1 规模（日 ≤ 200、单批 ≤ 50）不需要 Redis，直接用 PostgreSQL 当队列：

1. `POST /v1/reviews` 写入 `review_jobs(status=queued)` 后立即返回，不依赖进程内队列。
2. Worker 用 `SELECT ... FOR UPDATE SKIP LOCKED` 领取 `queued` 或租约过期的任务。
3. 领取时写 `locked_by`、`locked_at`、`lease_expires_at`（默认 10 分钟，执行中续租），`attempt_count += 1`。
4. 执行评审，按 stage 推进状态。
5. 成功置 `done`；失败按退避重试，超过 `max_attempts`（默认 3）置 `failed` 并记 `last_error`。
6. Worker 崩溃 → 租约过期后由其他 Worker 重新领取。

### 9.2 并发控制

单机 Worker 数默认 4（`WORKER_CONCURRENCY`），每个任务内三路模型调用仍并行。单次模型调用超时 120s；单任务总超时 10 分钟（超过则不再续租，任务可被重新领取）。

### 9.3 幂等

幂等键：`(case_id, input_hash, kb_version, rubric_version, prompt_version)`；命中且未 `force` 返回已有报告。`force=true` 插入新记录，旧记录保留。

**同一任务被重复领取或重试时，不得产生两份互相冲突的终稿**：终稿写入前校验 `status` 与 `attempt`，已存在终稿则丢弃本次结果并记日志。

### 9.4 批量

批量任务内部逐份独立入队，部分失败不影响整体；批次汇总给出成功/失败/未完成计数。

## 10. 版本与可追溯

报告头部固定记录：

```
kb_version              = 知识库内容哈希
rubric_version          = rubric 文件哈希
prompt_version          = 各 prompt 文件哈希（按角色分别记录）
retrieval_config_version= 检索参数哈希（Top-K、RRF k、rerank 阈值、查询上限）
embedding_profile       = provider / model / version / dimension / normalize
model_versions          = 各模型配置版本 + API 实际返回的版本（若提供）
```

任何一次"为什么这次评审结论变了"都可以通过这些版本号定位到差异来源。

## 11. 安全与合规

- 三厂商云 API 已确认允许调用；用例内容按公司要求记录调用日志（调用方、时间、模型、token）。
- API Key 鉴权，`X-Caller-Id` 记录调用方。
- 原始 prompt / 输出全量存档于 `model_runs`，仅服务内部可读；对外接口不返回原始 prompt。

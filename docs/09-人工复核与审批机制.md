# 09 · 人工复核与审批机制

> 版本：v1.12 · 2026-11-10（补充 20 落实：复核 result 与报告 decision 字段边界）
> 背景：v0.2 用 `verdict` + `human_approved_by` 同时表达 AI 结论与人工批准，无法回答"AI 最初判了什么、谁在何时改成了什么、为什么改"。本文定义两者的分离方式，以及审批状态、权限、审计与报告展示规则。
> 关联：01 §7、02 §2（`review_decisions`）、03 §5、04 §8、08 D15/D16。

---

## 1. 核心原则

| 原则 | 说明 |
|---|---|
| **AI 结论不可变** | AI 评审结果写入后只读；人工决定不能覆盖、改写或删除它 |
| **人工决定独立且追加** | 每次人工决定是一条新记录（append-only），不是字段覆盖 |
| **两种状态分开表达** | `ai_verdict`（AI 判了什么）与 `human_status`（人工处理到哪一步）互不替代 |
| **批准 ≠ 补齐** | 人工批准降级报告，不会把它改写成"所有环节均正常完成" |
| **全部可审计** | 谁、何时、基于哪一版报告、改了什么、理由是什么，全部可查 |

一句话：**AI 给结论，人给决定，两者都留痕。**

## 2. 三个状态维度

任务执行、AI 评审、人工审批是三件事，不能塞进一个 `status`：

| 维度 | 字段 | 取值 | 谁写 |
|---|---|---|---|
| 任务执行状态 | `review_jobs.status` | `queued` / `processing` / `retrying` / `done` / `failed` / `completed_with_warnings` | 服务端 worker |
| AI 评审结论 | `review_jobs.ai_verdict` | `blocked` / `conditional` / `need_human`（**永不为 `approved`**） | 服务端结论计算（`verdict.py`） |
| 人工审批状态 | `review_jobs.human_status` | `pending` / `approved` / `rejected` / `changes_requested` | 人工决定（派生自最新 `review_decisions`） |

典型组合：

| 场景 | status | ai_verdict | human_status |
|---|---|---|---|
| 评审完成，等待人工看 | `done` | `blocked` | `pending` |
| 评审完成，AI 认为有争议 | `done` | `need_human` | `pending` |
| 降级完成（部分通道失败） | `completed_with_warnings` | `conditional` | `pending` |
| 人工批准 | `done` | `blocked` | `approved` |
| 人工驳回 AI 结论 | `done` | `conditional` | `rejected` |
| 人工要求修改用例后重提 | `done` | `blocked` | `changes_requested` |

> `human_status=approved` 只表示"人批准了这份报告的结论"，不改变 `ai_verdict`，也不表示用例本身"通过验收"——业务验收结论由调用方系统自行记录。

## 3. AI 结论

- 由服务端 `verdict.py` 按 `docs/04` §8 计算，模型输出的 `ai_verdict` 只作对照。
- 取值只有 `blocked` / `conditional` / `need_human`。
- 写入后不可修改；需要重新判断只能**新建一次评审**（`generation+1`，见 `docs/01` §9.3）。
- 报告必须标注 `ai_verdict` 与计算依据（blocker 数、disputed 数、参与模型数）。

## 4. 人工决定

### 4.1 决定类型

| `decision` | 含义 | 对 `human_status` 的影响 | 是否可继续评审 |
|---|---|---|---|
| `approve` | 认可报告结论（含降级报告） | `approved` | 否，终态 |
| `reject` | 不认可报告结论 | `rejected` | 否，终态（需重新评审则新建 generation） |
| `request_changes` | 要求补充/修改用例或说明后重提 | `changes_requested` | 是，重新提交为新评审 |

> 注意：`reject` 否决的是"这份报告"，不是"这条用例一定没问题"。报告被驳回后，用例是否合格仍由业务方决定。

### 4.2 记录结构

`review_decisions`（详见 `docs/02` §2）：

| 字段 | 说明 |
|---|---|
| `review_id` | 关联评审 |
| `decision_no` | 全局递增序号，用于确定当前有效决定 |
| `decision` | `approve` / `reject` / `request_changes` |
| `reviewer_id` | 做出决定的人（服务端身份） |
| `reason` | 理由；`reject` 与 `request_changes` 必填 |
| `previous_verdict` | 决定前的 `ai_verdict`（快照，防止后续变化导致历史失真） |
| `report_schema_version` | 决定针对的报告结构版本 |
| `created_at` | 决定时间 |

### 4.3 追加而非覆盖

```
第 1 次：request_changes（要求补步骤）
第 2 次：approve（补充后认可）
```

两次都保留；`human_status` 取 `decision_no` 最大的一条；**禁止 UPDATE 或 DELETE 历史决定**：`review_decisions` 对应用账号只授予 INSERT/SELECT，不使用 `superseded_by` 指针（更新指针本身就违反 append-only）。`review_jobs.human_status` 由服务在同一事务内更新，供列表与展示使用。

## 5. 审批状态机

```
                 ┌──────────── request_changes ────────────┐
                 ▼                                          │
pending ── approve ──▶ approved（终态）                    │
   │                                                        │
   ├──── reject ─────▶ rejected（终态）                     │
   │                                                        │
   └──── request_changes ──▶ changes_requested ─────────────┘
                                   │
                                   └─ 用例修改后重新提交 → 新 generation，human_status=pending
```

规则：

1. `approved` / `rejected` 是终态；要改判必须新建一次评审，不能直接覆盖。
2. `changes_requested` 不是终态：允许后续 `approve` / `reject`。
3. 同一 `review_id` 的并发决定用乐观锁（`expected_updated_at` 或最后一条 `decision_no`）保护，冲突返回 409。
4. 新建评审（新 generation）不继承旧 `human_status`，但必须继承历史链（见 §5.1）。

### 5.1 审批与重新评审

- 新 generation 通过 `parent_review_id` 指向原评审，形成"同一用例评审历史链"。
- **`case_version` 与 `generation` 分开**：用例内容修改 → `case_version+1`；同一输入强制重跑 → `generation+1`。报告始终关联当时的 `case_version`。
- 旧报告、旧审批记录不被覆盖；新报告有自己的 `ai_verdict` 与 `human_status`。
- 可以查询同一 `case_id` 的所有 generation 及其审批结果。
- **是否继承旧报告的人工反馈**（`human_feedback`）由配置决定：默认不自动继承；若继承，必须在报告中标注"沿用自 generation N"，且不得伪装成本次评审的结论。
- 审批人判断"是否沿用旧结论"时，报告必须并列展示历史结论与本次结论。

### 5.2 业务审批边界与外部流程

对应业务基线 `BIZ-010`/`BIZ-011`/`BIZ-012`（`docs/00` §8）：

- **AI 评审结论**是机器判断（`ai_verdict`），不是审批结果；`approved` 只能出现在人工决定与 `human_status`，且不得渲染成"用例通过"。
- **人工复核**（issue 级 `human_review_tasks`）回答"这条问题是否成立"；**最终业务审批**（report 级 `review_decisions` 或调用方流程）回答"这条用例是否被业务接受"。两者不能合并为一个字段。
- TestJury **可以记录**最终业务审批（`review_decisions`），但**不默认拥有**外部系统的放行权；调用方也可以选择在自己的系统中完成审批，只把结果回传或完全不回传。
- 如果调用方用评审结果做流程门禁，门禁策略、责任和异常处理由调用方定义；TestJury 只提供结构化结果，不自动推进、不自动阻断外部流程。
- 新 generation 产生后，旧的人工审批自动失效（§12.5），但旧记录保留；不因外部系统状态变化改写 TestJury 的历史审批。

## 6. 角色与权限

> 全局角色与权限矩阵见 `docs/17` §5；本节只列审批相关约束。

| 角色 | 权限 |
|---|---|
| `reviewer`（测试/业务评审人） | 查看报告、提交 issue 级反馈（`adopted`/`rejected`/`missed`）、`request_changes` |
| `approver`（负责人） | 上述权限 + `approve` / `reject` |
| `admin` | 管理知识库发布、模型配置；**不自动获得审批权** |

约束：

- **角色由服务端根据 API Key 查授权表得出**；客户端传入的 `X-Role` 不作为授权依据，不能通过改请求头提升权限。
- 一个调用方可以绑定多个角色，但角色必须由服务端授予并审计。
- **`submitter_id` 必须是可信身份**：来自 API Key 绑定、可信网关注入或内部认证，不能取 `X-Caller-Id`（它通常代表系统/团队，不是具体人）。
- 正式审批必须由 `submitter_id != reviewer_id` 的人员执行；开发/测试环境可通过配置放宽，但服务端仍按可信身份判断。
- 所有决定记录 `reviewer_id`（服务端身份），不接受匿名审批。
- 审批历史可见性：`reviewer` 可看自己提交的评审；`approver`/`admin` 可看全部；导出审批历史仅 `admin`。

### 6.1 API Key 与个人身份

| 项 | 系统调用 | 人工审批 |
|---|---|---|
| 凭据 | 系统 API Key 或 OIDC client credentials | 个人 OIDC/SSO；禁止共享 Key |
| 身份字段 | `client_id`，`actor_type=service` | 稳定 `actor_id`（IdP subject），`actor_type=human` |
| 权限范围 | 仅提交/查询等 scope，不含审批 | `reviewer`/`approver` 角色，服务端授予 |
| 轮换 | 按周期轮换，旧 Key 宽限期后失效 | 由 IdP 会话/令牌管理，不在 TestJury 存密码 |
| 撤销/离职 | Key 立即失效 | IdP 禁用后令牌 ≤5 分钟失效；未完成任务转派，历史记录保留 |
| 代操作 | 不允许 | v1 不允许；如未来支持，必须记录 `actor_id` + `on_behalf_of` + 理由 |
| 审计 | 记录 client_id + request_id | 记录 actor_id + 认证来源 + 时间 + request_id |

补充规则：

- **系统 Key 不能用于审批**：审批接口要求 `actor_type=human`，系统身份调用返回 403。
- API Key 创建、轮换、撤销必须记录绑定人/系统、角色、有效期与操作人；多人共用 Key 视为审计缺陷。
- 人员离职或权限变更时，先撤销身份，再转派未完成复核任务；已提交结论不追溯改写（§12.6）。
- `submitter_id` 与 `approver actor_id` 都来自服务端可信身份，不取客户端头；分离校验基于真实个人身份。
- 审计只保留最小身份字段，导出需授权（`docs/10` §11.2）。

> 如果审批人无法唯一确定，"谁批准了这份报告"就无法回答，审批记录失去意义。

## 7. 降级报告的审批

允许人工批准降级报告，但报告必须同时展示：

- 哪些环节失败/降级（`degraded_reasons`）；
- 哪些维度 `not_assessed`（如投票缺失导致某维度无票）；
- 使用了什么降级策略（关键词检索替代向量、跳过 rerank 等）；
- 哪些结论缺少证据或仲裁。

批准动作只写 `human_status=approved`，**不得**修改 `degraded`、`degraded_reasons`、`ai_verdict`。展示层必须并列显示"人工已批准"与"评审存在降级"。

## 8. 与 issue 级反馈的关系

| 机制 | 回答的问题 | 数据表 | 用途 |
|---|---|---|---|
| `review_decisions` | 这份报告的结论是否被接受 | `review_decisions` | 业务审批、审计 |
| `human_feedback` | 每条 issue 是真问题还是误报、有没有漏检 | `human_feedback` | 评测集、指标、调优 |

两者独立：报告被 `approve` 不代表每条 issue 都被采纳；`feedback` 判 `rejected` 也不改变报告结论。报告中必须分别展示"报告级决定"和"issue 级复核"。

## 9. 接口与审计

### 9.1 接口

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/v1/reviews/{review_id}/decisions` | 新增人工决定（只 INSERT） |
| GET | `/v1/reviews/{review_id}/decisions` | 审批历史（按 `decision_no` 正序） |

请求示例：

```json
{ "decision": "request_changes", "reason": "第 3 步预期不明确，补充后重提" }
```

> `reviewer` 不取请求体或 `X-Role`，由服务端按 API Key 身份写入；请求体只能表达决定与理由。

响应返回新记录与派生后的 `human_status`。

### 9.2 审计事件

以下操作写审计日志（`audit_log`，见 `docs/10`）：

- 新增人工决定；
- 修改 issue 级反馈；
- 强制重跑（`force=true`）；
- 知识库发布/回滚；
- 模型配置、Prompt、Rubric 变更；
- 权限变更。

审计日志只追加，保留不少于 1 年（按公司合规要求调整）。

## 10. 报告展示

报告头部固定两块，不可合并：

```
【AI 评审结论】 blocked（blocker 2 项，参与模型 3/3）
【人工审批状态】 pending（尚无人工决定）
【降级情况】 无 / 或列出 degraded_reasons 与未评估维度
```

人工决定后：

```
【AI 评审结论】 blocked
【人工审批状态】 approved · zhangsan · 2026-11-10 14:20
【人工理由】 已确认阻断项，用例需返工
【审批历史】 request_changes（李四，11-10 10:05）→ approve（张三，11-10 14:20）
```

禁止把 `approved` 渲染成"用例通过"；文案固定为"人工已批准本报告"。

## 11. 数据一致性要求

- `ai_verdict` 与 `report_json` 同事务写入，报告生成后不可变。
- `human_status` 与 `review_decisions` 同事务更新；以最新决定为准，可由决定表重算校验。
- `previous_verdict` 是快照，不随 `ai_verdict` 后续变化。
- 删除评审任务时，`review_decisions` 随 `ON DELETE CASCADE` 删除，但审计日志保留最小字段（review_id、decision、reviewer、时间）。
- 报告重渲染使用 `report_schema_version` 对应模板，不按最新模板强转历史报告。

### 11.1 报告修正、归档与合规删除

报告不可变不等于永久不可删除。三种操作分开：

| 操作 | 行为 | 审计 |
|---|---|---|
| 报告修正 | 新建 generation，旧报告保留；记录修正原因 | `audit_log` |
| 业务归档 | 保留报告与审批，限制访问；不删除数据 | `audit_log` |
| 合规删除 | 按保留策略删除或匿名化，处理模型原始记录、备份与关联数据；审批中任务先冻结 | 记录删除范围、审批人、时间；审计最小字段保留 |

合规删除需 `admin` 发起 + 审批人确认；不能由普通 reviewer 执行。删除后不得用备份恢复把数据重新带回生产查询。

## 12. 人工复核 SLA

`need_human` 只是状态，不是流程。v1 至少定义边界（不实现复杂通知系统）：

| 项 | 建议 |
|---|---|
| 责任人 | 按模块指定 `approver`；无指定时进公共队列 |
| 优先级 | blocker / severity_disputed / 证据冲突 > 其它 |
| 处理时限 | 建议 2 个工作日（内部约定，可配置） |
| 超时提醒 | 每日汇总一次未处理清单；不做实时告警 |
| 回写方式 | 通过 `review_decisions` 追加，不直接改报告 |
| 长期未处理 | 报告保持 `pending`，不影响 AI 结论；列表按停留时长排序 |

> v1 不做通知系统与自动升级，但必须能按"停留时长 + 优先级"筛出待处理项。

### 12.1 复核队列最小字段（v1）

> v1 使用独立 `human_review_tasks` 表承载工作项；报告中的 `human_review_items` 只读，二者区别见 §12.3。

| 字段 | 说明 |
|---|---|
| `review_id` / `issue_no` | 定位 |
| `priority` | `blocker` / `severity_disputed` / `evidence_conflict` / 普通 |
| `assignee` | 按模块负责人分配，可为空（公共队列） |
| `status` | `pending` / `in_progress` / `completed` / `cancelled` |
| `received_at` / `due_at` | 进入时间与时限 |
| `result` / `reason` | 复核结果与理由（reject/修改必填）；`result` 仅用于 issue 级复核 |
| `decision` | 仅用于报告级 `review_decisions`（approve/reject/request_changes），不得与 issue 级 `result` 混用 |
| `handled_at` | 处理时间 |

v1 先实现队列、优先级、处理人、状态、耗时与结论；复杂 SLA、自动分派、通知后续再加。

### 12.2 复核两级与生命周期

| 层级 | 对象 | 人工结论 |
|---|---|---|
| Issue 级 | 单条问题 | `confirmed`（成立）/ `rejected`（误报）/ `modified`（修正）/ `insufficient_information`（信息不足）/ `escalated`（升级） |
| Report 级 | 整份报告 | `approve` / `reject` / `request_changes` |

任务状态：`pending → in_progress → completed`，可 `cancelled`；`completed` 可 `reopen` 回到 `in_progress`。

- `completed` 必须有 `result`；`cancelled` 可保留部分结果但不产生最终结论。
- `reopen` 不删除旧结果，追加事件；新结论成为当前结果，历史保留。
- 每次状态迁移/结果提交必须写 `human_review_events`，并用 `version` 做乐观并发（冲突返回 409）。

规则：

- 允许转派；`assignee` 变更写审计。
- 复核中的报告允许新建 generation；旧任务标记 `superseded`，新任务重新创建，不自动继承旧结论。
- 已完成的复核可重新打开，追加事件，不覆盖原结论。
- 同一 Issue 可多人复核；最终结论取最新有效事件，历史全部保留。
- 每次操作（分配/转派/开始/结论/重开/取消）写 `human_review_events`。
- 人工结论与 AI 结论分开存储；人工修改不覆盖 `ai_verdict`。

**字段边界（P1-03）**：Issue 级复核统一使用 `human_review_tasks.result` + `reason`（`confirmed`/`rejected`/`modified`/`insufficient_information`/`escalated`）；Report 级审批只使用 `review_decisions.decision`（`approve`/`reject`/`request_changes`）。`human_review_events` 记录事件类型与 `result`，不得复用 `decision`；API 与 DB 映射见 `docs/17` §5.1、§7。

### 12.3 报告事项 vs 复核任务
| 概念 | 实体 | 性质 |
|---|---|---|
| `human_review_items` | 报告 JSON 字段 | 只读的"建议人工确认"事项 |
| `human_review_tasks` | 独立表 | 可分配、转派、重开、计时的工作项 |

- 报告生成时按规则把部分 items 转为 tasks；不是一一对应。
- 任务有独立状态与历史；报告 items 不随任务状态改变。
- 二者通过 `review_id` + `issue_id` 关联；报表可对比"应处理/已处理"。

### 12.4 多人复核与最终结论

| 情况 | 规则 |
|---|---|
| 单条任务单人处理 | 该人的 `result` 即最终结论 |
| 多人独立复核 | 每人意见独立入事件；全部完成后汇总 |
| 意见一致 | 自动采纳一致结果 |
| 意见冲突 | 标记 `escalated`，由指定负责人裁决 |
| 裁决 | 写独立 `adjudicate` 事件（含理由/证据），不覆盖任何原始意见 |

- 同一人可追加意见，但最终以其最新有效事件为准；历史保留。
- 提交后不可物理删除，只能追加更正事件。
- 转派后原处理人意见保留，新处理人独立记录。
- 所有更新带 `version` 乐观锁；冲突返回 409，不静默覆盖。

### 12.5 Issue 复核与 Report 审批的关系

两个独立状态机，通过明确规则关联，不互相隐式修改：

| 规则 | 结论 |
|---|---|
| Issue 完成是否自动改报告 | 否；只更新 Issue 复核汇总 |
| Report 审批是否要求 blocker 任务完成 | 是：存在未完成 blocker 任务时不得 `approve` |
| Report `reject` 后旧 Issue 任务 | 保留有效，不自动关闭 |
| Report 重新审批 | 新建审批任务，旧记录保留 |
| `human_status=approved` 与未完成 blocker | 不允许 |
| 报告内容变化（新 generation） | 旧审批自动失效，需重新审批 |

### 12.6 运营规则（与系统状态机分离）

§12.1–§12.5 定义**系统允许发生什么**；本节定义**组织在什么情况下应该做什么**。运营规则不改变状态机，只决定分派、升级与抽检。

| 事项 | 运营规则 | v1 系统支持 |
|---|---|---|
| 分派 | 主责 + 备份；主责不可用时备份自动接替，转派写事件 | `review_roster.yaml` + 队列 API |
| 角色互斥 | 同一人不得同时担任同一任务的 primary 与 arbitrator；抽样人 ≠ 被抽任务的主责 | 权限校验 + 审计 |
| 利益冲突 | 规则提供人不得审核自己提供的规则；存在冲突时换人处理 | 审核记录 + 转派 |
| 最终裁定 | 争议由指定仲裁人裁定；无仲裁人时升级模块负责人 | 仲裁事件 + 理由 |
| 队列积压 | 超过队列上限时暂停新任务进入该模块队列，并告警 | 队列深度 + 准入 |
| 反馈闭环 | 复核结论进入待审核池，定期评审是否更新 Rubric/KB/评测集 | `docs/23` + 月度评审 |
| 无人认领 | 4 小时未认领进公共队列并提醒；24 小时升级模块负责人；48 小时升级产品负责人 | 按 `received_at` + `assignee IS NULL` 导出，不做自动通知 |
| 处理时限 | blocker/`severity_disputed`/证据冲突 2 个工作日；major 5 个工作日；minor 进周批量清单；到期不改变状态，只标派生 `overdue` | `due_at` + 列表排序 |
| 超时 | 超期 3 个工作日升级；升级不自动改结论 | 每日汇总清单 |
| 处理人离职/权限变更 | 撤销其 API Key；未完成任务转派模块负责人；已提交结论保留，不追溯改写 | 转派写 `human_review_events` + 审计 |
| AI 与人工冲突 | 人工可 `rejected`/`modified`，必须写理由；与 AI blocker 冲突时升级裁决，**不得改 `ai_verdict`** | 追加事件 + `escalated` |
| 多人同时复核 | 乐观锁 `version`；冲突返回 409，由后到者重新拉取；不静默覆盖 | `human_review_events.version` |
| 抽检 | 每周抽 10% 已 `completed` 的 issue 任务由第二人复核；不一致率 > 15% 时重新校准口径 | 抽样导出，人工执行 |
| 回写评测集 | `confirmed`/`rejected`/`modified` 进入待审核池（`docs/23`），复核后入冻结集；**不直接改 Rubric** | 反馈接口 + 待审核池 |
| 撤回/二次复核 | 已 `completed` 可 `reopen`，追加说明或新结论；不删除历史；同一任务最多两次 reopen，之后新建任务 | 事件 + 新任务 |
| 报告级审批 | 存在未完成的 blocker 级任务时不得 `approve`；新 generation 使旧审批失效 | 状态机校验（§12.5） |

> 不要把"系统允许复核"当成"复核流程能运行"。未指定责任人、未配置抽检与升级路径时，复核队列只是空表。上线前必须确认每个试点模块的负责人、备份人与抽检人。

### 12.7 v1 最小运营验收

v1 不建工单/SLA 系统，但以下最小闭环必须可验证：

- [ ] 每条待复核记录有明确负责人或"公共队列待领取"状态（`assignee` 可空但可筛选）。
- [ ] 分派/转派/重开/取消均有 `human_review_events` 与操作人。
- [ ] 人工结论有稳定个人身份（`actor_id`）与理由；`reject`/`request_changes` 必填理由。
- [ ] 超时只标 `overdue`，不自动改结论；升级动作有记录。
- [ ] 多人意见冲突 → `escalated`，裁决事件独立于原始意见。
- [ ] 人工反馈进入待审核池（`docs/23`），不直接改 Rubric。
- [ ] 每条记录可导出"责任人/状态/耗时/结论"，供周度抽检（≥10%）。

> 验收方式：用 10 条模拟任务演练分派→复核→冲突→重开→抽检，全部动作可追溯；责任人映射录入 `design/review_roster.yaml`（未指定前 `status=pending`），详见 `design/changes/` 变更记录与 `Q-13`。

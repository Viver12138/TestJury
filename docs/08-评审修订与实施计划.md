## 1. 评审结论

草案的业务链路是完整的：三模型盲评 → 问题融合 → 投票 → 主审仲裁 → 人工复核，结论永不由系统自动放行。基础设施规模也不是当前瓶颈。

需要补强的是三件事：

1. **检索能否稳定找到正确依据**——召回不足或召回错误，模型再强也只能在错误证据上判断。
2. **多模型判断能否被准确表达**——误报、漏报、错误融合必须有可计算、可追溯的数据结构，而不是只 merge 一份 `issues` 列表。
3. **质量能否分层量化**——必须能区分"检索没找到"、"模型判断错"、"仲裁融合错"，否则调优只能靠猜。

因此本次修订的主线是：**先把证据链和投票数据结构做对，再谈模型选型与阈值**。

## 3. 分层质量定位

调优时必须知道问题出在哪一层，因此指标按层归属，不合并成一个"准确率"：

| 层级 | 回答的问题 | 主要指标 |
|---|---|---|
| 检索层 | 正确知识有没有被找到 | Recall@5 / Recall@10 / MRR@10 / nDCG@10 |
| 重排层 | 正确知识有没有排到前面 | nDCG@10、Evidence Precision |
| 评审层 | 模型有没有正确识别问题 | blocker 召回、误报率、漏报率、三方一致率 |
| 融合层 | 同一问题有没有被正确合并 | 重复率、错误合并率（人工抽检） |
| 仲裁层 | 最终结论是否合理 | 仲裁准确率、主审-人工一致率、`need_human` 触发准确性 |
| 报告层 | 结论有没有可靠依据 | Citation Accuracy（引用是否真实且匹配） |

## 4. Embedding 与 Reranker 选型口径

候选模型（**均为待验证候选，不是定稿**；最终选择须用 TestJury 自己的检索黄金集决定）：

| 用途 | 部署方式 | 候选 | 定位 |
|---|---|---|---|
| Embedding | 云 API | `qwen3.7-text-embedding-flash` | 优先验证成本/吞吐/效果平衡 |
| Embedding | 云 API | `qwen3.7-text-embedding` | 高性能对照组 |
| Embedding | 本地 | `Qwen3-Embedding-0.6B` | 本地起步候选 |
| Embedding | 本地 | `Qwen3-Embedding-4B` | 高性能本地候选 |
| Reranker | 云 API | `qwen3.7-text-rerank` | 第一轮优先验证 |
| Reranker | 本地 | `Qwen3-Reranker-0.6B` / `4B` | 本地起步 / 高性能候选 |

选型原则：

- 公开榜（MTEB / C-MTEB）只作初筛，不作为决策依据。
- 重点观察：业务规则 Recall@K、相似功能点之间的区分能力、规则编号/字段名/数值的检索能力、同义改写召回、API 延迟与吞吐、版本稳定性与可追溯性。
- **先用云 API 建立效果基线，再决定是否值得本地部署**；否则容易把预算花在推理优化上，却无法证明检索收益。
- 实验必须记录：模型名与版本、维度、是否归一化、相似度度量、Recall@5/10、MRR@10、nDCG@10、平均延迟、单位成本。

检索与重排要**分开评测**：初检看"正确知识是否进入候选集"，重排看"正确知识是否被排到前面"，上下文看"注入的知识是否足以支撑结论"。只看最终 Recall 无法定位问题。

## 5. 实施优先级

### P0 · 进入开发前必须定稿（设计层已定稿，实现待做）

- [x] Hybrid Retrieval 完整链路（多查询 → 过滤 → FTS → 向量 → RRF → Rerank → 证据包）
- [x] 用例拆分为多检索查询的规则与优先级
- [x] 知识切片与证据溯源字段
- [x] 每个模型对候选问题的显式投票状态，区分 `not_assessed` 与 `reject`
- [x] 单条用例评审与功能点覆盖评审的边界（`test_scope`）
- [x] Prompt / Rubric / KB 的版本化依据
- [x] 任务持久化、重试与租约恢复机制

### P1 · 第一轮实现（M2–M4）

- [ ] FTS 检索（中文分词或规则编号/字段名精确匹配）
- [ ] 向量检索 + RRF 融合
- [ ] Reranker 接入
- [ ] 检索黄金集（查询-相关知识对）与检索层指标
- [ ] `issue_votes` 落库，仲裁输出按投票状态校验
- [ ] 保存模型（实际返回版本）、Prompt、Rubric、检索配置版本
- [ ] 融合与仲裁全轨迹保留（原始问题 → 候选 → 合并 → 终稿）

### P2 · 有数据后再决策

- [ ] 云 API 与本地 Embedding 对比
- [ ] Reranker 规模对比（0.6B / 4B / API）
- [ ] Top-K 与上下文预算调优
- [ ] 用"重复/非重复"标注校准融合阈值
- [ ] 是否需要 Redis / 独立消息队列（以队列压力与恢复时长为依据）
- [ ] 是否引入专用搜索引擎（以知识库规模为依据）

## 6. 待验证事项与风险

| # | 事项 | 说明 / 应对 |
|---|---|---|
| R8 | 检索效果未验证 | 检索黄金集未建前，任何"模型不行"的判断都不可信；先建 ≥ 100 条查询-知识对 |
| R9 | FTS 中文分词 | PostgreSQL 默认分词对中文效果差，需 zhparser / pg_jieba 或改为 n-gram + 规则编号精确匹配，需实测 |
| R10 | 检索配置漂移 | 检索参数（Top-K、RRF k、rerank 阈值）必须版本化，变更触发检索回归 |
| R11 | `test_scope` 数据成本 | 功能点场景清单需要测试专家维护；初期可只对 3–5 个高频模块的功能点提供，其余标注"范围未知" |
| R12 | 投票结构带来的 prompt 变化 | 要求模型对候选问题逐条表态会拉长输出，需评估 token 成本与截断风险 |

## 使用与恢复

1. 日常直接打开本机入口，从 `.tmp/local-access.json` 复制 `key` 到页面。凭证只保留在当前页面，不要写进报告或提交仓库。
2. 按“标题、前置条件、操作 → 预期”填写用例，选择当前实现基线后提交。查看评审依据、问题与建议；可下载报告、查看历史、保存采纳或不采纳反馈。
3. 对重复问题，保留其中一条并对另一条记录“不采纳（误报或重复）”，注明对应问题编号。服务身份的反馈不等于人工审批，也不会自动纳入黄金集。
4. 重启电脑后先打开 Docker Desktop，等待其就绪，再在项目目录运行以下命令。若 8088 已有本项目服务运行，不要重复启动。

```powershell
& 'C:\Users\admin\AppData\Local\Programs\DockerDesktop\resources\bin\docker.exe' start testjury-postgres
.\.venv\Scripts\python.exe scripts/serve_local.py
```

启动脚本只执行正常迁移，保留已有启用知识版本与数据。前台运行时保持终端开启；退出前确认页面历史里没有“等待评审/正在评审/正在重试”，再按 Ctrl+C。当前已由后台进程运行，PID 记录在 `.tmp/server.pid`；本机 `.tmp/restart-local.ps1` 会检查在途任务并核对进程命令，条件不满足时拒绝重启。不要通过删除数据库或重建 schema 处理启动问题。

健康检查：`/livez` 表示进程存活，`/readyz` 同时检查数据库、迁移与队列。当前后台日志位于 `.tmp/server-20261113.stdout.log` 和 `.tmp/server-20261113.stderr.log`。若数据库未就绪，先检查 Docker；若出现“存在活动任务”则等待任务结束。任务阶段恢复沿用已冻结版本，修改代码后不应强行让旧任务使用新配置。

数据库备份恢复只能先在独立临时库验证；不要直接覆盖当前应用库。此前实际备份恢复和逐表比对记录见 `evidence/M2/upgrade_preservation.json`。这不是生产 RPO/RTO 承诺。

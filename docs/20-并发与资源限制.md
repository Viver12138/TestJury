# 20 · 并发与资源限制

> 版本：v1.7 · 2026-11-10（补充 16 落实：技术上限与业务预算分离）
> 目的：把"Worker=4"这类初始值升级为可验证的容量设计，防止供应商限流、内存/连接池耗尽与成本失控。
> 关联：10 §10、13、19。

---

## 1. 容量模型

```text
峰值并发任务 = min(WORKER_CONCURRENCY, 供应商可用并发 / 每任务并发调用数)
每任务并发调用 ≈ 3（盲评/投票）+ 1（仲裁）+ 1（检索 embedding/rerank）
```

- Worker 数只是本地上限，不代表供应商能吃下。
- 按供应商分别计算：Qwen、DeepSeek、Kimi 的 RPM/TPM/并发独立。
- 单任务内三路并行是**扇出**，不是三个 Worker。

## 2. 资源上限

| 资源 | 默认 | 说明 |
|---|---|---|
| `WORKER_CONCURRENCY` | 4 | 本机同时执行任务数 |
| 单供应商并发 | 待实测 | 每 provider 独立 semaphore |
| 单供应商 RPM/TPM | 按合同 | 超限进入延迟重试 |
| `MAX_QUEUE_DEPTH` | 500 | 超过返回 429 `QUEUE_FULL` |
| 单批次用例 | 50 | API 硬限制 |
| 单任务输入 | 20k 字符 / 15k token 证据包 | 超限 422 或截断证据 |
| 单任务输出 | 按模型 `max_output_tokens` | 截断按 `docs/18` 处理 |
| 单任务总超时 | 20 分钟 | 含阶段与重试，不含排队 |
| 每日成本 | `DAILY_BUDGET_COST` | 超限告警/降级/暂停 |

> 15 分钟改为 **20 分钟**：完整阶段预算 805s，加 2 次重试余量后 15 分钟不够；压测后再定。

## 3. 准入与排队

1. API 检查队列深度与预算；超限返回 429，不创建任务。
2. 任务入队后按 `created_at` 近似 FIFO；同一调用方不保证公平，但记录 `caller_id` 便于限流。
3. 单调用方可配置并发配额，避免一个流水线占满队列。
4. 批次任务拆成子任务入队，不单独占用 Worker。

### 3.1 数据库连接池

| 项 | 规则 |
|---|---|
| 池上限 | API/Worker 分池；总连接 ≤ DB `max_connections` 的 80% |
| 获取超时 | 默认 5s；超时返回 503 `DB_BUSY`，不无限等待 |
| 拒绝策略 | 池耗尽拒绝新任务/请求，不排队到超时 |
| 泄漏检测 | 连接占用超阈值告警；定期回收 |
| 迁移/备份 | 使用独立连接，不占应用池 |

## 4. 供应商隔离与备用模型

- 每个 provider 独立 semaphore + 独立限流器；一个供应商慢不拖垮其他。
- 连接池按 provider 隔离，设置最大连接与空闲回收。
- 某 provider 连续失败 → 熔断（半开探测），不影响其他 provider。
- 限流等待计入阶段超时，但不计入模型调用超时。

**备用模型规则**：

1. 备用策略必须在任务创建时随主模型一起冻结（`primary` + `fallback` + 触发条件），不能在运行中临时选一个。
2. 只有冻结策略允许时才切换；切换写审计事件，报告记录实际使用模型。
3. **恢复任务时不得因为供应商故障临时换模型**；冻结的 fallback 不可用 → `failed(MODEL_UNAVAILABLE)`。
4. 切换后不得改变模型角色（主审仍是主审）；不允许用陪审替代主审仲裁。

### 4.1 熔断与恢复

| 状态 | 行为 |
|---|---|
| Closed | 正常调用；统计失败率 |
| Open | 连续失败/失败率超阈值 → 停止调用，直接失败/fallback |
| Half-open | 冷却后放少量探测请求；成功则 Closed，失败则继续 Open |

- 阈值按 provider 配置，默认连续 5 次 5xx/超时或 1 分钟失败率 >50%。
- 429 不算故障熔断，按限流退避；5xx/超时算故障。
- 熔断与恢复写审计/指标；恢复后不自动重放失败任务，需按冻结策略重试。

## 5. 慢任务与取消

- 单任务总超时到 → 停止发起新调用，保留 Checkpoint，状态 `failed`（`TIMEOUT`）。
- 取消（v1.5）：写 `cancel_requested_at`，Worker 在阶段边界检查并停止；已产生的阶段输出保留。
- 被取消任务不生成正式 `ai_verdict`；如需结果必须重跑新 generation。
- Worker 被慢供应商占用超过阈值 → 告警；必要时降低该 provider 并发。

## 6. 成本熔断

| 层级 | 超限行为 |
|---|---|
| 单任务 | **投票不可静默跳过**；预算不足以覆盖投票时，受影响候选标 `need_human`，报告标 `completed_with_warnings`，不生成正式完整结论 |
| 单批次 | 拒绝新任务入队 |
| 每日 | 告警 + 降级/暂停（配置） |
| 供应商 | 熔断并按冻结的 fallback 策略切换 |

> Reranker 可以跳过（降级检索）；投票不能。缺少投票的评审必须显式降级，不能伪装成正常完成。

### 6.1 预算模型

| 维度 | 规则 |
|---|---|
| 单任务 | `REVIEW_BUDGET_TOKENS` / `REVIEW_BUDGET_COST`；启动前预留核心阶段额度 |
| 单阶段 | 每阶段最大调用次数与 token；重试计入原阶段预算 |
| 单模型 | 按 provider 记录调用额度，避免一个模型吃满预算 |
| 仲裁 | 预留独立额度；条件仲裁不消耗未触发预算 |
| 批次 | 50 条总成本上限；超限拒绝新任务 |
| 软预算 | 达到后告警/降级非核心调用 |
| 硬预算 | 达到后禁止启动新的非必要调用；**已启动调用**按阶段策略决定是否等待 |
| 核心预留 | 投票与必要盲评的额度不能被前置阶段挤占 |

预算耗尽时不得"先花完再跳过投票"；应从一开始就为投票预留。

### 6.2 上下文超限

模型上下文不是无限预算，超限时必须有可解释策略：

| 场景 | 处理 |
|---|---|
| 知识证据过长 | 按相关性 + 证据等级 + claim 覆盖裁剪；先删低等级/重复证据 |
| 初审意见过长 | 结构化摘要（保留 issue/证据/结论），不直接硬截断 |
| 候选过多 | 分批投票，候选 ID 稳定；不因分批改变候选身份 |
| 仲裁超限 | 优先保留原始证据、争议候选、必要投票；可省略非争议项 |
| 核心证据无法保留 | `need_human` 或失败，不得删掉核心证据后仍出完整结论 |

每个阶段记录：原始 token、实际发送 token、裁剪内容与原因、裁剪策略版本、是否触及预算、是否降低完整性。报告展示"上下文被裁剪"标记。

### 6.3 成本口径分层

"花了多少钱"至少分六种口径，混在一起会得出错误的预算结论：

| 口径 | 定义 | 记录方式 |
|---|---|---|
| 已发生（incurred） | 已成功调用、按当前价格表计算的成本 | `model_runs.cost_estimate` 汇总 |
| 已预留（reserved） | 任务开始时为核心阶段预留、尚未消耗的额度 | `review_jobs` 预算预留字段 |
| 预计（projected） | 按剩余阶段与历史均值估算的最终成本 | 查询时计算，不落库为事实 |
| 失败调用（failed） | 失败/超时调用中供应商仍计费的部分 | 按供应商规则单独标记 |
| 重试（retry） | 重试产生的额外调用成本 | `attempt` 维度累计 |
| 缓存（cache） | 命中缓存减少的输入 token / 费用 | 与未命中成本分开记录 |

预算层级与超限行为：

| 层级 | 需要回答 | 超限默认行为 |
|---|---|---|
| 单次调用 | 本次请求实际花费多少 | 降级或跳过非核心调用（rerank 可跳过，投票不可跳过） |
| 单个评审 | 一份用例评审总成本 | 受影响候选 `need_human`，报告 `completed_with_warnings`（§6） |
| 批次 | 一批任务总成本 | 429 `BUDGET_EXCEEDED`，拒绝新任务入队 |
| 日预算 | 当日是否达到上限 | 告警 + 降级/暂停（可配置） |
| 月预算 | 当月是否达到上限 | 告警 + 拒绝新批次；管理员可显式批准继续并记审计 |

**超预算可选项**（按配置启用，不能默认静默跳过）：拒绝新任务、降级到低成本拓扑、暂停非关键阶段、管理员批准继续、仅告警不阻断。选择必须写入配置并出现在报告 `degraded_reasons`/预算记录中。

**价格版本**：每次计量记录 `price_config_version` 与币种；供应商调价只影响新调用，历史报告成本不重算。成本是估算值，与账单差异在验收报告中单独说明。

### 6.4 技术保护上限与业务批准预算（D185）

两者不是同一个数字，不能互相替代：

| 层 | 谁设 | 作用 | 变更 |
|---|---|---|---|
| 技术保护上限 | 工程/运维 | 防止失控调用、供应商故障或循环重试打爆额度 | 配置变更 + 压测/回归 |
| 业务批准预算 | 业务负责人/财务 | 决定可承接的评审量与风险等级 | 审批记录 + 价格版本 |

- 技术上限必须 ≤ 业务预算；业务预算下调时，技术上限同步收缩。
- 超技术上限：按 §6 的降级/熔断执行；超业务预算：由业务负责人决定拒绝、降级或批准追加。
- 单条/日/月/批次预算需按风险等级分别记录；"平均成本"不得替代分位数与最坏情况。
- 预算数值必须结合真实供应商价格、预期评审量、模型组合实验结果确定（`Q-14`/`V-09`），当前配置值只是初始占位。

## 7. 压测与验收

- 用 4/8/16 Worker 与 10/50/100 并发任务压测。
- 记录：队列等待、P95 阶段耗时、供应商 429 率、失败率、单位成本。
- 验收：在目标并发下 429 可解释、无重复终稿、成本不超预算、单供应商故障不拖垮全局。
- 压测结果写回本文件与 `docs/13` 的超时预算。

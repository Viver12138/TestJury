# 20 · 并发与资源限制

> 版本：v0.7 · 2026-11-09
> 目的：把"Worker=4"这类初始值升级为可验证的容量设计，防止供应商限流、内存/连接池耗尽与成本失控。
> 关联：10 §10、13、19。

---

## 1. 容量模型

```text
峰值并发任务 = min(WORKER_CONCURRENCY, 供应商可用并发 / 每任务并发调用数)
每任务并发调用 ≈ 3（盲评/投票）+ 1（仲裁）+ 1（检索 embedding/rerank）
```

- Worker 数只是本地上限，不代表供应商能吃下。
- 按供应商分别计算：Qwen、DeepSeek、Kimi 的 RPM/TPM/并发独立。
- 单任务内三路并行是**扇出**，不是三个 Worker。

## 2. 资源上限

| 资源 | 默认 | 说明 |
|---|---|---|
| `WORKER_CONCURRENCY` | 4 | 本机同时执行任务数 |
| 单供应商并发 | 待实测 | 每 provider 独立 semaphore |
| 单供应商 RPM/TPM | 按合同 | 超限进入延迟重试 |
| `MAX_QUEUE_DEPTH` | 500 | 超过返回 429 `QUEUE_FULL` |
| 单批次用例 | 50 | API 硬限制 |
| 单任务输入 | 20k 字符 / 15k token 证据包 | 超限 422 或截断证据 |
| 单任务输出 | 按模型 `max_output_tokens` | 截断按 `docs/18` 处理 |
| 单任务总超时 | 20 分钟 | 含阶段与重试，不含排队 |
| 每日成本 | `DAILY_BUDGET_COST` | 超限告警/降级/暂停 |

> 15 分钟改为 **20 分钟**：阶段超时合计 690s，加 2 次重试余量后 15 分钟不够；压测后再定。

## 3. 准入与排队

1. API 检查队列深度与预算；超限返回 429，不创建任务。
2. 任务入队后按 `created_at` 近似 FIFO；同一调用方不保证公平，但记录 `caller_id` 便于限流。
3. 单调用方可配置并发配额，避免一个流水线占满队列。
4. 批次任务拆成子任务入队，不单独占用 Worker。

## 4. 供应商隔离

- 每个 provider 独立 semaphore + 独立限流器；一个供应商慢不拖垮其他。
- 连接池按 provider 隔离，设置最大连接与空闲回收。
- 某 provider 连续失败 → 熔断（半开探测），不影响其他 provider。
- 限流等待计入阶段超时，但不计入模型调用超时。

## 5. 慢任务与取消

- 单任务总超时到 → 停止发起新调用，保留 Checkpoint，状态 `failed`（`TIMEOUT`）。
- 取消（v1.5）：写 `cancel_requested_at`，Worker 在阶段边界检查并停止；已产生的阶段输出保留。
- 被取消任务不生成正式 `ai_verdict`；如需结果必须重跑新 generation。
- Worker 被慢供应商占用超过阈值 → 告警；必要时降低该 provider 并发。

## 6. 成本熔断

| 层级 | 超限行为 |
|---|---|
| 单任务 | 跳过投票/rerank 并标降级；不得静默跳过投票 |
| 单批次 | 拒绝新任务入队 |
| 每日 | 告警 + 降级/暂停（配置） |
| 供应商 | 熔断并切换备用模型（若配置） |

## 7. 压测与验收

- 用 4/8/16 Worker 与 10/50/100 并发任务压测。
- 记录：队列等待、P95 阶段耗时、供应商 429 率、失败率、单位成本。
- 验收：在目标并发下 429 可解释、无重复终稿、成本不超预算、单供应商故障不拖垮全局。
- 压测结果写回本文件与 `docs/13` 的超时预算。

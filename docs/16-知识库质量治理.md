# 16 · 知识库质量治理

> 版本：v1.3 · 2026-11-10（M0 前契约收口）
> 目的：知识库不只要能检索到，还要保证规则准确、适用、可追溯；发布前后都要有质量门禁。
> 关联：11、04 §7.4、02 `kb_*`。

---

## 1. 规则生命周期

```
draft → reviewed → published → deprecated
```

| 状态 | 含义 | 可检索 | 允许操作人 |
|---|---|---|---|
| `draft` | 草稿，未审核 | 否 | 内容创建者 |
| `reviewed` | 已审核，待发布 | 否 | 审核人 |
| `published` | 正式生效 | 是 | 发布人 |
| `deprecated` | 已废弃 | 否（历史对照除外） | 发布人 |

- 状态只允许前进或回退到 `draft`（需审核人操作）；不允许 `deprecated → published` 直接复活。
- Git 提交 ≠ 规则生效；状态与 `kb_version` 由发布流程写入。
- 每次状态变更记录操作人、时间、原因（审计）。

## 2. 职责分离

> 角色统一见 `docs/17` §5：`kb_creator` / `kb_reviewer` / `kb_publisher`，与系统角色分开授权。

| 角色 | 权限 |
|---|---|
| `kb_creator` | 创建/修改 `draft`，提交审核 |
| `kb_reviewer` | 审核内容、批准进入 `reviewed`、驳回 |
| `kb_publisher` | 发布 `reviewed → published`、废弃、回滚 |
| `admin` | 管理账号与权限，**不自动获得内容审核/发布权** |

生产环境不允许同一人同时担任创建与发布（可配置，默认强制）。AI 生成的规则只能作为 `draft`，不得直接发布。

## 3. 适用范围字段

每条规则/切片除正文外必须能表达适用范围：

| 字段 | 说明 |
|---|---|
| `product_version` | 产品版本（`valid_from/to_version`） |
| `server_environment` | 服务端环境 |
| `client_type` | 客户端类型 |
| `user_level` | 用户等级 |
| `feature_flag` | 功能开关 |
| `role_permission` | 角色/权限 |
| `effective_from` / `effective_to` | 生效/失效时间 |
| `applicable_conditions` | 其它结构化条件 |

缺适用范围时，该规则只能作为 E2 参考，不得单独判 blocker。

## 4. 质量指标

| 指标 | 定义 | 目标 |
|---|---|---|
| 规则完整率 | 必要字段完整的规则比例 | ≥ 95% |
| 规则重复率 | 重复或高度相似规则比例 | ≤ 5% |
| 规则冲突率 | 同范围内相互矛盾的规则比例 | 0（发现即阻断） |
| 规则过期率 | 已过 `effective_to` 仍未废弃的比例 | ≤ 2% |
| 无来源比例 | 缺可靠来源的规则比例 | 0 |
| 适用范围缺失率 | 未填适用范围的比例 | ≤ 10% |

质量指标按 `kb_version` 记录，进入发布报告。

## 5. 重复与冲突识别

- **重复**：同一模块 + 功能点内，规则文本 trigram 相似度 ≥ 0.9 或语义相似度 ≥ 0.9，标记 `duplicate_candidate`，人工确认。
- **冲突**：同一范围内两条 E1 对同一行为规定不同 → `conflict`，阻断发布，转人工裁决。
- **版本差异**：同一 `rule_id` 不同 `kb_version` 的正文变化，记录 diff。
- 不允许模型自动合并/裁决冲突规则。

## 6. 发布差异报告

每次发布生成 `kb-diff-<version>.json`：

```json
{
  "from": "kb-2026-11-01",
  "to": "kb-2026-11-09",
  "added": [], "modified": [], "deleted": [], "deprecated": [],
  "affected_modules": ["挖宝"],
  "retrieval_metrics": { "recall_at_10": 0.91, "ndcg_at_10": 0.78 },
  "evidence_usage_change": "报告引用变化摘要",
  "conflicts": []
}
```

用途：发布后定位"结论变化是否由知识库变更引起"；与检索回归、评审回归一起归档。

## 7. 缺口聚合

`kb_gaps` 不只是"缺规则"，先分型再定责任人：

| `gap_type` | 含义 | 处理方向 |
|---|---|---|
| `knowledge_missing` | 知识库确实没有相关规则 | 补知识 |
| `retrieval_missed` | 有规则但检索没召回 | 修检索/索引，不是补录 |
| `knowledge_conflict` | 规则互相冲突 | 规则治理/人工裁决 |
| `knowledge_outdated` | 规则已过期 | 更新/废弃 |

`kb_gaps.gap_resolution` 记录实际处理动作：`add_knowledge` / `update_knowledge` / `adjust_retrieval` / `fix_applicability` / `resolve_conflict` / `no_action`。

关闭缺口不等于"补了规则"：`retrieval_missed` 应改检索；`knowledge_conflict` 应先裁决。关闭时写处理人、动作与关联规则/版本。

**关闭前验证**：

1. 修复已发布到新 `kb_version`；
2. 用原触发用例 + 缺口相关查询跑检索回归；
3. 记录修复前后 Recall/证据命中变化；
4. 验证通过才关闭；失败则重新打开并记录原因。

聚合规则：

- 组合键：`module + function_point + suspected_rule + root_cause`；先规则匹配，再语义相似（trigram/向量 ≥ 0.85）。
- 相似但不确定 → 人工合并队列；合并保留全部关联案例。
- 已解决缺口不再重复创建；可以重新打开并保留历史。
- **缺口去重**：同一组合键只保留一个 open 记录，`occurrences` 累加。

- 按 `module + function_point` 分桶；
- 对 `suspected_rule` 做 trigram/向量相似度聚合，阈值 ≥ 0.85 合并；
- 不同业务场景的缺口不合并（人工确认）；
- `occurrences ≥ 3` 进入待确认清单，**不自动生成规则**；
- 确认后由创建者写 `draft`，走正常审核发布。

## 8. 验收

- 同一内容重复发布得到相同 `kb_version`；内容变化得到新版本。
- 发布前：元数据、冲突、失效规则、Embedding 失败、检索回归全部通过。
- 发布后：差异报告可查，能回答"这次结论变化是否由 KB 变更引起"。
- 废弃规则不再被检索；历史报告引用仍可回查。
- 质量指标随版本记录，连续下降触发人工复核。

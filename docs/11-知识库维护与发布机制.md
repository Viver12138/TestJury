# 11 · 知识库维护与发布机制

> 版本：v1.2 · 2026-11-10（契约一致性冻结修订）
> 目的：明确知识库的**事实源、切片、向量化、中文检索、版本、发布与回滚**规则，保证每次评审都能回答"依据来自哪一版、哪一段"。
> 关联：02 §2（`kb_*`、`embedding_profiles`、`kb_versions`）、01 §5、06 §1、07 §2.3/§5。

---

## 1. 事实源与运行时副本

**决策：Git + Markdown 是唯一事实源，PostgreSQL 是运行时索引与检索副本。**（见 `docs/08` D19）

| 角色 | 存放 | 说明 |
|---|---|---|
| 事实源 | `kb_content/`（Git） | 人工编辑、代码评审、变更历史都在 Git |
| 运行时索引 | `kb_documents` / `kb_rules` / `kb_chunks` | 由发布流程生成，可随时按事实源重建 |
| 版本记录 | `kb_versions` | 版本号、状态、发布人、检索回归指标 |
| 当前生效 | `kb_versions.status='active'`（唯一） | 评审任务只读 active 版本 |

禁止在数据库中直接编辑知识库正文；所有变更必须走 Git → 发布流程。若未来改为数据库编辑，需另行设计版本与导出机制，不能双事实源并存。

## 2. 目录与元数据规范

```
kb_content/
├─ 挖宝/
│  ├─ requirements.md      # 功能说明/需求
│  ├─ rules.yaml           # 结构化规则（RULE-*）
│  ├─ known_limits.md      # 已知限制
│  ├─ history_bugs.md      # 历史缺陷
│  └─ terms.md             # 术语
└─ 背包仓库/
```

每个文件头部必须有元数据（YAML front matter 或同目录 `meta.yaml`）：

| 字段 | 必填 | 说明 |
|---|---|---|
| `doc_id` | 是 | 稳定标识，发布后不可复用 |
| `module` | 是 | 模块名（与用例 `module` 对齐） |
| `doc_type` | 是 | `requirement` / `rule` / `design` / `gm_command` / `known_limit` / `history_bug` / `term` / `flow`（见 `docs/17`） |
| `source_ref` | 是 | 原始出处（文档名、章节、链接） |
| `owner` | 是 | 内容负责人 |
| `updated_at` | 是 | 最后更新时间 |

校验失败（缺字段、`doc_id` 重复、`module` 不在白名单）→ 发布中止。

## 3. 切片规则

按知识类型切片，不按固定字符数硬切：

| 类型 | 切片单位 | 必须绑定 |
|---|---|---|
| 业务规则 | 一条规则一个 chunk | `rule_id`、适用范围、前置条件、原文位置 |
| 功能说明 | 一个功能点一个 chunk | `function_point`、`heading_path` |
| 已知限制 | 一条限制一个 chunk | 适用版本/范围 |
| 历史缺陷 | 一个缺陷一个 chunk | 发生版本、修复版本、当前状态 |
| 术语 | 一个术语一个 chunk | 正式名称、别名 |
| 操作流程 | 一个完整流程一个 chunk | 起止条件 |

每个 chunk 记录：`chunk_index`、`heading_path`、`content_hash`、`token_count`、`source_ref`、`embedding_profile_id`。切片后**不能只剩正文**——适用条件与出处必须与正文在同一行。

## 4. Embedding Profile 与维度

**决策：v1 固定 1024 维、单一 active profile。**（见 `docs/08` D18）

- `embedding_profiles` 记录 provider / model / model_version / dimension / normalize / config_version / status。
- v1 的 `dimension` 固定为 1024，数据库加 `CHECK (dimension = 1024)`；`kb_chunks.embedding` 与 `issue_embeddings.embedding` 都是 `vector(1024)`。
- 换模型 = 新建 profile → 重新切片/向量化 → 新索引 → 检索回归 → 切 active；**禁止混用不同 profile 的向量**。
- 若未来要多维度并存，必须按 profile 分表或分列，不能只在配置层声明支持。
- `issue_embeddings` 同样记录 `embedding_profile_id`，问题融合只用与当前 active profile 一致的向量。

## 5. 中文关键词检索

**决策：v1 采用"精确匹配 + pg_trgm 三元组"，`zhparser` 作为可选升级，不把未安装的扩展写死在迁移里。**

| 通道 | 实现 | 适用 |
|---|---|---|
| 精确匹配 | `rule_id`、字段名、错误码、数值的前缀/等值匹配 | RULE-XXX、`item_id`、1024 等 |
| 三元组 | `pg_trgm` GIN 索引（`content gin_trgm_ops`），`similarity()`/`%` | 中文短语、术语、近似子串 |
| FTS（可选） | `search_vector` 使用 `zhparser` 的 `zh` 配置 | 装好扩展后的语义分词检索 |

规则：

1. `pg_trgm` 是标准 contrib 扩展，部署时 `CREATE EXTENSION IF NOT EXISTS pg_trgm`；索引随发布重建。
2. `search_vector` 保留，但**生成配置必须与部署一致**：安装 zhparser 时用 `to_tsvector('zh', content)`；未安装时不要声称支持中文 FTS，关键词通道以 trigram + 精确匹配为准。
3. 分词配置变更 = 重建 `search_vector` 与相关索引，并跑检索回归；不能只改配置不重建。
4. 关键词与向量结果用 RRF 融合，**不直接相加原始分数**（见 `docs/01` §5.2）。

## 6. KB Version

- `kb_version = sha256(所有 kb_content 文件内容排序后拼接)` 取前 12 位。
- 同一 `kb_version` 永不覆盖；内容变更必然产生新版本。
- `kb_versions` 记录：`version`、`status`（`building` / `candidate` / `active` / `retired` / `failed`）、`created_at`、`published_by`、`notes`、`retrieval_metrics`（Recall@10、nDCG@10 等）。
- 评审任务创建时锁定 `kb_version`，报告记录该版本；任务执行中即使 active 切换，也不改变本次使用的版本。

## 7. 发布流程

```
1. Git 提交知识库变更
2. 格式与元数据校验（doc_id / module / doc_type / source_ref）
3. 切片（按类型），计算 content_hash
4. 生成 embedding（当前 active profile），写入 candidate 版本
5. 构建关键词索引（trigram / 可选 FTS）
6. 检索回归（检索黄金集；见 docs/07 §2.3）
   ├─ 指标不达标 → 发布中止，candidate 标记 failed
   └─ 通过 → 进入下一步
7. 生成新的 kb_version，写入 kb_versions(candidate)
8. 人工确认后切换 active（事务内：旧 active → retired，新版本 → active）
9. 新任务使用新版本；旧任务继续用其锁定的版本
10. 出问题 → 回滚：把旧版本重新置为 active（不删除新版本，便于复盘）
```

发布与回滚只能由 `kb_publisher` 执行，写审计日志（见 `docs/10` §11）；`admin` 不自动拥有该权限。

### 7.1 发布门禁

| 检查项 | 要求 |
|---|---|
| RULE-ID | 唯一、不复用、格式合法 |
| 规则内容 | 非空；切片不破坏规则完整性 |
| 元数据/解析 | front matter 合法；表格/代码块/公式未被切片破坏；`heading_path` 可回溯 |
| 来源 | `source_ref` / `source_version` 可追溯 |
| 模块/功能点 | 明确且在白名单内 |
| 适用版本/时间 | `valid_from/to_version`、`effective_from/to` 明确或显式留空 |
| 状态 | 只有 `reviewed`/`published` 可发布；`deprecated` 不进入检索 |
| 冲突 | 同级 E1 冲突必须人工裁决后才能发布 |
| Embedding | 记录成功/失败数量，失败不为 0 时中止 |
| 检索回归 | 必须通过（见 §10） |

> Markdown 提交到 Git 不等于规则自动获得业务权威性；规则等级与状态必须经过审核。

### 7.2 单模块试点

不要一开始批量导入所有模块。先选 1 个高频模块（如挖宝）完整跑通：

```
原始文档 → 结构化规则（RULE-ID）→ Markdown → 切片 → Embedding
→ 检索 → 证据引用 → 评审报告
```

试点验收：规则完整率、检索 Recall@10、证据可追溯、发布/回滚、报告引用真实。跑通后再扩到 3–5 个模块。

#### 首版知识库准入条件

| 项 | 要求 |
|---|---|
| 规则数量 | 试点模块至少 20 条有效规则（按业务复杂度调整） |
| RULE-ID | 每条规则必须有唯一 RULE-ID；无 ID 不得进正式库 |
| 来源与范围 | 每条必须有 `source_ref`、适用模块/版本/条件 |
| 审核 | 通过 `kb_reviewer` 审核，状态为 `published` |
| 检索 | 黄金检索集 Recall@10 ≥ 90%，证据可定位 |
| 冲突 | 同级 E1 冲突必须先裁决，未裁决不得发布 |
| 无依据表达 | 检索不到时标 `kb_insufficient`，不得编造规则 |
| 历史重评 | KB 更新不自动重评历史报告；需要时新建 generation 并记录触发原因 |

**责任分工（RACI）**：

| 事项 | 负责 | 批准 |
|---|---|---|
| 原始资料提供 | 业务/策划 | 模块负责人 |
| 规则整理 | `kb_creator` | `kb_reviewer` |
| 发布/回滚 | `kb_publisher` | 模块负责人 |
| 冲突裁决 | 模块负责人 + `kb_reviewer` | 产品负责人 |
| 版本废弃 | `kb_publisher` | 模块负责人 |

## 8. 回滚

- 回滚 = 切换 active 指针，不删除任何版本、不覆盖历史。
- 保留最近 N 个版本（默认 10）的索引与 chunk；更早版本归档。
- 回滚后必须记录原因、操作人、时间，并重跑一次检索回归确认。
- 已生成的报告不回改：它们引用的是当时的 `kb_version`，证据仍可回查。

### 8.1 发布差异报告

每次发布生成 `kb-diff-<version>.json`：新增/修改/删除/废弃规则、受影响模块、检索指标变化、证据引用变化、冲突列表（格式见 `docs/16` §6）。用于判断"结论变化是否由知识库变更引起"。

## 9. 证据稳定性

- `kb_refs` / `evidence_refs` 引用 `chunk_id` + `kb_version`，不引用"当前最新内容"。
- chunk 的 `id` 在同一 `(doc_id, chunk_index, kb_version)` 内稳定；重新切片会生成新 chunk，旧报告仍指向旧版本。
- 历史缺陷类证据必须带"发生版本/修复版本"，报告不得把它表述为"当前版本仍存在"。
- 删除文档时保留 tombstone（`doc_id` + 版本 + 删除时间），避免旧引用悬空。

### 9.1 规则冲突与版本适用性

- 每条规则/切片带 `evidence_level`（E1–E4）、`rule_status`、`valid_from_version`、`valid_to_version`、`effective_from`、`effective_to`、`applicable_conditions`、`source_version`。
- 规则生命周期固定为：`draft → reviewed → published → deprecated`；只有 `published` 进入当前有效证据集合，`deprecated` 不进入检索。
- **检索相关性 ≠ 适用性**：召回后先按当前用例版本/条件过滤；不适用但相关的证据可以展示，但不得作为判定依据。
- 已过 `valid_to_version` 或 `effective_to` 的规则默认不注入；只有"历史对照"场景才注入，且必须标注"已失效"。
- **同级权威规则冲突**（两条 E1 对同一行为规定不同）：模型不得自行选择；记录双方证据，结论转 `need_human`。
- **E1 与 E2 冲突**：以 E1 为准并提示"需求与规则不一致，需确认哪份为准"，不直接判用例错误。
- 冲突判定顺序固定：版本/时间 → 模块/产品/环境 → 配置的优先级 → 无法确定则转人工；不允许模型挑"更符合自己观点"的证据。

## 10. 检索回归

- 数据集与指标见 `docs/07` §2.3、§3.2；发布前必须跑。
- 分段记录：初检 / RRF / rerank / 证据包。
- 门禁：Recall@10 或 nDCG@10 较上一 active 版本下降 > 3 个百分点 → 禁止发布。
- 回归结果写入 `kb_versions.retrieval_metrics`，作为版本证据。

## 11. 权限、审计与运维

| 操作 | 权限 | 审计 |
|---|---|---|
| 创建/修改规则 | `kb_creator`（Git PR） | Git 历史 |
| 审核规则 | `kb_reviewer` | 发布记录 |
| 发布/废弃/回滚 | `kb_publisher` | `audit_log` |
| 查看版本与指标 | 内部只读 | — |
| 重建索引 | `admin` / 运维 | `audit_log` |

**职责分离**：生产环境 `kb_creator` 与 `kb_publisher` 不得为同一人（可配置，默认强制）；AI 生成内容只能进 `draft`，不得直接发布。角色统一见 `docs/17` §5，规则生命周期与质量指标见 `docs/16`。

运维要点：

- 重建索引期间旧索引保持可读，切换用事务/别名，不做"先删后建"。
- 发布失败不改变 active；candidate 保留供排查。
- 每次发布记录 embedding 调用量、token、耗时，便于成本归因。

## 12. 常见故障

| 故障 | 处理 |
|---|---|
| `doc_id` 重复 | 发布中止，修数据后重跑 |
| embedding 服务不可用 | candidate 标记 failed；active 不变 |
| 中文检索效果差 | 对比 trigram / zhparser 两种方案，用检索集决定，不凭感觉切换 |
| 新旧版本指标接近 | 允许发布，但记录差异；连续下降则回滚 |
| 旧报告引用失效 | 检查是否误删版本；按 tombstone 恢复只读副本 |

## 13. 验收要点

见 `docs/07` §9.3，至少覆盖：

- 同内容重复发布产生相同 `kb_version`，内容变更产生新版本；
- active 唯一，回滚后新任务使用旧版本；
- 报告能定位到 `chunk_id` + `source_ref` + `kb_version`；
- 换 embedding profile 后不混用旧向量；
- 中文关键词检索在真实样本上可用（trigram 或 zhparser 至少一种）；
- 发布失败不影响线上评审。

# 04 · 评审标准（Rubric）

> 版本：v1.6 · 2026-11-10（补充 15 落实：Rubric 版本绑定与冻结规则）

## 1. 评审对象与边界

评审的是**用例质量**，不是功能实现质量。禁止评价：代码、性能、美术表现、剧情文案、实现难度。

一句判据：**这份用例能不能让另一个不了解该功能的人，原样执行并明确判断通过/不通过。**

### 1.1 v1 范围

**v1 只做单条功能测试用例（`test_type=functional`）的质量评审。** 非功能测试类型在 API 层返回 422 `UNSUPPORTED_TEST_TYPE`，不进入本 Rubric（`docs/00` §6）。功能点/需求的整体覆盖评审是另一类任务，需要需求、功能点与完整案例集合，v1 只预留数据结构（`test_scope`）与接口位置，不输出功能点覆盖率或覆盖缺口报表（见 `docs/08` D16）。

允许的表述：

- "当前用例未覆盖 `test_scope.required_scenarios` 中列出的某场景"（必须指明范围来源）；
- "当前用例自身的前置/步骤/预期存在问题"。

禁止的表述：

- "该功能点覆盖不足/覆盖率为 X%"；
- "这个需求缺少 N 个场景"（没有完整范围依据时）。

评审依据只有三类，且互相不可替代：**用例本身**（被评审对象）、**知识库**（业务事实）、**版本化 Rubric**（评审口径）。模型不得把通用测试经验伪装成产品业务事实（见 §7）。

## 2. 三个维度

| 维度 | 代码 | 主攻角色 | 关注点 |
|---|---|---|---|
| 业务/需求 | `business` | 陪审甲（deepseek-flash） | 测的是不是该测的东西、规则对不对、前置是否成立 |
| 测试设计 | `test_design` | 陪审乙（kimi-k3） | 步骤能不能执行、预期能不能判定、数据全不全、分支够不够 |
| 自动化可行性 | `automation` | 陪审乙（kimi-k3） | 步骤能否被自动化、依赖能否获取、定位是否可维护 |

主审（qwen-max）**三个维度全评**；两名陪审以各自主攻维度做深，同时允许对其他维度提出问题（权重低，但不禁止）。

### 2.1 业务评审维度映射

`docs/00` §5.2 定义 11 个**业务评审维度**；本文件用 3 个评分维度（business / test_design / automation）承载它们。两者不是同一层概念，映射关系必须显式维护：

| # | 业务评审维度（`docs/00` §5.2） | Rubric 检查点 | 主要问题分类 | 说明 |
|---|---|---|---|---|
| 1 | 需求一致性 | B3 | `规则冲突` | 预期与需求/业务规则冲突 |
| 2 | 测试目标明确性 | B1 | `意图不符` | 实际验证内容与标题/功能点不一致 |
| 3 | 前置条件合理性 | B4 | `前置不足` | 前置缺失或不可达成 |
| 4 | 测试步骤可执行性 | T1 | `步骤不可执行` | 步骤不是单一、具体、可执行动作 |
| 5 | 预期结果明确性 | T2 | `预期不明确` | 预期不可观察、不可判定 |
| 6 | 边界条件考虑 | T5 | `边界缺失` | 边界值/临界状态未覆盖 |
| 7 | 异常场景考虑 | T5 | `边界缺失` | 失败路径、异常输入未覆盖；与第 6 项共用检查点，按问题描述区分 |
| 8 | 业务规则覆盖 | B2 / B3 | `覆盖缺失` / `规则冲突` | 规则明确要求验证的关键行为未覆盖 |
| 9 | 数据合理性 | T4 | `数据缺失` | 测试数据缺失、矛盾或不可获得 |
| 10 | 重复与冗余 | T8 | `重复冗余` | 无意义的重复用例或重复步骤 |
| 11 | 自动化可行性提示 | A1–A6 | `自动化不可行` / `状态不可读` / `定位不稳定` / `数据不可准备` / `框架不匹配` | 只给可行性与限制判断，不承诺脚本生成或执行 |

规则：

- 每个业务维度至少映射到一个检查点；新增/删除维度必须同时修改 `docs/00` §5.2 与 `rubric/rubric.yaml`，否则 `scripts/check_rubric.py` 失败。
- 同一检查点可承载多个业务维度（如 T5），但问题分类与描述必须能让读者区分。
- 业务维度是评审目标，评分维度是组织方式；投票与严重级仍按 `docs/12` 计算，不因映射表改变。

## 3. 检查点清单

### 3.1 业务/需求维度（B）

| ID | 检查点 | 典型问题 |
|---|---|---|
| B1 | **用例意图一致**：用例实际验证的内容与标题/所属功能点一致 | 标题写"藏宝点发现"，步骤却在测按钮动效 |
| B2 | **关键分支覆盖**：在本用例声称的场景范围内，关键分支/状态是否都有对应用例步骤 | 只测成功路径，未测背包满、无藏宝点、重复点击 |
| B2.1 | **（v1.5 预留）功能点覆盖**：对照 `required_scenarios` 判断整个功能点是否有场景缺口；v1 仅允许指出"当前用例未覆盖某已列场景"，不输出覆盖结论 | 功能点要求覆盖并发，但 5 条关联用例全无并发场景 |
| B3 | **业务规则正确性**：预期结果与知识库规则是否冲突 | 知识库写明冷却 30 秒，用例预期可连续挖掘 |
| B4 | **前置条件充分**：等级、帮会、货币、道具、任务状态等业务前置是否写明且真实可达成 | 写"拥有帮会"但未说明如何获得帮会 |
| B5 | **术语与命名一致**：使用产品正式术语，不臆造功能名 | 把"藏宝点"写成"宝箱点" |
| B6 | **业务状态一致性**：步骤间的状态流转是否自洽 | 第 2 步已丢弃道具，第 4 步却要求使用该道具 |

### 3.2 测试设计维度（T）

| ID | 检查点 | 典型问题 |
|---|---|---|
| T1 | **步骤可执行**：每步是单一、具体、可执行的动作 | "检查界面是否正常"不是动作 |
| T2 | **预期可判定**：预期结果是可观察、可比较的明确现象 | "显示正常""无明显异常""效果符合预期" |
| T3 | **步骤-预期对应**：每个 action 有对应预期，不多不少 | 第 3 步无预期；或一步列了五个预期 |
| T4 | **测试数据齐备**：需要具体数值/道具/坐标的地方给出具体值或来源 | "传入任意物品" |
| T5 | **边界与异常覆盖**：在场景范围内覆盖边界值、失败路径、重复操作 | 只测 1 个物品，不测 0 个/满背包 |
| T6 | **可重复执行**：用例可独立重复运行，含环境重置/清理步骤 | 依赖上一次执行遗留状态 |
| T7 | **无歧义**：不存在两种以上合理解读 | "点击右侧按钮"但界面有多个右侧按钮 |
| T8 | **无重复冗余**：不存在无意义的重复步骤、重复断言或与验证目标无关的复制内容 | 同一断言重复写 5 次；整段复制上一用例步骤 |

### 3.3 自动化可行性维度（A）

| ID | 检查点 | 典型问题 |
|---|---|---|
| A1 | **步骤可自动化**：不做人工目测/人工判断/主观感受 | "观察画面是否流畅" |
| A2 | **状态可获取**：断言所需状态能被程序读取，而非只能靠截图肉眼判断 | 只能通过 UI 截图判断物品数量 |
| A3 | **定位可维护**：元素定位方式稳定，不依赖硬编码坐标或易变文案 | 写死坐标 (312,480) 且无容错 |
| A4 | **数据可准备/清理**：测试数据能程序化生成与回收 | 需要人工找策划要道具 |
| A5 | **执行稳定性**：无长等待、无强依赖外部随机事件且无重试设计 | 等待 10 分钟刷新、依赖随机掉落 |
| A6 | **框架能力匹配**：与 `automation_context` 描述的能力边界一致，超出部分需显式说明替代方案 | 无自动寻路却写"自动走到藏宝点" |

## 4. 严重级定义

| 级别 | 代码 | 判据 | 例子 |
|---|---|---|---|
| **阻断** | `blocker` | 用例无法执行、预期无法判定、或与知识库规则直接冲突 | 关键步骤缺失；预期为"显示正常"；规则写错导致结论必错 |
| **重要** | `major` | 明显降低用例有效性，但执行者能靠经验补全 | 测试数据未给出具体值；缺少失败路径；前置条件不全 |
| **建议** | `suggestion` | 可读性、规范性、优化类 | 术语不统一；步骤描述可更精炼 |

判定原则：
- 拿不准时**降一级**（宁可标 `major`，不要轻易标 `blocker`），但**可以标建议级存疑**。
- 同一处存在多个问题时，按**最高级别**记一条，不重复堆叠。
- 一条 issue 只对应一个问题；复合问题拆成多条。

## 6. 各角色权重

| 角色 | business | test_design | automation | 说明 |
|---|---|---|---|---|
| 主审盲评 | 1.0 | 1.0 | 1.0 | 全维度等权 |
| 陪审甲 | **2.0** | 0.5 | 0.5 | 业务视角主攻，其余可提但从严 |
| 陪审乙 | 0.5 | **1.5** | **1.5** | 测试设计与自动化主攻 |

> **权重只表示专业分工与提示重点，不参与投票计数。**
>
> - 盲评阶段：权重影响主攻维度、检查点顺序与建议排序；
> - 候选问题投票：三方**严格等权，一方一票**；
> - 成立性：按票数规则计算，不乘权重；
> - 严重级：只统计明确 `accept` 的票，不乘权重；
> - 主审仲裁：有解释与取舍权，但不能修改投票记录。
>
> 修改 Rubric 权重不得改变投票权重；如果确实需要改变票权，必须作为独立决策并更新 `docs/02`/`docs/07` 的统计口径。

**投票与置信度分开**：支持/反对/未评估/不确定的计数是事实（见 `docs/02` `issue_votes`），置信度是经黄金集校准后的派生值。**不得**把"1 方支持 0.6、2 方 0.85、3 方 0.95"当作规则；未校准时报告只展示计数与 `support_ratio`。

## 7. 依据、证据与结论强度

### 7.1 三类依据

| 依据 | 作用 | 缺失时 |
|---|---|---|
| **用例** | 被评审对象 | 无法评审，直接拒绝请求 |
| **知识库**（业务规则 / 功能说明 / 已知限制 / 历史缺陷 / 术语） | 判断业务事实是否成立 | 降级为推断，`kb_grounded=false` |
| **版本化 Rubric** | 维度、判定标准、严重级、输出规则 | 用仓库当前版本评审，版本号写入报告 |

模型只能依据这三类信息判断。**通用测试设计经验可以用于提建议，但不能当作产品业务事实**；两者必须在报告里可区分。

### 7.2 证据规则（所有角色通用）

1. **`evidence_quote` 必须是用例原文的逐字摘录**，不得改写、不得拼接。
2. **`kb_grounded=true` 必须同时给出 `kb_refs` 与 `evidence_refs`**（至少一条可溯源知识），否则视为无效依据。
3. 知识库无依据时，**允许**基于通用测试准则提出问题，但必须 `kb_grounded=false`，并在 `rationale` 中注明"（基于通用测试准则推断）"。
4. **禁止编造产品规则**。知识库里没有的规则，不得作为"规则冲突"的依据。
5. 涉及具体数值（冷却时间、概率、上限）而无知识库依据时，只能标为 `suggestion` 级"建议确认"，不得标 `blocker`。
6. **引用必须真实存在**：`kb_refs` / `evidence_refs` 指向的条目必须出现在本次注入的证据包内；引用不存在的知识、或引用内容与结论不匹配，该条判为无效依据（进入 Citation Accuracy 评测）。

### 7.3 结论强度限制

| 缺失条件 | 允许输出 | 禁止输出 |
|---|---|---|
| 无 `test_scope` | 单条用例内部的覆盖问题（B2） | "整个功能点缺少某类场景"（B2.1 不可用） |
| 无 `automation_context` | "该步骤难以自动化，需确认框架能力"（≤ major） | 断言"无法自动化"/"框架不支持"（A6 不可用） |
| 无知识库依据 | 测试设计类建议（suggestion / major） | 业务规则冲突（blocker） |
| 检索链路降级 | 基于现有证据的结论 + 报告顶部提示 | 把"检索残缺"表述为"知识库确认" |

> 规则的目的不是让模型少说话，而是让结论强度与证据强度匹配：**证据不足时降级表述，而不是降级为不提问题**。

### 7.4 证据类型与强度

知识库里的内容不是同等强度的事实，先分级再决定能下多强的结论：

| 级别 | `evidence_type` | 来源 | 能支撑什么 | 默认强度 |
|---|---|---|---|---|
| E1 | `business_rule` | 规则库（RULE-*）/ 验收标准 | 业务规则冲突、行为判定 | strong |
| E2 | `requirement` / `known_limit` / `historical_bug` | 需求、功能说明、已知限制、历史缺陷 | 需求符合性、适用范围；历史缺陷只能提示"曾出现" | strong / medium / weak |
| E3 | `testing_standard` | 测试规范 / Rubric 建议 | 测试设计建议 | medium |
| E4 | `inference` | 模型基于上下文的推断 | 只能作为待确认线索 | weak |

硬性约束：

1. **无 E1/E2 依据时，不得判业务规则冲突或 blocker**；只能作为待确认建议。
2. **`historical_bug` 不能证明当前版本仍存在该缺陷**；只能写"历史曾出现，需确认当前版本"，不得直接判 `规则冲突` / `blocker`。
3. **`testing_standard` 不是产品事实**，只能支撑测试设计建议，不能支撑"业务规则错误"。
4. **`inference` 必须 `kb_grounded=false`**，并在 `rationale` 标注推断。
5. 一个 issue 的 `evidence_type` 取**最强**的一条证据；`evidence_strength` 随类型与来源版本确定。
6. 引用历史缺陷/已知限制时，必须同时给出 `valid_from_version` / `applicable_conditions`；缺版本则降为 `weak`。
7. **同级权威规则冲突**（两条 E1 对同一行为有不同规定）：模型不得自行选一条当事实；记录双方证据，结论标 `need_human`。
8. **检索未召回不等于规则不存在**：不得把"知识库没找到"写成"规则缺失"或"业务规则错误"。

### 7.4.1 证据冲突与时效

冲突判定顺序固定，不允许模型自行挑"更符合自己观点"的证据：

1. 先看 `rule_status`：`deprecated` 不进入当前有效证据；`draft`/`reviewed` 不得当权威依据。
2. 再看适用性：`valid_from/to_version`、`effective_from/to`、`applicable_conditions` 是否覆盖当前用例。
3. 再看等级：E1 > E2 > E3 > E4；E4 不能单独支撑任何业务结论。
4. 同级冲突（两条 E1 对同一行为规定不同）：记录双方证据与来源，结论标 `need_human`。
5. E1 与 E2 冲突：以 E1 为准但必须提示"需求与规则不一致，需确认哪份为准"；不能直接判用例错误。
6. 无法确定优先级：`need_human`，不得猜测。

**历史缺陷**只能作为风险提示、相似场景线索或重点验证建议；不能单独证明当前缺陷，也不能单独支撑 `blocker`。

### 7.4.2 融合后的证据归属

- 证据绑定到 **claim（主张）**，不是绑定到"融合后的问题"。
- 合并两个问题不会自动合并证据强度：A 有规则依据、B 没有，合并后只能标 `partially_grounded`，不能标 `grounded`。
- 证据状态：`grounded` / `partially_grounded` / `ungrounded` / `conflicted` / `insufficient`。
- `conflicted` 或 `insufficient` 不得判 `blocker`；`ungrounded` 不得判业务规则冲突。
- 仲裁可以补充证据，但必须记录来源与 claim 对应关系，不得把补充证据回溯成原始依据。

**融合不得自动提高证据强度。** 这是硬规则。

合并前必须同时满足 **Claim 一致**、**Evidence 指向同一规则/约束**、**Root Cause 一致**；任一不满足则保留独立候选，交投票或人工。仅文本相似不得合并。

`partially_grounded` 的 blocker：报告可以为 `blocked`，但必须进人工复核清单并标注"证据部分支持"；不得通过降级为 `major` 规避复核。

## 8. 结论规则（仲裁使用）

> 完整输入组合、2/3 与 1/3 处理、禁止组合见 `docs/12-评审决策真值表.md`；本节为摘要，最终由 `verdict.py` 执行。

```
成立性：
  ≥2 明确 accept 且 <2 明确 reject        → accepted
  ≥2 明确 reject                         → rejected
  其余（uncertain/not_assessed 占多）     → disputed / need_human

严重级（仅统计 accept 票）：
  取最高级别为终值
  最高与最低相差 ≥2 级（blocker vs suggestion）→ severity_disputed → need_human
  blocker 终值需同时满足：accepted + severity=blocker + 无 ≥2 reject

结论：
  存在按上述口径成立的 blocker，且未被 ≥2 明确 reject → blocked
  主审驳回陪审提出的 blocker，两陪审均未同意驳回     → blocked（标注"待人工裁决"）
  无 blocker 且存在 disputed / severity_disputed      → need_human
  无 blocker 且无 disputed                            → conditional
  系统永不输出 approved（人工批准是独立状态，不改变 AI 结论）
```

"否决"只统计显式 `reject`：`not_assessed` 与 `uncertain` 都不算否决票。结论由服务端按 `docs/01` §7 重算，模型输出的 `ai_verdict` 仅作对照。

**成立性与严重级必须分开**：不认同严重级别不得因此否定问题成立；严重级分歧也不覆盖原始投票。主审把 blocker 降级时，服务端强制转人工复核，模型不能取消。

**AI 结论与人工决定分离**：`ai_verdict` 只有 `blocked/conditional/need_human`；`human_status`（`pending/approved/rejected/changes_requested`）由 `review_decisions` 派生。人工批准不把 `ai_verdict` 改成 `approved`，也不消除降级标记（见 `docs/09`）。

## 9. Rubric 配置文件

> 机器可执行事实源已落地到 `rubric/rubric.yaml`（含 `schema.json` 与 `versions/`）。本节是结构说明，实际加载以仓库文件为准；两者不一致时以 `rubric/rubric.yaml` 为准并修本文。
>
> Rubric 版本使用 SemVer；当前 `0.2.0` 为 `draft`，**正式评审只允许使用 `published` 版本**。任务创建时冻结 `rubric_version`，执行中不因配置更新而改变。
>
> **版本绑定规则**（补充 15 P0-1）：
> - 当前 `rubric.version` 必须有对应的 `rubric/versions/v<version>.yaml` 冻结副本；缺失即校验失败。
> - 验收用例与服务端都必须从主配置读取版本号，再定位副本，**不得硬编码历史版本路径**。
> - 报告写入本次实际使用的 `rubric_version`；历史报告按当时的版本副本解释，不因新版本发布而改变。
> - 修改规则必须递增版本并新增副本；禁止原地修改已冻结副本（`rubric/README` §规则）。
> - `scripts/check_rubric.py` 校验副本存在/一致，并扫描 `design/` 是否硬编码了非当前版本。

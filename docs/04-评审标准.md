# 04 · 评审标准（Rubric）

## 1. 评审对象与边界

评审的是**用例质量**，不是功能实现质量。禁止评价：代码、性能、美术表现、剧情文案、实现难度。

一句判据：**这份用例能不能让另一个不了解该功能的人，原样执行并明确判断通过/不通过。**

## 2. 三个维度

| 维度 | 代码 | 主攻角色 | 关注点 |
|---|---|---|---|
| 业务/需求 | `business` | 陪审甲（deepseek-flash） | 测的是不是该测的东西、规则对不对、前置是否成立 |
| 测试设计 | `test_design` | 陪审乙（kimi-k3） | 步骤能不能执行、预期能不能判定、数据全不全、分支够不够 |
| 自动化可行性 | `automation` | 陪审乙（kimi-k3） | 步骤能否被自动化、依赖能否获取、定位是否可维护 |

主审（qwen-max）**三个维度全评**；两名陪审以各自主攻维度做深，同时允许对其他维度提出问题（权重低，但不禁止）。

## 3. 检查点清单

### 3.1 业务/需求维度（B）

| ID | 检查点 | 典型问题 |
|---|---|---|
| B1 | **用例意图一致**：用例实际验证的内容与标题/所属功能点一致 | 标题写"藏宝点发现"，步骤却在测按钮动效 |
| B2 | **关键分支覆盖**：在本用例声称的场景范围内，关键分支/状态是否都有对应用例步骤 | 只测成功路径，未测背包满、无藏宝点、重复点击 |
| B3 | **业务规则正确性**：预期结果与知识库规则是否冲突 | 知识库写明冷却 30 秒，用例预期可连续挖掘 |
| B4 | **前置条件充分**：等级、帮会、货币、道具、任务状态等业务前置是否写明且真实可达成 | 写"拥有帮会"但未说明如何获得帮会 |
| B5 | **术语与命名一致**：使用产品正式术语，不臆造功能名 | 把"藏宝点"写成"宝箱点" |
| B6 | **业务状态一致性**：步骤间的状态流转是否自洽 | 第 2 步已丢弃道具，第 4 步却要求使用该道具 |

### 3.2 测试设计维度（T）

| ID | 检查点 | 典型问题 |
|---|---|---|
| T1 | **步骤可执行**：每步是单一、具体、可执行的动作 | "检查界面是否正常"不是动作 |
| T2 | **预期可判定**：预期结果是可观察、可比较的明确现象 | "显示正常""无明显异常""效果符合预期" |
| T3 | **步骤-预期对应**：每个 action 有对应预期，不多不少 | 第 3 步无预期；或一步列了五个预期 |
| T4 | **测试数据齐备**：需要具体数值/道具/坐标的地方给出具体值或来源 | "传入任意物品" |
| T5 | **边界与异常覆盖**：在场景范围内覆盖边界值、失败路径、重复操作 | 只测 1 个物品，不测 0 个/满背包 |
| T6 | **可重复执行**：用例可独立重复运行，含环境重置/清理步骤 | 依赖上一次执行遗留状态 |
| T7 | **无歧义**：不存在两种以上合理解读 | "点击右侧按钮"但界面有多个右侧按钮 |

### 3.3 自动化可行性维度（A）

| ID | 检查点 | 典型问题 |
|---|---|---|
| A1 | **步骤可自动化**：不做人工目测/人工判断/主观感受 | "观察画面是否流畅" |
| A2 | **状态可获取**：断言所需状态能被程序读取，而非只能靠截图肉眼判断 | 只能通过 UI 截图判断物品数量 |
| A3 | **定位可维护**：元素定位方式稳定，不依赖硬编码坐标或易变文案 | 写死坐标 (312,480) 且无容错 |
| A4 | **数据可准备/清理**：测试数据能程序化生成与回收 | 需要人工找策划要道具 |
| A5 | **执行稳定性**：无长等待、无强依赖外部随机事件且无重试设计 | 等待 10 分钟刷新、依赖随机掉落 |
| A6 | **框架能力匹配**：与现有自动化框架的能力边界一致，超出部分需显式说明替代方案 | 无自动寻路却写"自动走到藏宝点" |

## 4. 严重级定义

| 级别 | 代码 | 判据 | 例子 |
|---|---|---|---|
| **阻断** | `blocker` | 用例无法执行、预期无法判定、或与知识库规则直接冲突 | 关键步骤缺失；预期为"显示正常"；规则写错导致结论必错 |
| **重要** | `major` | 明显降低用例有效性，但执行者能靠经验补全 | 测试数据未给出具体值；缺少失败路径；前置条件不全 |
| **建议** | `suggestion` | 可读性、规范性、优化类 | 术语不统一；步骤描述可更精炼 |

判定原则：
- 拿不准时**降一级**（宁可标 `major`，不要轻易标 `blocker`），但**可以标建议级存疑**。
- 同一处存在多个问题时，按**最高级别**记一条，不重复堆叠。
- 一条 issue 只对应一个问题；复合问题拆成多条。

## 5. 问题分类（category 枚举）

| 代码 | 名称 | 归属维度 |
|---|---|---|
| `覆盖缺失` | 覆盖缺失 | business / test_design |
| `规则冲突` | 与业务规则冲突 | business |
| `意图不符` | 用例意图不符 | business |
| `前置不足` | 前置条件不足 | business |
| `术语不一致` | 术语/命名不一致 | business |
| `状态不自洽` | 步骤间状态不自洽 | business |
| `步骤不可执行` | 步骤不可执行 | test_design |
| `预期不明确` | 预期不可判定 | test_design |
| `数据缺失` | 测试数据缺失 | test_design |
| `边界缺失` | 边界/异常未覆盖 | test_design |
| `不可重复` | 不可独立重复执行 | test_design |
| `歧义` | 描述有歧义 | test_design |
| `自动化不可行` | 步骤无法自动化 | automation |
| `状态不可读` | 断言依赖不可读状态 | automation |
| `定位不稳定` | 元素定位不可维护 | automation |
| `数据不可准备` | 数据无法程序化准备 | automation |
| `框架不匹配` | 超出框架能力 | automation |

## 6. 各角色权重

| 角色 | business | test_design | automation | 说明 |
|---|---|---|---|---|
| 主审盲评 | 1.0 | 1.0 | 1.0 | 全维度等权 |
| 陪审甲 | **2.0** | 0.5 | 0.5 | 业务视角主攻，其余可提但从严 |
| 陪审乙 | 0.5 | **1.5** | **1.5** | 测试设计与自动化主攻 |

> 权重不参与问题是否成立的判定，只影响**同一问题被多少方提出**时的置信度与排序；`proposed_by` 只记录提出方，不记权重。

## 7. 证据规则（所有角色通用）

1. **`evidence_quote` 必须是用例原文的逐字摘录**，不得改写、不得拼接。
2. **`kb_grounded=true` 必须同时给出 `kb_refs`**（至少一条 RULE-ID 或文档 ID），否则视为无效依据。
3. 知识库无依据时，**允许**基于通用测试准则提出问题，但必须 `kb_grounded=false`，并在 `rationale` 中注明"基于通用测试准则推断"。
4. **禁止编造产品规则**。知识库里没有的规则，不得作为"规则冲突"的依据。
5. 涉及具体数值（冷却时间、概率、上限）而无知识库依据时，只能标为 `suggestion` 级"建议确认"，不得标 `blocker`。

## 8. 结论规则（仲裁使用）

```
若 存在 blocker 且 未被 ≥2 方否决            → blocked
若 主审驳回 blocker 且 两陪审均未同意驳回      → blocked（标注"待人工裁决"）
若 无 blocker 且 存在 disputed 或 参与模型 < 3 → need_human
若 无 blocker 且 无 disputed                  → conditional
系统永不输出 approved（通过只能由人工复核产生）
```

## 9. Rubric 配置文件形态（草稿）

```yaml
# rubric/rubric.yaml
version: 1
dimensions:
  business:
    name: 业务/需求
    owner: jury_a
    weights: { chief: 1.0, jury_a: 2.0, jury_b: 0.5 }
    checkpoints:
      - { id: B1, name: 用例意图一致 }
      - { id: B2, name: 关键分支覆盖 }
      # ...
  test_design:
    name: 测试设计
    owner: jury_b
    weights: { chief: 1.0, jury_a: 0.5, jury_b: 1.5 }
    checkpoints:
      - { id: T1, name: 步骤可执行 }
      # ...
  automation:
    name: 自动化可行性
    owner: jury_b
    weights: { chief: 1.0, jury_a: 0.5, jury_b: 1.5 }
    checkpoints:
      - { id: A1, name: 步骤可自动化 }
      # ...
severity:
  blocker: "无法执行 / 无法判定 / 与知识库规则直接冲突"
  major:   "明显降低有效性，执行者可凭经验补全"
  suggestion: "可读性、规范性、优化类"
categories:
  覆盖缺失: { dimensions: [business, test_design] }
  规则冲突: { dimensions: [business] }
  # ...
conclusion_rules:
  auto_pass: false
  blocker_majority_reject_threshold: 2   # 3 方中至少 2 方同意驳回
  chief_reject_requires_human_review: true
  chief_supplement_blocker_requires_human_review: true
```

## 10. 评审口径示例（供 prompt 对齐）

| 用例原文 | 判定 | 理由 |
|---|---|---|
| "点击【发现】按钮，获得随机物品并进入背包" | `blocker` / 预期不明确 | 无法判定"随机物品"是否正确，无物品池范围、无数量断言 |
| "点击【开始挖宝】后生成藏宝点" | `major` / 预期不明确 | 未说明藏宝点位置是否可见、是否在地图上限内 |
| "使用坐标传送至洛阳 (312,480)" | `suggestion` / 自动化建议 | 硬编码坐标可维护性差，建议参数化 |
| "背包满时挖宝应提示无法获得" | 无需提问 | 预期明确、可判定、规则清晰 |
| "检查界面显示是否正常" | `blocker` / 步骤不可执行 | 非具体动作，且无判定标准 |

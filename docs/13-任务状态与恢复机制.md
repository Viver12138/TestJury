# 13 · 任务状态与恢复机制

> 版本：v0.8 · 2026-11-10（v0.8：跨文档冲突清理与 P0 决策冻结）
> 目的：明确异步任务的执行状态、阶段 Checkpoint、超时、租约、重试与崩溃恢复，避免重复执行与重复终稿。
> 关联：01 §9、02 `review_jobs`/`review_stages`、10 §8、12。

---

## 1. 状态机

| 当前 | 允许转到 | 触发 |
|---|---|---|
| `queued` | `processing` | Worker 领取（硬校验已在 API 层完成，入队后不因字段非法失败） |
| `processing` | `retrying` / `done` / `completed_with_warnings` / `failed` | 阶段失败待重试 / 成功 / 降级完成 / 不可恢复 |
| `retrying` | `processing` / `failed` | 重试领取 / 超过最大次数 |
| 租约过期的 `processing` | `queued`（或 `retrying`） | 恢复任务重新入队 |
| `done` / `completed_with_warnings` / `failed` | 无（终态） | — |

- 终态不可回到 `processing`；重评必须新建 `generation`（`parent_review_id` 指向旧记录）。
- v1 不提供主动取消；需要终止只能等超时/失败（取消接口列入 v1.5）。
- 状态转换由服务端校验，非法转换直接拒绝并告警。

## 2. 阶段与 Checkpoint

阶段固定为：

```
INPUT_CHECK → PREPROCESS → KB_RETRIEVE → BLIND_REVIEW → FUSION
→ VOTE → ARBITRATION → VERDICT → RENDER
```

每个阶段在 `review_stages` 落**当前状态**行，每次尝试在 `review_stage_attempts` 落**历史**行（`attempt_no`、`input_digest`、`output_ref`、`error_code`、`worker_id`、`model_run_id`）。当前态被重试覆盖时，历史仍可查。

规则：

- 阶段成功即写 `succeeded`，并保存可复用的输出（如 `blind_review` 的三份原始输出、`fusion` 的候选清单）。
- 重试从**最后成功的阶段之后**恢复；已成功阶段不重跑（除非其输入版本变化）。
- 投票阶段失败不重跑预处理与盲评；仲裁失败不重跑投票。
- `output_ref` 指向 `model_runs` / `review_candidates` / `report_json`，不复制大文本。
- 重复执行同一阶段时，先检查 `review_stages.status`，已成功则跳过。

## 3. 超时分层

| 层次 | 默认 | 说明 |
|---|---|---|
| 单次模型调用 | 120s（embedding 30s、rerank 20s） | 单请求上限 |
| 阶段超时 | 预处理 60s、盲评 240s、投票 180s、仲裁 180s、渲染 30s | 阶段总时长，含重试 |
| 任务总超时 | 20 分钟 | 含阶段与重试，不含排队；阶段合计 690s，15 分钟不够 |
| Worker 租约 | 5 分钟 | 心跳每 60s 续租；租约 < 任务超时，避免"死任务"长期占用 |

> 8 次模型调用 × 120s + 重试已超过 10 分钟；阶段合计 690s，v1 默认任务总超时 20 分钟（含阶段与重试，不含排队），压测后校准。

## 4. 重试

| 层级 | 次数 | 策略 |
|---|---|---|
| 单次调用 | 2 | 超时/5xx/限流退避重试；4xx 不重试 |
| 阶段 | 2 | 仅对可重试错误；记录 `attempt` |
| 任务 | 3（`max_attempts`） | 超过后 `failed`，保留已完成阶段输出 |

- 重试产生新的 `model_runs`（`attempt` 递增），不复用旧调用记录。
- 重试不得重复写入投票/候选；写入前按 `(candidate_id, reviewer_id)` 幂等。
- 重试前检查 `review_stages`，从失败阶段恢复。

## 5. 租约与崩溃恢复

1. 领取：`SELECT ... FOR UPDATE SKIP LOCKED`，写 `locked_by`、`locked_at`、`lease_expires_at`。
2. 执行：每 60s 续租；续租失败（失去租约）立即停止写入终稿。
3. 崩溃：租约过期后任务回到可领取；新 Worker 读取 `review_stages` 从最后成功阶段继续。
4. 终稿保护：写入前校验 `status`、`attempt`、`generation` 与 `locked_by`；已存在终稿则丢弃并记录冲突。
5. 同一任务重复领取不得产生两份有效终稿；以 `review_jobs.id` 为幂等边界。

### 5.1 恢复时的版本冻结

任务创建时冻结：`kb_version`、`rubric_version`、`prompt_versions`、`model_config_version`、`retrieval_config_version`、`embedding_profile_id`、`reranker_profile_id`、`report_schema_version`、`input_hash`、`case_version`、`fallback_model_policy`。

- 恢复只读这些版本，**不得**切到当前 active KB/Prompt/模型。
- 冻结版本不可用 → `failed(VERSION_UNAVAILABLE)`，不静默使用新版本。
- `input_digest` 覆盖阶段依赖：用例摘要、上游输出摘要、Prompt/模型/KB/检索/Rubric 版本。
- 摘要不一致 → 新 generation / 重跑该阶段 / 拒绝恢复，三选一，不能静默复用旧输出（见 `docs/22`）。

## 6. 幂等

- 提交幂等：`idempotency_key`（输入 + 版本组合）；`force=true` 新建 generation。
- 阶段幂等：同阶段同输入只写一次；`input_digest` 变化才重跑。
- 投票幂等：`UNIQUE(candidate_id, reviewer_id)`；重复投票以首次为准，后续拒绝或覆盖需显式策略（v1 以首次为准）。
- 终稿幂等：`report_json` 与 `issues` 同事务写入；已存在则跳过。

## 7. case 版本与评审代次

两个概念必须分开：

| 概念 | 字段 | 含义 |
|---|---|---|
| 用例内容版本 | `case_version` | 同一 `case_id` 的内容修改版本 |
| 评审运行代次 | `generation` | 同一输入/配置下第几次评审（force 重跑） |

- 用例实质修改（步骤/预期/前置/测试数据）→ `case_version+1`，并作为新的 `input_hash` 输入。
- 仅改备注/标题措辞是否升版：由调用方决定并在请求中声明；服务端不猜。
- 同一 `case_version` + 相同配置重复提交 → 幂等命中；`force` → 新 `generation`。
- 报告始终关联当时的 `case_version`；不允许用新版本覆盖旧评审上下文。

## 8. 批量任务

- 子任务独立执行，部分失败不影响其他子任务。
- 批次状态：`queued` / `processing` / `completed` / `partially_completed` / `failed` / `cancelled`。
- 部分失败时保留成功结果；失败子任务可单独重跑（新 generation）。
- 批次统计按子任务终态汇总；重跑后更新计数，不覆盖历史批次记录。

## 9. 监控与告警

- 队列深度、租约过期数、阶段失败率、P95 各阶段耗时、重试率、2/3 与 1/3 占比。
- 同一任务连续失败 3 次、租约频繁过期、阶段耗时突增 → 告警。
- 告警只提示，不自动改状态。

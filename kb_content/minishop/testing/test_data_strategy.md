# 1. 数据策略目标

让交易域用例：

- 可重复执行，不依赖执行顺序；
- 不污染共享库；
- 不硬编码自增 ID；
- 对库存、券有效期、订单状态有明确初始值；
- 失败后可定位是数据问题还是产品问题。

# 2. 种子数据基线

## 2.1 账号

| 用户名 | 密码 | 角色 |
|---|---|---|
| `admin` | `admin123` | `ADMIN` |
| `user` | `123456` | `USER` |

## 2.2 商品/SKU 选择矩阵

| 用途 | 商品 | 原因 |
|---|---|---|
| 正常下单 | 机械键盘（399，库存 50） | 库存充足、单价适中 |
| 高价订单 | MacBook（8999，库存 8） | 触发高价/大额券 |
| 低价订单 | 咖啡（59，库存 100） | 低价、无规格 |
| 售罄 | 无线鼠标（199，库存 0） | 库存为 0 的拒绝路径 |
| 库存边界 | 蓝牙耳机（599，库存 1） | 买 1 成功、买 2 失败 |
| 多规格 | 运动鞋（499，8 个 SKU，库存 1–2） | SKU 选择、独立库存、并发 |
| 高库存 | 小米手机（2999，库存 10） | 退款恢复库存断言 |

## 2.3 优惠券基线

| 名称 | 门槛 | 优惠 | 当前库状态 |
|---|---:|---:|---|
| 新人满100减10 | 100 | 10 | 已过期（2026-10-21） |
| 满1000减100 | 1000 | 100 | 可用至 2026-11-20 |
| 满5000减500 | 5000 | 500 | 可用至 2026-12-20 |
| 满50减5(已过期) | 50 | 5 | DISABLED |

# 3. 数据隔离策略

| 级别 | 做法 | 适用 |
|---|---|---|
| 数据库级 | `DATABASE_URL=sqlite:///./verify.db`，每轮删除重建 | 全量回归、e2e |
| 用户级 | 每次注册唯一用户（如 `tc_<timestamp>_<rand>`） | 并行用例、避免串数据 |
| 商品级 | 不同用例选择不同 SKU | 减少库存互相影响 |
| 订单级 | 每用例独立创建订单，不共用订单 | 状态推进互不干扰 |
| 券级 | 每次领取独立券；必要时后台建券 | 门槛/过期/停用场景 |

推荐组合：**独立库 + 独立用户 + 独立 SKU**。仅用户级隔离不足以避免库存/券的相互影响。

# 4. 数据准备配方

## 4.1 正常可支付订单

1. 登录 `user`；
2. 创建地址；
3. 查询机械键盘 SKU；
4. 预览 → 创建订单；
5. 记录 `order_id`、`pay_amount`；
6. 不支付，作为 `PENDING_PAYMENT` 基线。

## 4.2 已支付订单

在 4.1 基础上：

1. `POST /api/payments`；
2. `POST /api/payments/{id}/success`；
3. 断言订单 `PAID`，记录支付前后库存。

## 4.3 已发货订单

在 4.2 基础上：

1. 使用 `admin` token；
2. `POST /api/admin/orders/{id}/ship`，填写物流信息；
3. 断言 `SHIPPED`。

## 4.4 已完成订单

在 4.3 基础上：

1. `POST /api/orders/{id}/confirm`；
2. 断言 `COMPLETED`。

## 4.5 退款相关订单（跨模块）

在 4.2 基础上调用 `POST /api/refunds`，订单进入 `REFUNDING`；本批不覆盖退款审核细节。

## 4.6 库存边界数据

- 售罄：无线鼠标，库存 0；
- 边界：蓝牙耳机，库存 1；
- 多规格：运动鞋，白 39/40 库存 1，其余 2。

## 4.7 优惠券数据

- 无券：不传 `user_coupon_id`；
- 未达门槛：用“满5000减500”买 399 元商品；
- 恰好达门槛：用“满1000减100”买总价恰好 1000 元；
- 已使用：先下一单用掉，再复用到另一单；
- 已过期：当前库“新人满100减10”已过期；
- 停用：当前库“满50减5”为 DISABLED，无法领取；
- 他人券：用户 A 领取，用户 B 使用 A 的用户券 ID。

# 5. 数据清理与重置

| 方式 | 命令/操作 | 说明 |
|---|---|---|
| 删除共享库 | 停服 → 删除 `Minishop/data/minishop.db` → 重启 | 不可撤销 |
| 删除独立库 | 停服 → 删除 `Minishop/backend/verify.db` | 推荐每轮重建 |
| 清理测试用户 | 无删除用户接口 | 只能重置数据库 |
| 清理订单 | 无删除订单接口 | 只能重置数据库 |

当前没有测试数据管理 API，也没有软删除/归档接口。

> 注意（2026-11-11 实测）：当前种子库券#1 已过期，`e2e_test.py#L80-L81` 的“可领券>=3”与 `next(...)` 会失败（StopIteration）；执行前需重建数据库或动态取券。

# 6. 确定性与时间

- 订单号含时间戳 + 随机数，不固定；不要断言具体订单号，只断言格式/唯一性。
- 支付单号同理。
- 时间字段为 UTC naive；断言“非空/递增/顺序”而不是具体时间。
- 券有效期依赖播种日期；跨日期执行时必须动态判断。
- 库存/销量会随执行累积；跨用例断言必须使用“相对变化量”，不要断言绝对值（除非使用全新库）。

# 7. 并发与顺序

- SQLite 单文件，写并发能力有限；并发用例应使用独立库并串行复核结果。
- 超卖场景需要两个用户、同一 SKU、分别创建订单后依次支付；不要依赖真实并发时序。
- 重复支付/重复发货/重复确认可以用串行重复请求验证 409。

# 8. 敏感数据

- 种子账号是公开演示数据，不是真实凭据；
- 用例中不要写入真实手机号、真实地址、真实支付信息；
- 测试消息/日志中不要包含真实个人信息；
- 本知识库不包含任何生产密钥；`SECRET_KEY` 是开发默认值。

# 9. 数据缺口

- 无测试数据工厂/夹具；
- 无数据库迁移与 schema 版本；
- 无按用户/订单清理接口；
- 券发放量语义不清（见冲突 C-06），影响“领完”场景构造；
- 库存聚合字段可能与 SKU 之和不一致，断言时以 SKU 为准。

# 1. 测试范围与原则

## 范围

本规范适用于 `order` 试点模块及其前置依赖（登录、商品查询、购物车、地址、优惠券）的测试用例设计与评审。

## 原则

1. **显式选择评审基线**：选择 `current_implementation` 时，用冻结源码和可复核 API/数据观察描述当前行为；选择 `target_specification` 时，用已确认的目标规则判断预期。当前实现中的缺陷不能覆盖目标规则，页面文案或常识不能代替依据。
2. **可判定**：每条预期结果必须能落到 HTTP 状态码、`code`/`message`、字段值、数据库记录或页面可见状态。
3. **前置显式**：不得用“已登录”“有库存”等模糊描述，必须写明账号、角色、地址、订单状态、券状态、库存值。
4. **数据可复现**：优先使用独立库或独立用户，避免依赖执行顺序和历史残留。
5. **区分事实与推断**：知识库没有依据的行为，应标注“待确认”，不得写成强制预期。
6. **已知缺陷不反推规则**：当前实现缺陷（如单规格商品无法加购）应作为缺陷/限制记录，不应被写成“正确业务规则”。

# 2. 测试用例结构要求

每条用例至少包含：

| 字段 | 要求 |
|---|---|
| `case_id` | 稳定唯一，建议 `TC-ORDER-<序号>` |
| `title` | 一句话说明“在什么条件下验证什么行为” |
| `priority` | P0/P1/P2，P0 为主链路与资金/库存/权限 |
| `type` | 功能/边界/异常/权限/状态/并发/数据一致性 |
| `preconditions` | 账号、角色、地址、SKU、库存、券、订单状态、数据库初始值 |
| `steps` | 编号步骤，每步一个动作，注明 API 或 UI |
| `expected` | 每步可观察结果 + 最终状态 |
| `knowledge_refs` | 相关 `RULE-*`/`REQ-*`/`API-*`/`STATE-*` |
| `evidence` | 响应、SQL 结果、截图、日志中的至少一种 |

# 3. 前置条件规范

必须写清：

- 账号：用户名/角色/状态（`ACTIVE`/`DISABLED`），是否使用种子账号；
- 登录态：是否携带 token，token 是否过期；
- 地址：数量、是否默认、归属哪个用户；
- SKU：商品名、SKU 规格、价格、初始库存；
- 优惠券：模板 ID/名称、门槛、面额、有效期、用户券状态；
- 订单：当前状态、金额、是否已用券；
- 数据隔离：使用哪个数据库/是否已重置。

反例：`前置条件：用户已登录，购物车有商品` —— 不可接受。

正例：`前置条件：user/123456 已登录；地址 A 属于 user；机械键盘 SKU 库存 50；未领券；数据库为独立 verify.db`。

# 4. 测试步骤规范

- 一步一个动作，避免“下单并支付”合并；
- 标明通道：`API: POST /api/orders` 或 `UI: 购物车页点击“去结算”`；
- 请求体写关键字段，不写与用例无关的字段；
- 涉及状态推进时，逐步断言中间状态，不只看最终状态；
- 涉及异步/多请求时，写明顺序与等待条件。

# 5. 预期结果规范

必须可判定，建议同时给出：

| 层次 | 示例 |
|---|---|
| HTTP | `201`、`409` |
| 业务码 | `code=OK` 或 `code=HTTP_ERROR` |
| 消息 | `message=商品「机械键盘」库存不足` |
| 数据 | `orders.status=PENDING_PAYMENT`、`pay_amount=1187.0` |
| 副作用 | `product_skus.stock` 减少 3、`inventory_logs` 新增 1 条 |
| 页面 | 订单详情显示“已支付”标签、支付按钮消失 |

禁止：`显示正常`、`符合预期`、`金额正确`（未给计算方式）。

# 6. 测试数据规范

- 使用 `TEST-DATA` 中的种子基线与准备配方；
- 不硬编码自增 ID；通过名称/关键词查询获得 ID；
- 每次执行使用独立用户或独立数据库；
- 涉及库存的用例记录支付前后库存与销量；
- 涉及券的用例记录模板有效期与用户券状态；
- 时间相关断言使用服务端时间，不依赖本地时区显示；
- 不以 `e2e_test.py` 的执行结果替代用例断言（它是脚本，不是测试规范）。

# 7. 边界与异常覆盖要求

交易域用例至少覆盖以下维度：

## 7.1 数量与库存

- 数量 0、-1、1；
- 数量 = SKU 库存；
- 数量 = SKU 库存 + 1；
- 库存 0 的商品；
- 库存 1 的商品买 2；
- 同一 SKU 在 `items` 中重复出现（当前不合并，可能超库存）。

## 7.2 金额与优惠

- 无券；
- 券门槛前 0.01；
- 金额恰好等于门槛；
- 券面额大于总金额；
- 已使用/已过期/已停用/他人券；
- 券 `start_time` 在未来的情况（当前未校验，需确认）。

## 7.3 状态

- 待支付取消；
- 已支付取消（应拒绝）；
- 重复支付；
- 支付失败后重试；
- 未支付发货；
- 未发货确认收货；
- 重复发货/重复确认；
- 退款中订单发货/确认（当前拒绝）；
- 退款拒绝后的状态（当前回 `PAID`，需确认）。

## 7.4 权限

- 无 token（401）；
- 普通用户访问管理接口（403）；
- 他人订单详情（403）；
- 他人订单取消/确认（404）；
- 被禁用用户使用旧 token（403）。

## 7.5 数据一致性

- 创建订单不扣库存、不清购物车；
- 支付成功扣 SKU/商品库存、增销量、写日志；
- 取消归还券、`used_quantity` 回退；
- 重复支付不重复扣库存。

# 8. 证据与结果记录要求

每条用例执行后至少保留：

- 实际请求（方法、路径、关键 body）与响应（状态码、`code`、`message`、关键 `data`）；
- 关键数据库查询结果（订单、明细、支付、物流、券、库存、日志）；
- UI 用例的页面截图或 DOM 断言；
- 失败时的服务端日志片段；
- 使用的知识库版本与 `knowledge_id`。

# 9. 项目特殊约定

1. 支付为模拟支付，不存在真实扣款；“支付成功”只表示订单状态推进。
2. 金额为浮点数，断言时使用容差（如 `abs(actual-expected) < 0.01`），不要做字符串相等。
3. 时间字段为 UTC naive，ISO 字符串不带时区；不要用本地时间字符串直接比较。
4. 种子券有效期相对播种日期，跨日期执行可能变化；用例应动态查询券状态。
5. 商品图为内联 data URL 且当前 SVG 格式非法，**不要**把图片渲染作为断言点。
6. 单规格商品在详情页无法加购（已知前端缺陷）；UI 主流程用例应使用多规格商品（如运动鞋），或改用 API 准备数据。
7. 当前没有测试环境重置接口，数据清理只能删库/换库。

# 评审团 Agent · 设计文档

> **输入**：一份功能测试用例
> **输出**：一份评审报告（结构化 JSON + 人读 Markdown）
> **核心**：1 名主审 `qwen-max` + 2 名陪审 `deepseek-flash` / `kimi-k3` 独立盲评，主审二次调用完成问题融合与终审
> **形态**：FastAPI 异步 HTTP 服务，PostgreSQL + pgvector
> **状态**：设计定稿，代码未开始 · 2026-11-09

---

## 1. 一句话定位

一个**异步 HTTP 服务**：测试流水线把功能测试用例 POST 进来，服务调度三个模型独立盲评，由主审完成问题融合与终审，产出一份**带证据引用、可追溯、可人工复核**的评审报告。

评审的对象是**用例质量**（覆盖是否完整、步骤是否可执行、预期是否可判定、能否自动化），不是功能本身是否正确。

## 2. 共识决策记录

| # | 决策项 | 结论 |
|---|---|---|
| 1 | 输入形态 | 结构化 JSON 为主（步骤数组），`raw_text` 纯文本兜底 |
| 2 | 评审团构成 | 1 主审 + 2 陪审，三个**不同厂商/家族**的模型 |
| 3 | 模型分工 | 主审 `qwen-max`；陪审甲 `deepseek-flash`（业务/需求视角）；陪审乙 `kimi-k3 pro`（测试设计 + 自动化可行性视角） |
| 4 | 主审职责 | 盲评一次 + 仲裁一次，**两次独立调用**，防止锚定 |
| 5 | 三方关系 | 三份盲评意见**等权**，主审在自己那份上只有一票 |
| 6 | 主审权限 | 可否决陪审，但必须写明驳回理由；驳回的阻断项进入人工复核清单 |
| 7 | 知识库 | 分层检索：结构化索引（模块→功能点→规则/术语/已知限制/历史缺陷）+ 原文切片；PostgreSQL + pgvector |
| 8 | 知识库范围 | 从零建，先做 3–5 个高频模块，跑通后再扩 |
| 9 | 知识库缺口 | 评审中反复出现的"无依据判断"自动聚合为缺口清单，定期人工确认后入库 |
| 10 | 知识库未覆盖 | 降级评审 + 报告顶部醒目提示；问题区分"基于知识库验证"与"基于通用准则推断" |
| 11 | 问题融合 | 规则键分桶（步骤号 ±1 容差）→ embedding 同义判断 → 仲裁模型最终确认 |
| 12 | 结论档位 | 打回 / 有条件通过 / 待人工裁决；**系统永不自动判"通过"，通过只能由人工点** |
| 13 | 报告形态 | JSON（主数据）+ Markdown（人读），附录附三份原始意见 |
| 14 | 服务形态 | 异步作业：创建任务 → 轮询/webhook 取结果；另提供批量接口 |
| 15 | 技术栈 | Python + FastAPI + PostgreSQL + pgvector + 进程内 asyncio |
| 16 | 并发 | 单机并发 4 个评审任务，超出排队 |
| 17 | 鉴权 | 内部服务，API Key + 调用方标识 |
| 18 | 存档 | 每次模型调用的完整 prompt/输出、token 数、耗时全部落库 |
| 19 | 版本追溯 | 报告记录知识库版本号 + rubric 版本号 + prompt 版本号 |
| 20 | 合规 | 三个厂商 API 允许调用；按公司要求记录调用日志 |
| 21 | 验收 | 30 份人工标注种子集冷启动；上线后靠人工复核结论回写持续积累真值 |
| 22 | 规模 | 单批 ≤ 50 份，日 ≤ 200 份 |
| 23 | v1 范围 | 评审链路 + 报告 + 复核回写 + 知识库缺口清单 + 批量接口 |
| 24 | v1 不做 | 自动改写用例、复评 diff、知识库编辑界面、看板、多团队隔离 |

## 4. 明确不做（v1）

- **不自动改写用例**：只给修改建议，不产出改写后的用例文本。
- **不做复评 diff**：同一用例修改后重新提交视为新评审，不做版本对比（v1.5）。
- **不做知识库编辑界面**：知识库以 Markdown 文件 + Git 管理（v2）。
- **不自动放行**：任何情况下系统结论都不是"通过"。
- **不做多团队隔离**：单一内部团队使用（v2）。

## 5. 待定事项与风险

| # | 事项 | 说明 / 应对 |
|---|---|---|
| R1 | **知识库素材尚未提供** | 建议最小可用集先覆盖 5 个模块，候选：背包/仓库、挖宝、语音聊天室+打赏、帮会同盟/约战/宣战、奇穴装配（均来自现有测试点） |
| R2 | **黄金集没有现成真值** | 30 份种子集需 1–2 名测试专家标注 2–3 小时；上线后靠复核回写积累 |
| R3 | **模型档次不齐** | `deepseek-flash` 偏轻量，可能拖低业务视角；建议上线前用同一批用例做一次盲测，季度轮换一次视角绑定做校准 |
| R4 | **主审自我偏好** | 主审既盲评又仲裁，天然偏向自己的判断；用"三方等权 + 驳回留痕 + 阻断项人工复核"三约束兜底 |
| R5 | **上下文长度** | 主审要读三份原始意见 + 用例 + 知识库，需确认 `qwen-max` 的实际窗口与输出上限 |
| R6 | **成本无上限但需可观测** | 全量记录 token 与耗时；知识库单次注入上限 15k token 作为第一道闸 |
| R7 | **纯文本用例解析质量** | 预处理模型拆步骤可能拆错；拆分结果随报告返回供人核对，拆不出则降级为整篇评审 |

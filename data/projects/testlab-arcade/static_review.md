# TestLab Arcade UI 测试案例静态体检

> 审查对象：`source/ui_test_cases_v1.0.xlsx`（55 条，P0 41 / P1 14）
> 依据：`source/ui_spec.md`（UI 规范 V1.0）、`source/requirements.md`（一期策划案）
> 说明：以下为静态比对结论，不是模型评审结论；最终以逐条人工/模型评审为准。
> **重要**：本套用例由 AI 生成、未经人工复核，不能作为验收真值、评测标签或“已知正确”基线。

## 1. 覆盖范围

- 55 条均为 UI 布局、响应式与可访问性用例；**没有**策划案 §8 建议的登录/游戏功能用例（注册成功、重复邮箱、密码强度、登录失败、会话、权限、计分、失球、暂停、成绩保存等）。
- 因此本套用例不能证明一期功能需求已覆盖；若目标是功能验收，需要另建功能用例集。
- UI 规范 §13 明确“不实现的控件不要求出现”，UI-REG-006 是反向保护用例，合理。

## 3. 一般性质量观察

- 38 条用例的“操作步骤条数”与“预期结果条数”不一致；部分属于一步多断言，可接受，但评审时需要确认每条预期都有执行动作对应。
- 多条预期使用“约/清晰/足够/稳定”等措辞；UI 规范给了 ±4px/±8px 容差的地方可接受，未给阈值的地方不可判定。
- 多条用例前置条件只写“页面已加载/可触发请求”，未说明登录态、账号数据、网络条件；执行前需补齐。
- 55 条用例均无执行结果，缺陷编号为空；当前只能做静态评审，不能计算通过率。

## 4. 建议

1. 先确认本次要评审的“缺陷用例”具体是哪一条（或一组）；不要用 55 条整体直接跑真实模型，成本约 ¥1/条、耗时约 6–8 分钟/条。
2. 若目标是验证评审器，优先选 UI-LOGIN-006、UI-GAME-007、UI-RESP-002 这类有明确质量缺陷的用例。
3. 若目标是验证 TestLab 功能质量，需要补充策划案 §8 的功能用例；现有 UI 用例不能替代。


## 5. AI 生成、未复核带来的额外风险

- 期望值可能是模型按 UI 规范“推断”出来的，规范未定义的样式/状态容易被写成硬性要求（见 UI-LOGIN-006、UI-REG-005、UI-PROFILE-004）。
- 用例之间的粒度不一致：同一类检查有的拆成多条，有的合并成一条（UI-GAME-007、UI-RESP-002）。
- 没有执行结果与缺陷记录，无法证明这些用例能发现真实问题；只能证明“写出来了”。
- 不能把本套用例直接当评测集：若用它们做评审器的 ground truth，会把 AI 生成偏差当成标准答案。
- 正确处理顺序：静态体检 → 抽样模型评审 → 人工逐条裁决 → 冻结为可引用样本；裁决前只标记为 `candidate`。

# 人工裁决填写教程（TestLab Arcade）

> 适用对象：负责复核 AI 评审/静态审计结果的人工裁决人。
> 目标：把候选问题填成可追溯的 issue 级标签，而不是“看起来像标签”的 AI 猜测。
> 当前状态：8 个用例、19 条候选，全部 `pending`；本教程填完后才算 `decided`。

---

## 0. 先记住三句话

1. **AI 建议不是标签**：`ai_recommendation: likely_valid` 只是线索，必须自己核对用例与规范。
2. **规范没写 ≠ 用例错**：先判 `needs_spec`（需产品/设计确认），不要直接判 `invalid` 或 `valid`。
3. **签名才算数**：`adjudicator` 必须是真实的人；填 `AI`、`agent`、`system` 一律无效。

---

## 1. 文件角色

| 文件 | 作用 | 是否事实源 |
|---|---|---|
| `adjudication/<case_id>.yaml` | 每个用例的候选问题、证据、最终裁决 | **是** |
| `adjudication/adjudication.xlsx` | 带下拉选项的填写表：原始用例 + 候选问题 + 裁决 | 否，填写入口；`to-csv` 回收到 CSV |
| `adjudication/adjudication.csv` | 批量交换/评审会看板/导入格式 | 否，需导入 YAML |
| `adjudication/history.jsonl` | 每次裁决的追加历史 | 追加，不覆盖 |
| `adjudication/README.md` | 字段与流程说明 | 说明 |

> YAML 是唯一事实源。人工填写只改 `adjudication.xlsx`（或 CSV），填完 `to-csv` + `import-csv` 入库；xlsx 和 CSV 不要同时改。

## 2. 十分钟快速填写

### 路线 A：用裁决表 xlsx（推荐，带下拉框 + 原始案例）

1. 打开 `data/projects/testlab-arcade/adjudication/adjudication.xlsx`。
   - 「逐条裁决」里**一条候选一行**，左侧 ① 就是该用例的原始全文（前置条件 / 测试步骤 / 预期结果 / 规范引用），不用再翻 YAML；
   - ② 是 AI 指出的问题，④ 是 AI 的参考答案 —— **建议先自己判完再看 ④**，避免被 AI 锚定。
2. 只需要动 ③ 和 ⑤ 两块：
   - `final_validity` 裁决结论 —— **下拉**（valid / invalid / uncertain / needs_spec）
   - `final_severity` 严重级 —— **下拉**（blocker / major / suggestion，仅 valid 填）
   - `final_category` 问题分类 —— **下拉**（Rubric 18 类，仅 valid 填）
   - `correction` 改写建议 —— 手写（写“怎么改”，不是“建议补充”）
   - `adjudicator` 裁决人 —— 手写真实姓名/工号；先在「选项表」E 列填上名字，这一列也能下拉选
   - `adjudicated_at` 裁决时间 —— 可空，导入时自动补
   - `note` 备注 —— 手写
   - `case_verdict` 用例结论 / `case_defect_count` 缺陷数 / `case_note` 用例备注 —— **每个用例只在首行填一次**
3. 保存为 `.xlsx`（**不要另存为 CSV**，另存会丢下拉框）。
4. 在仓库根目录执行：

```powershell
python scripts\adjudication_sheet.py check       # 可选：先看有没有填写冲突
python scripts\adjudication_sheet.py to-csv      # 回收成 adjudication.csv（有冲突会报行号并中止）
python scripts\adjudicate.py import-csv --dry-run
python scripts\adjudicate.py import-csv
python scripts\adjudicate.py stats
```

5. `stats` 显示 `pending: 0` 且 `cases_done` 等于 8，即完成。

> 想重新生成空表：`python scripts\adjudication_sheet.py build`（表里已有裁决内容时会拒绝覆盖；确认丢弃才加 `--force`）。

### 路线 B：直接用 CSV（没有下拉框，适合脚本/文本处理）

1. 打开 `data/projects/testlab-arcade/adjudication/adjudication.csv`（已含原始用例列：`module`/`priority`/`source`/`ui_spec_ref`/`preconditions`/`steps`/`expected`）。
   > 若 CSV 正在 Excel/WPS 中打开，`export-csv` 与 `to-csv` 会提示被占用；先关闭文件再导出/覆盖。
2. 只填 `final_validity`、`final_severity`、`final_category`、`correction`、`adjudicator`、`adjudicated_at`（可空）、`note`，以及每个 case 只填一次的 `case_verdict`、`case_defect_count`、`case_note`；原始用例、候选、AI 建议等列不要动。
3. 保存为 **CSV UTF-8**。
4. 在仓库根目录执行：

```powershell
python scripts\adjudicate.py import-csv --dry-run
python scripts\adjudicate.py import-csv
python scripts\adjudicate.py stats
```

如果上次导入被中断，先执行 `python scripts\adjudicate.py recover-imports`；导入会在 `adjudication/.imports/` 写批次 journal 与备份，失败会自动回滚 YAML/history。

5. `stats` 显示 `pending: 0` 且 `cases_done` 等于 8，即完成。

### 路线 C：直接改 YAML 或命令行

## 3. 字段怎么填

### 3.1 `final_validity`（必填）

> 在 `adjudication.xlsx` 里这一列是**下拉框**，只能从下表四个值里选。

| 值 | 含义 | 什么时候用 |
|---|---|---|
| `valid` | 问题成立，需要修改用例 | 能用用例文本/规范证明；且影响执行或判定 |
| `invalid` | 问题不成立 | claim 与用例不符、规范并未要求、纯风格偏好、重复问题 |
| `uncertain` | 信息不足，无法判断 | 缺执行环境/缺产品说明；但**不是**规范未定义 |
| `needs_spec` | 规范/需求未定义，需产品确认 | 规范确实没写，无法由用例作者单方面修 |

判定树：

```text
claim 描述的文本/行为在用例里真实存在吗？
  否 → invalid
  是 → 规范或需求明确要求/禁止该行为吗？
        明确要求 → 再看影响
        明确禁止 → valid（可能 blocker）
        没写     → needs_spec
  影响：执行者能否稳定执行/判定？
        不能 → valid，严重级 blocker
        能但明显降低有效性 → valid，major
        只是可读性/规范建议 → valid，suggestion；若纯风格偏好 → invalid
```

### 3.2 `final_severity`（valid 必填）

| 值 | 判定标准 | 例子 |
|---|---|---|
| `blocker` | 无法执行、无法判定，或与权威依据直接冲突 | 一例两场景、没有可观察判定标准、规范明确要求但期望相反 |
| `major` | 明显降低有效性，执行者可凭经验补全 | 未说明请求延迟手段、步骤缺具体路径、焦点顺序未列清单 |
| `suggestion` | 可读性、规范性、优化类 | 措辞可更明确、补充示例数据 |

> `invalid` / `uncertain` / `needs_spec` **不要填 severity**；填了会被导入校验拒绝。

### 3.3 `final_category`（valid 必填）

只能从 Rubric 的 18 个分类中选（xlsx 里这一列同样是下拉框）：

```text
覆盖缺失、规则冲突、意图不符、前置不足、术语不一致、状态不自洽、
步骤不可执行、预期不明确、数据缺失、边界缺失、不可重复、歧义、
自动化不可行、状态不可读、定位不稳定、数据不可准备、框架不匹配、重复冗余
```

常见对应关系：

| 现象 | 建议分类 |
|---|---|
| 预期没有可观察判定标准 | 预期不明确 |
| 一个用例覆盖两个独立场景 | 状态不自洽 / 重复冗余（按根因选一个） |
| 没有请求延迟/挂起手段 | 不可重复 |
| 步骤缺少操作路径 | 步骤不可执行 |
| 只有界面、无法读取记录/接口结果 | 状态不可读 |
| 未指定页面/按钮/数据 | 前置不足 / 数据缺失 |
| 无法稳定自动化 | 自动化不可行 |

### 3.4 `correction`（valid 建议必填）

写“怎么改”，不要写“建议补充”。

| 差 | 好 |
|---|---|
| 建议补充预期 | 预期 2 改为：“保存中按钮显示‘保存中…’，`aria-busy=true`，且按钮 disabled；读取成绩列表确认无新增记录。” |
| 建议拆分 | 拆为两条：`UI-GAME-007A 启动中按钮禁用`、`UI-GAME-007B 保存中状态与重复提交`。 |
| 建议明确间距 | 相邻按钮水平间距 ≥ 8px，触控目标 ≥ 44×44px。 |

### 3.5 `adjudicator` / `adjudicated_at`

- `adjudicator`：真实姓名或稳定身份（如 `zhangsan`），不能用 `AI`、`agent`、`system`。
- `adjudicated_at`：ISO 8601，可省略；CLI/导入会自动填当前时间。

### 3.6 `note`

只写裁决理由或待确认信息，例如：

- `规范 §6.1 未定义颜色/字重，需设计确认`
- `与 CAND-02 同一根因，已合并计数`
- `本机无法构造请求延迟，暂判 uncertain`

### 3.7 用例级字段

| 字段 | 取值 | 说明 |
|---|---|---|
| `case_verdict` | `in_progress` / `pass` / `needs_fix` / `blocked` / `uncertain`（xlsx 里是下拉框） | 用例级结论；`in_progress` 用于还有候选未裁决 |
| `case_defect_count` | 整数（xlsx 里是 0–6 下拉，可留空） | 必须等于 `valid` 候选数；不填则自动计算 |
| `case_note` | 文本 | 拆分/重跑/待确认说明 |

> 用例级三列在 xlsx 里**只填每个用例的首行**，同用例其它行留空；`to-csv` 会自动补齐到该用例所有行。

**完成条件**：

- `pass` / `needs_fix` / `blocked` / `uncertain` 是最终结论，要求该用例**所有候选都已裁决**（无 `pending`）。
- 还有 `pending` 时只能填 `in_progress`，或先不填。
- `pass` 不允许存在 `valid`，也不允许存在 `uncertain`/`needs_spec`（有未确定项请用 `uncertain`）。
- `needs_fix` 至少一条 `valid`。
- `blocked` 至少一条 `valid` + `blocker`。

判定建议：

- `pass`：0 条 valid；
- `needs_fix`：≥1 条 valid，但没有 valid blocker；
- `blocked`：≥1 条 valid blocker；
- `uncertain`：关键候选是 uncertain/needs_spec，无法给结论。

## 6. 常见错误

| 错误 | 后果 | 正确做法 |
|---|---|---|
| 直接照抄 `ai_recommendation` | 标签仍是 AI 判断 | 自己核对 claim 与证据 |
| 规范没写就判 `invalid` | 把“设计缺口”当成“用例误报” | 判 `needs_spec` 并写 note |
| `valid` 不填 severity/category | 导入失败 | 两者都填 |
| `invalid` 填了 severity | 导入失败 | severity 留空 |
| `adjudicator` 写 AI/agent | 标签无效 | 写真实姓名/身份 |
| 改 `case_id`/`candidate_id`/claim 等只读列 | 导入找不到候选 | 只改 ③/⑤ 两块可填列 |
| 删除或合并候选行 | 丢失证据链 | 保留候选，`note` 写“与 CAND-xx 同一根因” |
| 把 xlsx 另存为 CSV | 下拉框全部丢失 | xlsx 只存 xlsx；要 CSV 就运行 `to-csv` |
| xlsx 和 CSV 同时改 | 后导入的覆盖前面的填写 | 只改一份（推荐 xlsx） |
| CSV 保存为 GBK | 中文乱码 | 保存 CSV UTF-8 |
| 只改 CSV 不导入 | YAML 仍是 pending | 执行 `import-csv` |
| 忘了先 `to-csv` | 导入的是旧 CSV | xlsx 改完先 `to-csv` 再 `import-csv` |
| 覆盖别人的裁决 | 历史可查但当前视图被改 | 多人复核用独立副本，不要共用一份 YAML |

## 7. 多人复核与一致性

当前工具是**单裁决人**模型：同一候选再次 `decide` 会覆盖 `final`，但 `history.jsonl` 保留旧记录。

多人复核建议：

1. 复制整个 `adjudication/` 目录为 `adjudication-reviewerB/`；
2. 两人各自填写；
3. 对比 CSV 的 `final_validity`/`final_severity`；
4. 分歧条目由第三人仲裁，写进最终目录；
5. 统计一致率（Cohen's kappa 或简单一致率），不要只报“都填完了”。

## 10. FAQ

**Q：AI 建议 `likely_valid`，我可以直接填 `valid` 吗？**
A：不可以。`likely_valid` 只表示“值得人工确认”，不是结论。

**Q：规范没写，应该判 `invalid` 还是 `needs_spec`？**
A：`needs_spec`。判 `invalid` 会把设计缺口误记成用例误报。

**Q：`uncertain` 和 `needs_spec` 有什么区别？**
A：`uncertain` 是信息不足（缺环境/缺数据）；`needs_spec` 是规范/需求未定义。两者都不填 severity。

**Q：一个用例有 6 条候选，`case_defect_count` 填几？**
A：只填裁决为 `valid` 的数量；同一根因的候选在 note 里注明合并关系，不要重复计数。

**Q：CSV 里 `case_verdict` 要每行都填吗？**
A：不用。同一 case 只在第一行填一次；但最终结论要求所有候选已裁决，否则请填 `in_progress`。

**Q：`case_defect_count` 可以手填吗？**
A：可以，但必须等于 valid 候选数；不确定就留空，导入时自动计算。

**Q：多人同时导入会覆盖吗？**
A：导入会检查 YAML 的原始 hash；发现被其他人修改会拒绝。不要共用同一份工作副本；多人复核请各自复制目录。

**Q：导入后能撤销吗？**
A：当前视图会被覆盖，但 `history.jsonl` 保留旧记录；重要撤销建议人工复核后重新裁决并写 note。

**Q：为什么没有自动判定？**
A：这是人工标签。自动判定会让 AI 生成偏差进入 ground truth，评测结果会失真。

**Q：为什么 CSV 没有下拉框？**
A：CSV 是纯文本，不能存数据验证。下拉框只在 `adjudication.xlsx` 里：xlsx 负责填写（可选、不会手滑写错值），CSV 负责交换与导入（`to-csv` 回收）。

**Q：xlsx 里把 AI 建议放在裁决列右边，是不是顺序错了？**
A：是故意的。先自己判、再看 ④ AI 提示，能减少“照着 AI 填”的锚定偏差；需要 AI 建议随时向右滚一屏即可。

**Q：在 xlsx 里选完，为什么 CSV / YAML 没变化？**
A：xlsx 只是填写入口。要依次执行 `adjudication_sheet.py to-csv` 和 `adjudicate.py import-csv`。

**Q：表格太宽看不全怎么办？**
A：Ctrl+滚轮缩到 70%–85%；前三列（用例编号/标题/模块）已冻结，右侧 ④ 是 AI 提示。

**Q：只写了一半能 `to-csv` 吗？**
A：可以。未填的候选按 `pending` 导出，导入时跳过；但填了「用例结论」的最终值时，该用例所有候选必须已裁决，否则导入会拒绝。
